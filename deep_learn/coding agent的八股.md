
# 项目介绍

##  1、1分钟版本

我做了一个基于 Java 的 Coding Agent，整体架构分为从入口、执行策略和 Harness 底座三个方面。
入口支持 CLI、TUI、微信和 Runtime API。执行策略包括默认的 ReAct、基于 DAG 的 Plan-and-Execute，以及由 Planner、Worker、Reviewer 协作的 Multi-Agent。
底层通过统一的 `LlmClient` 适配不同模型；通过 `ToolRegistry` 管理文件、Shell、代码搜索、Web 和 MCP 工具；同时实现了短期记忆、长期记忆、上下文压缩和 Skill 系统。
在工程保障方面，项目还实现了人工审批、路径和命令安全策略、操作审计、任务取消、LSP 诊断以及 Side-Git 快照回滚。

这个项目的核心价值，是把模型的概率性决策放进一套确定性的执行框架中，让 Coding Agent 的运行过程可控制、可观测、可审计、可恢复。
##  2、3分钟版本

我做了一个基于 Java 的 Coding Agent。整体架构分为从入口、执行策略和 Harness 底座三个方面。
首先是入口。项目支持 CLI、inline TUI、微信通道和 Runtime API。入口负责接收任务、解析斜杠命令、展开本地文件或 MCP 资源引用，然后选择对应的执行模式。

第二部分是执行策略，目前有三种。

默认模式是 ReAct。每一轮模型都会接收对话历史和工具定义。如果模型返回 tool call，系统就执行工具，再把结果作为 tool message 回灌给模型；当模型不再调用工具时，本次任务结束。
复杂任务可以使用 Plan-and-Execute。Planner 会先把目标拆成带依赖关系的 DAG，用户可以审阅、补充或者取消计划。执行阶段根据依赖关系选择当前可执行的任务，互不依赖的任务可以并行处理；如果执行早期失败，系统还可以根据错误信息重新规划。
第三种是 Multi-Agent。系统包含一个 Planner、两个 Worker 和 Reviewer。Planner 负责拆解任务，Worker 负责执行，Reviewer 负责检查结果。没有通过审查的步骤会带着 Reviewer 的反馈重新执行，并设置有限重试次数。互相独立的步骤可以分配给不同 Worker 并行处理。

这三种执行策略下面共享的是同一套 Harness 底座，而不是各自维护一套模型、工具和安全系统。

在模型侧，项目通过统一的 `LlmClient` 接口适配不同供应商，屏蔽消息协议、流式输出、tool call、token 统计、上下文窗口和图片输入等差异。

在上下文侧，系统会把基础 Prompt、执行模式规则、项目级 `PAI.md`、相关长期记忆、MCP 资源索引和 Skill 动态组装成 system prompt。项目同时区分对话历史、短期记忆和长期记忆；上下文接近窗口上限时，会压缩较早的对话，并保护 tool-call 和 tool-result 的完整配对关系。

在能力侧，所有内置工具和 MCP 动态工具都会注册到统一的 `ToolRegistry`。模型看到的是工具名称、描述和 JSON Schema，具体执行由 Harness 完成。工具覆盖文件操作、Shell、精确代码搜索、RAG、Web、浏览器、Skill 和记忆等能力。

同一轮存在多个 tool call 时，ToolRegistry 可以并行执行，但返回结果仍保持原始调用顺序，避免破坏消息协议。Harness 还统一负责工具超时、任务取消和错误结果回灌。

安全与恢复方面。文件操作受 `PathGuard` 限制，不能逃出项目目录；Shell 命令经过 `CommandGuard` 检查；写文件、执行命令和 MCP 工具可以触发人工审批；危险操作会记录到审计日志。每轮任务执行前后还会创建独立的 Side-Git 快照，修改出现问题时可以恢复工作区，同时不会污染用户原有的 Git 历史。

这个项目让我理解最深的一点是，Coding Agent 的工程难点不只是模型效果，而是如何管理模型的不确定性：模型负责决策，Harness 负责上下文、工具、并发、超时、安全、审计和恢复。

## 3、介绍一下记忆模块

我在这个项目里设计了一套分层记忆机制，主要包括项目规则、短期记忆和长期记忆，整个模块由 `MemoryManager` 统一管理。

项目规则通过 `PAI.md` 管理，保存当前仓库长期稳定的开发规范，比如技术栈、目录结构、测试命令和代码风格。这类信息适合团队共享，也可以提交到 Git。系统启动时会读取项目规则，并把它作为项目上下文注入 system prompt。

短期记忆主要维护当前会话中的历史消息，包括用户输入、模型回答和工具执行结果。它解决的是单次会话中的上下文连续性，让模型知道用户当前的目标、已经执行过哪些操作、工具返回了什么结果，以及还有哪些问题没有处理。

长期记忆保存跨会话复用的稳定事实，比如用户偏好、项目约定和之前明确做出的技术决策。它使用 JSON 文件持久化，程序启动时会加载已有内容，新增、删除或者清空记忆时会同步写回文件。保存时还会根据内容进行去重，避免同一个事实被重复记录。

一次请求进入 Agent 后，系统首先记录用户输入，然后根据当前问题检索相关长期记忆。检索结果不会直接混入普通对话，而是放到 system prompt 的“相关长期记忆”区域，再和项目规则、Skill、工具说明以及短期记忆一起发送给模型。

模型调用工具以后，工具结果也会进入短期记忆，作为下一轮推理的依据。例如模型先搜索代码，再读取具体文件，下一轮必须知道之前定位到了哪些文件、读取到了什么内容，才能继续完成任务。

考虑到文件内容和命令日志可能非常长，记忆模块不会无限制保存完整的工具输出，而是对用于记忆管理的工具结果进行截断，只保留必要摘要。这样可以避免单个工具结果快速消耗短期记忆预算。

在长期记忆的写入策略上，我采用的是显式保存，而不是自动提取每一轮对话。用户可以使用 `/save` 命令，也可以明确要求系统记住某项规则，然后由 Agent 调用 `save_memory` 工具完成保存。

这里主要考虑的是记忆污染问题。模型很难稳定判断一条信息是长期事实，还是只对当前任务有效的临时要求。如果自动保存每轮对话，很容易把临时文件路径、错误结论或者一次性操作写进长期记忆，后续又通过 system prompt 影响其他任务。因此，长期记忆只保存用户明确要求记录的稳定信息。

长期记忆还设计了 Scope 机制，分为 project scope 和 global scope。project scope 会绑定规范化后的项目路径，只能在当前项目中被检索，适合保存项目技术栈和开发约定；global scope 可以跨项目复用，适合保存用户通用的交流偏好和编码习惯。这样既能实现跨会话记忆，也可以避免不同项目之间的上下文相互污染。

长期记忆的召回目前采用轻量级关键词检索，没有使用向量数据库。系统会对中文和英文查询进行分词，再结合精确匹配、关键词覆盖情况和时间衰减计算相关度。

系统不会把全部长期记忆都放进 Prompt，而是根据当前用户问题按需召回，并使用 token 预算限制注入量。这样可以避免无关记忆干扰模型，也能防止长期记忆随着使用时间增加而不断占用上下文。

短期记忆需要解决的核心问题是上下文窗口有限。随着会话不断进行，用户消息、模型回答和工具结果会越来越多。当历史消息接近当前模型的上下文上限时，系统会自动压缩较早的短期记忆。

具体做法是把较早的用户消息、模型回答和工具执行结果交给模型生成摘要，然后用摘要替换原来的历史内容，同时保留最近三轮完整消息。摘要会重点保留用户目标、已经完成的操作、关键工具结果、已经形成的结论和仍未完成的问题。

这里比较关键的难点是工具调用协议。一次工具调用通常由 assistant 发出的 tool call 和随后返回的 tool result 组成。如果压缩切分点刚好落在两者中间，下一次模型请求就可能只有工具请求而没有结果，或者只有工具结果却找不到对应请求，最终导致模型 API 拒绝这组消息。

因此，我把压缩切分点限制在 user message 边界。系统从最近几轮用户消息开始保留整个尾部，确保其中的 tool call 和 tool result 一起保留，不会被历史压缩拆开。

压缩过程也做了失败保护。系统会先生成摘要和新的消息列表，只有摘要成功返回后，才会替换原来的历史消息。如果模型调用失败或者返回空摘要，系统会放弃本次压缩，继续使用原始历史，避免因为压缩失败破坏当前会话。

不同模型的上下文窗口大小不同，所以压缩阈值也不是固定值。切换模型以后，系统会根据新模型的上下文窗口重新计算短期记忆预算、长期记忆注入预算和自动压缩阈值，同时为摘要生成、工具调用和模型最终回答预留空间。

整体来看，这个记忆模块主要解决了三个问题：第一，不同生命周期的信息如何分层管理；第二，长期记忆如何通过 Scope 隔离并根据当前问题按需召回；第三，上下文窗口接近上限时，如何在保留关键任务状态和工具调用协议的前提下安全压缩短期记忆。

如果用一句话总结：

> 我把记忆模块设计成“分层存储、Scope 隔离、按需召回和安全压缩”的结构：项目规则保存团队规范，短期记忆维护当前会话并在上下文快满时压缩历史消息，长期记忆通过显式保存实现跨会话复用。

## 介绍一下工具部分怎么做的？


我在项目里通过 `ToolRegistry` 统一管理 Agent 的工具能力，包括文件操作、代码搜索、Shell、Web、浏览器会话、Skill、记忆和快照恢复等。

工具执行支持批量并行。如果模型一轮返回多个工具调用，系统会使用固定线程池并发执行，最大并发数是4，并通过批量超时防止某个工具长期阻塞。虽然工具完成顺序可能不同，但最终会按照模型原始调用顺序组装结果，保证 tool call 和 tool result 的对应关系稳定。

工具层还统一处理任务取消和异常。策略拒绝、执行失败、超时或者用户取消，都不会直接让 Agent 崩溃，而是转换成工具结果回灌给模型，让模型调整方案。

安全方面，我做了三层控制。第一层是 `PathGuard`，限制文件工具只能访问当前项目；第二层是 `CommandGuard`，拦截高风险 Shell 命令；第三层是 HITL 人工审批。

HITL 通过 `HitlToolRegistry` 包装统一执行入口。读文件和代码搜索等只读操作默认放行，写文件、执行命令、创建项目和快照恢复等有副作用的操作需要用户确认。用户可以批准、拒绝或者修改参数后执行。

HITL 只代表用户接受这次操作，不会绕过底层策略。即使用户批准写文件，路径仍然不能逃出项目目录；批准执行命令以后，命令仍然需要通过安全检查。所有危险操作还会写入审计日志。

Web 和浏览器的定位也不同。Web 工具负责搜索和静态页面正文抓取，速度更快、成本更低；浏览器负责动态渲染、登录态和页面交互。一般优先使用 Web，静态抓取失败后再切换浏览器。

一句话总结：

> 工具模块是 Agent 的统一能力执行层，负责并行调度、超时取消和结果回灌，并通过路径策略、命令策略、人工审批和审计保证工具操作安全可控。

## 面试口述版：工具模块

我在这个项目里通过 `ToolRegistry` 统一管理 Agent 的工具能力。目前包括文件读写、目录遍历、代码搜索、Shell 命令、RAG、Web、浏览器会话、Skill、长期记忆和快照恢复等工具。

工具模块不仅负责注册工具，更重要的是统一处理并行调度、超时取消、安全校验、人工审批、操作审计和结果回灌。上层不同的 Agent 执行模式共享同一个 `ToolRegistry`，所以这些执行规则和安全能力能够保持一致。

在代码定位方面，我提供了 `glob_files`、`grep_code`、`read_file` 和 `search_code` 几类工具。

`glob_files` 用于按照文件名快速筛选候选文件，`grep_code` 基于精确关键词或者正则搜索代码，找到位置后再通过 `read_file` 分段读取上下文。`search_code` 属于 RAG 语义检索，适合处理自然语言问题或者用户不知道具体类名的情况。

我的默认策略是优先使用 glob、grep 和分段读取，因为这些工具查询的是当前文件系统，结果比较确定，也容易通过文件和行号验证。RAG 主要作为语义检索的补充，而不是代替精确搜索。

文件读取支持 offset 和 limit，代码搜索也限制了匹配数量、单文件命中数和结果字符数。当结果达到预算时，工具会返回 partial 状态，并提示模型缩小搜索范围或者继续读取。这样可以防止一次工具调用把大量无关代码塞进上下文。

Web 和浏览器解决的是两种不同的联网场景。

Web 工具主要提供搜索和 HTTP 正文抓取。系统通过搜索服务获取候选页面，再使用 HTTP 客户端抓取 HTML，通过正文提取转换成 Markdown。它适合官方文档、博客、新闻和普通静态页面，特点是速度快、成本低，而且不需要维护浏览器状态。

浏览器则是有状态的页面交互环境，适合 JavaScript 动态渲染、SPA、登录态、点击、表单填写和截图等场景。当前内置工具主要负责浏览器会话的连接、断开和状态管理，具体页面操作通过外部浏览器工具接入。

在工具选择上，系统通常先使用 Web 搜索和静态抓取；如果目标页面依赖 JavaScript、需要登录状态，或者静态抓取拿不到正文，再切换到浏览器。浏览器的点击、输入和脚本执行可能改变外部状态，所以安全级别也高于普通 Web 抓取。


在并行执行方面，如果模型一轮只返回一个工具调用，系统会直接执行，避免创建线程池的额外开销。如果同一轮返回多个工具调用，`ToolRegistry` 会把它们转换成独立任务，通过固定线程池并行执行，并发度取工具数量和4之间的较小值。

批量执行使用 `invokeAll`，它既可以为整个批次设置统一超时，也可以保持 Future 列表和任务提交顺序一致。

工具实际完成的顺序可能不同。例如第二个文件可能先读取完成，但系统不会按照完成时间组装结果，而是按照模型原始调用顺序遍历 Future，再根据 tool call ID 生成对应的工具结果。

这样既获得了并行执行的效率，又能保证工具请求和工具结果之间的对应关系稳定。

工具模块还设计了两级超时。批量工具调用有统一的批次超时；`execute_command` 还有自己的进程级超时。如果整个批次到达超时时间，未完成的任务会被取消，并转换成标准化的超时结果，已经完成的工具结果仍然保留。

任务取消也是通过统一的 `CancellationContext` 向下传递。工具批次开始前和每个工具实际执行前都会检查取消状态。如果用户取消当前任务，尚未执行的工具不会继续产生副作用，而是返回取消结果。执行结束后，线程池会在 `finally` 中关闭，避免线程资源泄漏。

工具返回值使用统一的结构表示，除了文本，还可以携带图片。普通文件和命令工具通常返回文本；浏览器截图等工具可以返回图片内容。Agent 会保留文本结果，同时把图片转换成多模态消息发送给支持图片输入的模型。

工具异常不会直接让 Agent 主循环崩溃。参数解析失败、工具内部异常、策略拒绝、超时和用户取消，都会转换成模型可以理解的工具结果。模型看到失败原因后，可以调整参数、选择其他工具或者向用户说明任务无法继续。

在安全方面，我设计了多层防护。

第一层是资源限制。文件读取有最大行数，写文件有单次大小限制，代码搜索和命令输出都有字符预算。它主要防止模型生成异常大的输入，也防止工具结果快速占满上下文。

第二层是路径安全。文件读写、目录遍历和代码搜索都要经过 `PathGuard`。它会把模型提供的路径解析成规范化的绝对路径，再检查最终目标是否位于当前项目根目录内。

除了绝对路径越界和 `..` 目录穿越，它还会检查符号链接。如果一个项目内的符号链接实际指向项目外部，也会被拒绝。这样可以避免模型通过路径拼接或者软链接访问工作区之外的文件。

第三层是命令安全。`execute_command` 在创建进程前会经过 `CommandGuard`，拦截明显危险的命令模式，例如提权、全盘删除、磁盘格式化、危险的磁盘写入、fork bomb、全文件系统扫描，以及下载脚本后直接交给 Shell 执行。

这些安全策略属于硬限制。即使用户批准了工具调用，路径和命令仍然要通过策略检查，人工授权不能绕过系统安全边界。

对于有副作用的工具，我还增加了 HITL，也就是 Human in the Loop 人工审批。实现上不是把审批逻辑分别写进 `write_file`、`execute_command` 等工具，而是在普通 `ToolRegistry` 外增加一个 `HitlToolRegistry`，统一拦截危险工具。

`ApprovalPolicy` 负责判断工具是否需要审批。读取文件、列目录和搜索代码等只读工具默认直接执行；写文件、执行命令、创建项目和快照恢复等可能修改状态的工具，需要用户确认。

当危险工具到达执行入口时，系统会根据工具名称、参数和风险说明构造审批请求。用户可以批准、拒绝、跳过，也可以修改参数后再批准。

如果用户修改了参数，后续执行使用的是用户确认后的最终参数，而不是模型最初生成的参数。例如模型准备执行一个范围过大的命令，用户可以缩小命令范围后再允许执行。

如果用户拒绝或者跳过，系统不会直接终止整个 Agent，而是把审批结果作为工具结果回灌给模型。模型会知道这项操作没有执行，然后选择只读方案、修改计划，或者明确告诉用户当前任务受到权限限制。

HITL 还支持对同名工具持续放行，适合一段时间内连续执行同类操作。但持续放行只会跳过重复的人工确认，不会关闭 `PathGuard` 和 `CommandGuard`。

工具执行还接入了审计链路。用户拒绝记录为 HITL deny，安全策略拦截记录为 policy deny，实际执行成功记录为 allow，执行异常记录为 error。日志中会保存工具名称、脱敏后的参数、执行结果类型和耗时，方便后续排查 Agent 做过什么以及为什么失败。

写文件成功以后还会触发 post-edit LSP 诊断。诊断不会阻塞写文件本身，而是在后续模型调用前作为上下文反馈给 Agent。这样模型写完代码以后可以看到语法错误、类型错误或者其他诊断，再继续修复。

每轮任务外层还有 Side-Git 快照。任务执行前创建 pre-turn 快照，执行结束后创建 post-turn 快照。如果工具修改了错误文件，可以通过快照恢复。`revert_turn` 本身也是危险工具，所以同样要经过人工审批和审计。

我认为工具模块最重要的设计，是把模型的不确定性限制在“选择什么工具、生成什么参数”这一层，后续的并发调度、超时取消、路径边界、命令策略、人工审批和操作审计都由 Harness 确定性执行。

如果用一句话总结：

> 我通过 `ToolRegistry` 建立了统一的工具执行链，通过固定线程池实现并行和结果保序，通过超时与取消控制执行生命周期，再通过 HITL、PathGuard、CommandGuard、AuditLog、LSP 和 Side-Git 共同保证工具操作安全、可追踪、可诊断、可恢复。




## 安全怎么保证的？

安全方面，我主要做了三层控制，分别解决文件越界、危险命令和模型自主执行高风险操作的问题。

第一层是 `PathGuard`。文件读取、写入、目录遍历和代码搜索在执行前，都会先把模型提供的路径转换成规范化绝对路径，再判断它是否位于当前项目根目录内。这样可以拦截绝对路径越界和 `..` 目录穿越。对于已经存在的路径，还会解析符号链接，避免项目内部的软链接实际指向项目外部。路径检查属于硬限制，不能通过人工批准绕过。

第二层是 `CommandGuard`。模型生成 Shell 命令后，系统不会直接创建进程，而是先做静态规则检查，拦截提权、全盘删除、磁盘格式化、fork bomb、全文件系统扫描以及下载脚本后直接执行等高风险模式。被拦截的命令不会执行，而是返回明确的策略拒绝原因，让模型选择更安全的替代方案。

第三层是 HITL，也就是 Human in the Loop。它主要解决一个问题：有些操作本身合法，但是否应该执行，需要用户做业务判断。比如写文件、执行命令、创建项目和快照恢复并不一定危险，但都可能产生副作用，所以默认需要人工确认。

实现上，我没有把审批逻辑分别写进每个工具，而是通过 `HitlToolRegistry` 包装统一的工具执行入口。用户可以批准、拒绝、跳过，也可以修改参数后再批准。如果用户修改了参数，系统会使用确认后的参数执行。

这三层的职责是不同的：`PathGuard` 和 `CommandGuard` 负责系统不可突破的安全边界，HITL 负责边界内的操作授权。因此，即使用户批准了写文件，目标路径仍然不能逃出项目目录；即使批准了 Shell 命令，它仍然需要通过命令安全检查。

最后，危险工具还会进入审计链路，记录这次操作是被用户拒绝、被策略拦截、执行成功还是执行异常。这样就形成了“硬策略限制、人工授权、事后审计”的完整安全链路。







##  Web 和浏览器解决的是两种不同的联网场景。

Web 工具主要提供搜索和 HTTP 正文抓取。系统通过搜索服务获取候选页面，再使用 HTTP 客户端抓取 HTML，通过正文提取转换成 Markdown。它适合官方文档、博客、新闻和普通静态页面，特点是速度快、成本低，而且不需要维护浏览器状态。

浏览器则是有状态的页面交互环境，适合 JavaScript 动态渲染、SPA、登录态、点击、表单填写和截图等场景。当前内置工具主要负责浏览器会话的连接、断开和状态管理，具体页面操作通过外部浏览器工具接入。

在工具选择上，系统通常先使用 Web 搜索和静态抓取；如果目标页面依赖 JavaScript、需要登录状态，或者静态抓取拿不到正文，再切换到浏览器。浏览器的点击、输入和脚本执行可能改变外部状态，所以安全级别也高于普通 Web 抓取。
