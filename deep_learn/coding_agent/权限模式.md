# 本项目一共有几种权限模式？各有什么不同。

FirstCoder 一共有三种权限模式，分别是 `standard`、`aggressive` 和 `bypass`。`standard` 是默认模式，安全性最高，项目内普通文件读取和只读 Git 操作可以直接执行，但写文件、删除文件、执行 Shell、访问网络、调用 MCP，以及访问项目外或敏感路径，通常需要用户确认。`aggressive` 是提高自动化程度的模式，它会自动允许项目内普通文件写入，以及 `pytest`、`ruff`、`mypy`、`npm test` 等白名单中的常见验证命令，但删除文件、访问网络、敏感文件、危险 Shell 和项目外操作仍然需要确认或直接拒绝。`bypass` 则用于完全自动化或基准测试，默认策略会放行所有权限请求，不再暂停等待用户审批，同时把文件沙箱从项目范围切换为 unrestricted。不过 bypass 并不是完全取消所有安全机制：已经保存的显式拒绝规则仍然优先于 bypass；文件修改仍可执行写前审查，如果审查失败，操作依然会被阻止。

简单来说：
> `standard` 是谨慎执行，`aggressive` 是自动放行项目内常规开发操作，`bypass` 是不进行交互式审批并解除项目沙箱限制。

还要区分三个概念：权限模式只有这三种；一次权限检查的结果是 `allow`、`ask` 或 `deny`；文件系统沙箱则是另一套机制，standard 和 aggressive 使用项目级沙箱，bypass 使用 unrestricted。

# ask时，给用户的选择有哪些
FirstCoder 的权限策略返回 `ASK` 后，普通权限确认通常会给用户三个选择：`Deny`、`Allow once` 和 `Allow always`。
`Deny` 只拒绝当前工具调用；
`Allow once` 只允许本次执行；
`Allow always` 除了允许本次执行，还会根据文件路径、命令前缀、网络主机或 MCP 工具等作用域保存一条长期授权规则，后续匹配的请求可以直接放行。不过，并不是所有工具都支持长期授权，例如 `python_exec` 和 `apply_patch` 会关闭 `allow_always`，此时只显示拒绝和允许一次。
如果这次 `ASK` 是由写前审查产生的，用户看到的是修改预览，主要选择是拒绝或者应用本次已预览的修改，不能保存长期授权；用户还可以在拒绝时附带反馈，让模型知道应该怎样调整代码。

可以归纳为：

```
普通权限确认：
1. Deny
2. Allow once
3. Allow always（仅工具允许时显示）

写前审查确认：
1. Deny
2. Apply reviewed change
3. Reject with feedback（通过文字反馈拒绝）
```

需要注意，当前没有“永远拒绝”的用户选项，`Deny` 和 `Reject with feedback` 都只针对本次调用。

# `Allow always` 的作用域是怎样确定的？

FirstCoder 的 `Allow always` 不是永久放行整个工具，而是根据当前 `PermissionRequest` 的操作类型，生成一条尽量小范围的长期授权规则。文件读取、写入和删除默认使用 `EXACT_PATH`，也就是只授权当前这个文件的规范化绝对路径；Shell 使用 `COMMAND_PREFIX`，但为了避免把权限扩大到整个解释器，当前实现会把本次完整命令作为前缀，例如允许 `pytest tests`，后续相同命令或在其后追加参数的命令可以匹配，但不会直接放行所有 `pytest`；Git 操作按子命令授权，例如允许 `status` 后，可以匹配 `status --short`，但不能匹配 `reset`；网络请求按主机名授权，例如允许访问 `example.com`，后续访问这个主机的其他页面可以匹配；环境变量按具体变量名授权；MCP 则按具体的 MCP 工具授权。每条授权还必须匹配相同的操作类型，例如某个路径的读取授权不能自动变成写入授权。

对应关系是：

|权限操作|`Allow always` 的默认作用域|
|---|---|
|文件读取、写入、删除|当前文件的精确绝对路径|
|Shell|当前完整命令前缀|
|Git|当前 Git 子命令|
|网络请求|当前主机名|
|环境变量|当前环境变量名|
|MCP|当前 MCP 工具|

例如：

```
允许 write("src/config.py")
→ 只长期允许写入这个文件
→ 不代表允许写入整个 src 目录
→ 也不代表允许删除这个文件
```

另外，工具可以在自己的权限声明中设置 `allow_always=False`。例如 `python_exec` 和 `apply_patch` 风险范围不容易精确界定，所以只能允许本次，不能创建长期授权。

一句话概括：

> FirstCoder 根据操作类型自动计算最小授权范围，并同时匹配操作类型和目标作用域，避免用户允许一次具体操作后，意外放开整个工具。

# 讲一下`Allow always` 的Scope机制。一个授权规则长什么样？不同的工具Scope有什么不同

FirstCoder 的 `Allow always` 本质上是把用户当前这次授权转换成一条持久化的 `PermissionGrant`。它不会直接永久放行整个工具，而是根据权限操作类型计算一个尽可能小的 Scope。后续工具调用生成新的 `PermissionRequest` 后，系统会先比较操作类型，再判断请求目标是否落在这个 Scope 内；两者都匹配才会自动放行。

一条授权规则大致长这样：

```
{
  "id": "grant_perm_write_xxx",
  "effect": "allow",
  "action": "write_path",
  "scope_type": "exact_path",
  "scope_value": "E:\\project\\src\\config.py",
  "created_at": "2026-09-03T10:00:00+00:00",
  "reason": "用户选择 allow always"
}
```

各字段的含义是：

- `id`：授权规则的唯一标识。
- `effect`：规则效果，当前 `Allow always` 创建的是 `allow`。
- `action`：允许的操作类型，例如读取、写入、Shell 或网络。
- `scope_type`：使用哪一种作用域匹配方式。
- `scope_value`：具体允许的路径、命令、主机或工具。
- `created_at`：规则创建时间。
- `reason`：规则的来源或创建原因。

这里特别重要的是，匹配条件是：

```
action 相同
并且
scope 匹配
```

例如，下面的规则只允许写入指定文件：

```
action = write_path
scope_type = exact_path
scope_value = E:\project\src\config.py
```

它不能用于读取或删除这个文件，因为读取对应 `read_path`，删除对应 `delete_path`，操作类型不同。

不同工具的 Scope 实际上是按照权限操作类型确定的：

|工具或操作|Scope 类型|Scope 值|匹配方式|
|---|---|---|---|
|`view`、`read_multi` 等读取工具|`EXACT_PATH`|规范化后的绝对路径|只匹配同一文件路径|
|`write`、`edit` 等写入工具|`EXACT_PATH`|规范化后的绝对路径|只允许写同一个文件|
|`delete`|`EXACT_PATH`|规范化后的绝对路径|只允许删除同一个目标|
|`shell`|`COMMAND_PREFIX`|本次完整命令|匹配相同命令或在其后追加参数|
|Git 工具|`COMMAND_PREFIX`|Git 子命令|例如 `status` 可以匹配 `status --short`|
|`fetch`、`web_search` 等网络操作|`HOST`|规范化后的主机名|同一主机下的地址可以匹配|
|环境变量读取|`ENV_KEY`|转成大写的变量名|只匹配同一个环境变量|
|MCP 工具|`MCP_TOOL`|MCP 工具的完整标识|只匹配同一个 MCP 工具|

例如，用户永久允许：

```
shell("pytest tests")
```

系统保存：

```
action = execute_shell
scope_type = command_prefix
scope_value = pytest tests
```

以后：

```
pytest tests
→ 匹配

pytest tests -q
→ 匹配

pytest other_tests
→ 不匹配

rm -rf src
→ 不匹配
```

Shell 的长期授权还会拒绝带有 `&&`、`;`、管道、重定向、换行等控制符的请求，防止模型在已授权命令后拼接另一条危险命令。

网络授权则按主机匹配。例如用户永久允许：

```
https://example.com/api/users
```

保存的 Scope 是：

```
scope_type = host
scope_value = example.com
```

之后访问 `example.com` 的其他路径可以匹配，但访问 `api.other.com` 不会匹配。

项目还支持 `PATH_TREE`，它表示整个目录及其子目录：

```
scope_type = path_tree
scope_value = E:\project\worktree
```

不过普通用户点击 `Allow always` 时，文件操作默认只生成更保守的 `EXACT_PATH`，不会自动放大为整个目录树。`PATH_TREE` 主要用于系统内部明确配置的场景，例如允许后台 coder 在自己的隔离 Worktree 中修改文件。

这些授权最终持久化在 FirstCoder 数据目录的 `permissions.json` 中，因此后续 Session 也可以继续使用。并不是所有工具都允许创建这种规则；如果工具的 `ToolPermissionSpec` 设置了 `allow_always=False`，审批界面就不会提供 `Allow always`，例如 `python_exec` 和 `apply_patch` 只能逐次批准。

一句话概括：

> `Allow always` 负责创建长期授权，Scope 负责限制这条授权能够覆盖什么目标；FirstCoder 根据操作类型选择精确路径、命令前缀、主机名、环境变量或 MCP 工具等匹配方式，避免一次授权被无限扩大。

# 不同的工具ask时用户能看到什么



> 用户在 `ASK` 时看到哪些选项，既取决于工具是否设置了 `allow_always=False`，也取决于这次暂停是“权限策略要求审批”，还是“写前审查要求确认”。

## 一、支持 `Allow always` 的工具

下面这些工具没有关闭 `allow_always`，如果它们因为权限策略返回 `ASK`，用户通常会看到：

```
Deny
Allow once
Allow always
```

|工具类别|工具|
|---|---|
|文件读取|`ls`、`view`、`grep`、`glob`、`tree`、`read_multi`|
|文件修改|`write`、`edit`、`delete`|
|Shell 与进程|`shell`、`diagnostics`、`process_start`|
|Git|`git_status`、`git_diff`、`git_log`|
|网络|`fetch`、`web_search`|
|外部工具|动态加载的 MCP 工具|

其中，Git 的三个只读工具在项目内通常会被直接 `ALLOW`，所以正常情况下不会出现审批界面；只是它们的权限声明本身没有禁止 `Allow always`。

## 二、不支持 `Allow always` 的工具

当前明确设置了 `allow_always=False` 的是：

```
python_exec
apply_patch
```

当它们进入普通权限审批时，用户只能看到：

```
Deny
Allow once
```

原因是它们每次调用的内容和影响范围变化很大，不适合通过一条简单 Scope 长期放行。

## 三、同一个工具看到的选项也可能不同

以 `write` 为例，它本身支持 `Allow always`，但是在不同情况下，用户看到的选项可能不同。

### Standard 模式下写文件

Standard 默认认为写文件需要审批：

```
write("src/app.py")
→ 权限策略返回 ASK
→ 同时生成写前预览
```

此时用户看到：

```
Deny
Allow once
Allow always
```

还可以在拒绝时附带反馈。

### Aggressive 模式下写普通文件

Aggressive 的权限策略会自动允许项目内普通写入：

```
write("src/app.py")
→ 权限策略返回 ALLOW
```

但是普通交互式 Session 默认还开启写前审查，所以系统可能因为“需要用户确认这份 diff”而暂停。

这时候不是在询问是否长期授权，而是在询问是否应用当前预览，因此用户看到：

```
Deny
Apply reviewed change
```

不会显示 `Allow always`，因为权限策略本身已经允许，当前暂停只是写前审查门禁。

### Aggressive 模式下写敏感文件

例如：

```
write(".env")
```

Aggressive 也不会自动允许敏感写入：

```
权限策略返回 ASK
```

由于 `write` 支持长期授权，此时又会显示：

```
Deny
Allow once
Allow always
```

## 四、四个修改工具的具体区别

|工具|是否支持长期授权|普通权限 `ASK` 时|仅写前审查暂停时|
|---|---|---|---|
|`write`|是|Deny / Allow once / Allow always|Deny / Apply reviewed change|
|`edit`|是|Deny / Allow once / Allow always|Deny / Apply reviewed change|
|`delete`|是|Deny / Allow once / Allow always|Deny / Apply reviewed change|
|`apply_patch`|否|Deny / Allow once|理论上只有 Deny / Apply reviewed change，但当前它设置了 `allow_auto=False`，通常先进入普通权限审批|

只要生成了写前预览，用户还可以使用：

```
Reject with feedback: <修改意见>
```

拒绝本次修改，并把原因返回给模型。

## 五、没有权限声明的工具

还有一些工具没有配置 `ToolPermissionSpec`，因此不会产生权限系统的 `ASK`，也不会显示上述选项，例如：

```
think
task_create
task_update
task_list
task_revise
delegate
background_status
background_cancel
process_status
process_logs
process_stop
retrieve_archive
load_skill
```

其中 `ask_user` 虽然也会暂停等待用户，但它是模型主动向用户提问，不属于权限审批。

## 最终结论

可以这样记：

```
普通权限 ASK
├─ 工具支持 allow_always
│  → Deny / Allow once / Allow always
│
└─ 工具不支持 allow_always
   → Deny / Allow once

写前审查单独要求确认
→ Deny / Apply reviewed change
```

所以，不同工具在 `ASK` 时看到的选项确实可能不同；但决定因素不只是工具名称，还包括工具的 `allow_always` 配置，以及这次暂停究竟来自权限策略还是写前审查。




# Apply reviewed change什么时候会出现

`Apply reviewed change` 会在下面这种情况出现：

> 权限系统已经决定允许这次操作，但 Session 的写前审查要求用户确认实际修改内容。

完整条件是：

```
工具支持写前预览
并且
Session 开启了写前审查
并且
权限预检结果已经是 ALLOW
并且
当前不是 bypass 模式
```

支持写前预览的工具有：

```
write
edit
apply_patch
delete
```

典型例子是 aggressive 模式下写入普通项目文件：

```
模型调用 write("src/app.py")
        ↓
aggressive 权限策略判断：
项目内普通写入，可以 ALLOW
        ↓
但是 Session 开启了写前审查
        ↓
系统生成文件 diff
        ↓
用户看到：
Deny
Apply reviewed change
```

此时用户确认的不是“是否授予写文件权限”，因为权限系统已经允许了；用户确认的是：

> 我已经看过这份具体修改，是否把它真正应用到文件中？

`Apply reviewed change` 本质上仍然是一次性的允许，不会生成长期 grant。

## 已有长期授权时也可能出现

例如用户之前已经为 `src/app.py` 保存了 `Allow always`：

```
write("src/app.py")
→ 命中 allow grant
→ 权限结果为 ALLOW
→ 但是仍需检查具体 diff
→ 显示 Apply reviewed change
```

这说明：

```
Allow always
→ 长期允许对这个路径发起写操作

Apply reviewed change
→ 确认本次具体修改内容
```

两者属于不同层次。

## 什么情况下不会出现

如果权限策略本身返回 `ASK`，显示的是普通权限选项：

```
Deny
Allow once
Allow always（工具支持时）
```

即使界面同时展示了 diff，按钮通常仍然叫 `Allow once`，而不是 `Apply reviewed change`。

例如 Standard 模式第一次调用 `write`：

```
权限策略返回 ASK
→ 显示 Deny / Allow once / Allow always
```

Bypass 模式下虽然系统仍可生成写前预览，但不会暂停等待确认，因此不会显示 `Apply reviewed change`。

后台隔离 coder 会关闭逐次写前确认，也不会出现这个选项。

需要特别说明的是，`apply_patch` 虽然支持生成写前预览，但它设置了：

```
allow_auto=False
allow_always=False
```

所以在 Standard 和 Aggressive 下，它的权限策略通常直接返回 `ASK`，显示的是：

```
Deny
Allow once
```

而不是 `Apply reviewed change`。

一句话总结：

> `Apply reviewed change` 出现在“权限已经允许，但具体文件改动仍需人工看 diff 确认”的场景；它是写前审查按钮，不是普通权限授权按钮。
# 那些工具可以看到Reject with feedback选择

FirstCoder 中，只有能够生成写前预览的文件修改工具，才会在权限界面看到 `Reject with feedback` 的提示。目前包括 `write`、`edit`、`delete` 和 `apply_patch`。这些工具执行前，系统可以计算出文件修改后的结果并生成 diff，因此用户不但可以拒绝，还可以附带原因，例如输入 `reject: 请保留原来的异常处理`。系统会取消本次工具调用，并把这段反馈放入失败的工具结果中返回给模型，让模型根据反馈重新生成修改方案。

对应关系是：

|工具|是否支持写前预览|是否显示 `Reject with feedback`|
|---|---|---|
|`write`|是|是|
|`edit`|是|是|
|`delete`|是|是|

```
        ↓

```

如果写前预览生成失败，系统会直接阻止操作，不会进入正常审批；如果是 bypass 模式，系统虽然可能生成预览事件，但不会暂停等待用户输入，因此也不会显示这个交互提示。普通命令行适配器能够解析 `reject: ...`，但当前主要是 TUI 会明确把它展示给用户。

> `Reject with feedback` 是写前审查提供的反馈式拒绝能力，目前只适用于能够生成文件变更预览的 `write`、`edit`、`delete` 和 `apply_patch`。

# 写前预览是什么？

FirstCoder 的写前预览，是在文件修改工具真正产生副作用之前，由本地代码根据工具参数计算出“如果执行，文件会发生什么变化”，并把结果以 diff 的形式展示或记录下来。它主要支持 `write`、`edit`、`delete` 和 `apply_patch`。例如 `write` 会比较原文件和新内容，`edit` 会验证待替换文本是否存在并计算替换结果，`apply_patch` 会先解析补丁并进行 dry-run，`delete` 会列出即将删除的文件。在这个阶段只读取和模拟，不真正修改文件。

完整链路是：

```
模型生成文件修改工具调用
→ 权限预检
→ 本地生成写前预览
→ 记录文件修改类型、diff 和原文件摘要
→ 展示给用户
→ 用户允许或拒绝
→ 允许后检查预览是否仍然有效
→ 执行保存的原始工具调用
```

写前预览除了让用户知道 Agent 准备修改什么，还解决了一个并发安全问题：生成预览时，系统会记录相关文件的内容摘要；用户确认后、正式执行前，再重新计算摘要。如果文件在等待确认期间被其他线程、进程或用户修改，原预览就会被判定为过期，系统拒绝执行并要求重新生成 diff，防止用户批准的是 A 内容，最终落盘的却是 B 内容。

在不同权限模式下，它的作用略有不同。Standard 模式中，文件写入通常本来就需要审批，写前预览会作为审批信息一起展示；Aggressive 模式可能已经允许项目内普通写入，但普通交互式 Session 仍可以通过写前预览要求用户确认具体 diff，此时显示 `Apply reviewed change`；Bypass 模式不会暂停等待用户，但仍会生成预览事件，如果预览无法安全生成，操作仍然会被阻止。后台隔离 coder 因为没有用户交互通道，并且修改被限制在独立 Git Worktree 中，所以会关闭逐次写前确认，最后由父 Agent统一审查 Worktree diff。

用户还可以使用：

```
reject: 请保留原标题，只修改第二段
```

拒修改并附带反馈。这段反馈会作为原工具调用的失败结果返回模型，让模型重新生成修改方案。

一句话概括：

> 写前预览是在文件真正修改前，由可信的本地代码模拟操作、生成 diff 并记录文件快照；它既让用户能够审查具体改动，也通过执行前的快照复核，保证用户批准的内容和最终执行的内容一致。

# `apply_patch` 的 dry-run 是怎样实现的？

`apply_patch` 的 dry-run 并不是复制一份项目，也不是调用 Git，而是把一次补丁执行拆成两个阶段：

```
规划阶段：解析、校验、在内存中计算结果
提交阶段：真正写入和删除文件
```

当 `dry_run=True` 时，只执行规划阶段，跳过提交阶段。

## 1. 先把 Patch 解析成执行计划

例如：

```
*** Begin Patch
*** Update File: app.py
@@
-debug = True
+debug = False
*** End Patch
```

解析后得到：

```
PatchPlan
└── PatchOperation
    ├── action = update
    ├── path = app.py
    ├── move_to = None
    └── hunks
        ├── old_lines = ["debug = True"]
        └── new_lines = ["debug = False"]
```

当前支持四类语义：

```
add       新增文件
update    修改文件
delete    删除文件
move      修改后移动文件
```

## 2. 创建待提交列表

执行计划时不会立刻修改文件，而是先创建两个内存列表：

```
pending_writes: list[tuple[Path, str]]
pending_deletes: list[Path]
```

它们分别表示：

```
pending_writes
→ 如果最终提交，要向哪些路径写入什么内容

pending_deletes
→ 如果最终提交，要删除哪些路径
```

另外还会记录：

```
changed_files
created_files
deleted_files
moved_files
diff_sections
```

## 3. 在内存中规划每个操作

对于新增文件：

```
检查目标文件是否已经存在
→ 已存在则失败
→ 不存在则将“路径＋新内容”放入 pending_writes
→ 生成新增文件 diff
```

对于更新文件：

```
检查源文件存在且是普通文件
→ 使用 UTF-8 读取当前内容
→ 在内存字符串中查找每个 hunk 的旧内容
→ 没找到则失败
→ 找到多次则失败，要求提供更精确的上下文
→ 找到一次则在内存中替换
→ 将替换后的内容放入 pending_writes
→ 生成修改 diff
```

例如：

```
count = text.count(old_text)

if count == 0:
    raise ValueError("没有找到要替换的内容")

if count > 1:
    raise ValueError("请提供更精确的上下文")

text = text.replace(old_text, new_text, 1)
```

如果是移动文件：

```
检查目标路径不存在
→ 将修改后内容加入目标路径的 pending_writes
→ 将原路径加入 pending_deletes
```

对于删除文件：

```
检查目标存在且是文件
→ 读取原内容
→ 将路径加入 pending_deletes
→ 生成删除 diff
```

到这里为止，所有变化都只存在于内存列表中，项目文件没有改变。

## 4. `dry_run` 决定是否真正提交

核心判断是：

```
if not dry_run:
    for target, text in pending_writes:
        target.write_text(text)

    for target in pending_deletes:
        target.unlink()
```

所以：

```
dry_run=True
→ 不进入 if
→ 不创建文件
→ 不覆盖文件
→ 不删除文件

dry_run=False
→ 依次执行 pending_writes
→ 再执行 pending_deletes
```

它不是为 dry-run 单独实现一套 Patch 算法，而是所有模式都先完成同样的规划，只在最后决定要不要把规划结果写到磁盘。

## 5. dry-run 仍然会返回执行结果

即使不修改文件，它仍会返回：

```
{
  "changed_files": ["app.py"],
  "created_files": [],
  "deleted_files": [],
  "moved_files": [],
  "diff": "--- a/app.py\n+++ b/app.py\n...",
  "diff_truncated": false
}
```

因此系统能够知道：

- 补丁能否应用。
- 会影响哪些文件。
- 哪些文件会被新增、删除或移动。
- 修改前后有什么差异。
- diff 是否因为超过限制而被截断。

合并后的 diff 最多保留约 20000 个字符，过长时会截取头尾部分。

## 6. 写前预览怎样使用 dry-run

写前预览处理 `apply_patch` 时，会先执行：

```
_apply_plan(sandbox, plan, dry_run=True)
```

这一步主要验证：

```
路径是否合法
文件是否存在
目标文件是否冲突
Patch hunk 是否能够唯一匹配
补丁整体是否具备执行条件
```

然后写前预览服务再根据 PatchPlan 在内存中推导每个文件的修改后状态，为每个文件生成独立的 `ReviewFile`、diff 和 SHA-256 快照。

所以两者的关系是：

```
apply_patch dry-run
→ 验证补丁可以应用，并计算整体结果

PrewriteReview
→ 在 dry-run 基础上整理逐文件预览和快照
```

## 7. dry-run 的边界

它能保证补丁在“当前读取到的文件状态下”可以应用，但不能保证用户确认以后文件仍然没变化。因此写前审查还会额外记录文件摘要，批准时再次检查。

另外，真正提交并不是数据库式原子事务：

```
依次写入 pending_writes
→ 再依次执行 pending_deletes
```

如果正式提交过程中发生磁盘错误，理论上可能只完成部分修改，当前没有自动回滚机制。

可以这样总结：

> `apply_patch` 的 dry-run 通过“先规划、后提交”实现。它先解析补丁，在内存中验证 hunk、计算修改后内容、收集待写入和待删除路径并生成 diff；只有 `dry_run=False` 才会执行最后的磁盘写入和删除，因此 dry-run 不需要复制项目，也不会产生文件副作用。

# 写前预览是怎么实现的？
写前预览的实现思路是：**不直接调用真正的文件工具，而是先用一套可信的本地预览服务，根据工具参数计算修改后的内容，生成 diff 和文件快照；用户批准后，再验证快照没有变化，最后才执行原工具。**

## 一、写前预览在哪里触发

模型生成文件修改调用后，工具执行服务先做权限预检。当前只有四个工具支持写前预览：

```
{"write", "edit", "apply_patch", "delete"}
```

如果本次调用需要权限确认，或者权限已经允许但 Session 要求审查具体修改，系统就会调用写前预览服务：

```
ToolCall
→ 权限预检
→ 判断工具是否支持预览
→ 根据工具参数生成 PrewriteReview
→ 成功后展示 diff
→ 失败则直接阻止操作
```

实现入口在 [service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\tools\\infrastructure\\filesystem\\review\\service.py)。

## 二、四种工具怎样模拟

### `write`

例如：

```
write(
    path="README.md",
    content="新的内容"
)
```

预览服务会：

```
解析并校验目标路径
→ 读取文件当前内容
→ 将模型传入的 content 作为修改后内容
→ 判断是 create、modify 还是 unchanged
→ 比较 before 和 after
→ 生成 unified diff
```

这个过程不会调用真正的 `write` 执行器，也不会写入磁盘。

### `edit`

例如：

```
edit(
    path="app.py",
    old="debug = True",
    new="debug = False"
)
```

预览服务会：

```
读取 app.py
→ 查找 old 出现次数
→ 没找到则预览失败
→ 出现多次但没有 replace_all，则预览失败
→ 在内存中执行字符串替换
→ 根据替换前后内容生成 diff
```

因此预览阶段同时完成了一部分参数和前置条件校验。

### `apply_patch`

`apply_patch` 的预览过程最复杂：

```
解析 Patch 文本
→ 转换成 PatchPlan
→ 得到新增、修改、删除和移动操作
→ 检查同一路径没有被重复修改
→ 读取涉及文件的当前状态
→ 使用 dry_run 验证补丁是否可以应用
→ 在内存中计算应用补丁后的项目状态
→ 为每个文件分别生成 diff
```

`dry_run` 只验证和计算，不把补丁真正写入项目。

### `delete`

对于单个文件，系统会读取删除前的内容，并将修改后内容看作不存在：

```
before = 原文件内容
after = None
operation = delete
```

然后生成删除 diff。

如果删除的是目录，系统会递归遍历目录中的文件和符号链接，为目录和文件分别建立预览记录。二进制文件无法生成文本 diff 时，会标记为：

```
Binary file will be deleted
```

## 三、预览结果长什么样

每个文件都会产生一个 `ReviewFile`：

```
path             文件路径
operation        create / modify / delete / move / unchanged
before_digest    修改前内容摘要
after_digest     预计修改后内容摘要
diff             unified diff
added_lines      新增行数
removed_lines    删除行数
source_path      移动操作的原路径
binary           是否为二进制文件
snapshot         用于过期检测的内部快照
```

多个文件还会汇总为 `ReviewSummary`：

```
创建了多少文件
修改了多少文件
删除了多少文件
移动了多少文件
删除了多少目录
新增了多少行
删除了多少行
```

最终组成：

```
PrewriteReview
├── tool_name
├── files: tuple[ReviewFile, ...]
├── summary: ReviewSummary
└── error
```

传给界面时，内部的 `snapshot` 不会展示，只展示路径、操作类型、diff、行数统计和摘要。

## 四、diff 是怎样生成的

文本文件使用 Python 的 `difflib.unified_diff`，产生类似 Git diff 的结果：

```
--- a/app.py
+++ b/app.py
@@
-debug = True
+debug = False
```

同时统计：

```
以 + 开头但不是 +++ 的行 → added_lines
以 - 开头但不是 --- 的行 → removed_lines
```

## 五、文件快照是怎样生成的

为了保证用户确认时文件没有被别人修改，系统会计算 SHA-256 摘要。

普通文件：

```
SHA-256(文件完整字节)
```

符号链接：

```
SHA-256("symlink:" + 链接目标)
```

目录：

```
递归遍历所有内容
→ 文件相对路径
→ 每个文件的 SHA-256
→ 汇总计算目录摘要
```

不存在的文件使用：

```
None
```

这也可以识别“预览时文件不存在，但确认前被别人创建”的情况。

## 六、用户批准后怎样执行

系统不会根据前端返回的内容重新构造工具调用，而是保存原始 `ToolCall` 的深拷贝，形成待执行事务：

```
PendingToolExecution
├── request_id
├── 原始 tool_call
├── permission_request
├── prewrite_review
├── review_only
└── 后续被跳过的工具调用
```

用户选择允许后，系统先检查：

```
prewrite_review_port.is_current(review)
```

它会重新读取所有快照目标并计算摘要：

```
当前摘要 == 预览时摘要
→ 预览仍然有效
→ 执行保存的原始 ToolCall

当前摘要 != 预览时摘要
→ 预览已经过期
→ 不执行工具
→ 返回 prewrite_review_stale
```

因此：

```
预览 app.py
→ 用户等待确认
→ 期间 app.py 被其他人修改
→ 用户点击允许
→ 摘要不一致
→ 系统拒绝执行
→ 要求重新读取并生成 diff
```

## 七、如果预览生成失败

以下情况可能导致预览失败：

- 路径或参数格式错误。
- `edit` 找不到需要替换的内容。
- 匹配出现多次但没有开启 `replace_all`。
- Patch 语法错误。
- Patch 无法应用到当前文件。
- 文件不是预期的文本格式。
- 目录删除参数不符合要求。
- 路径越过沙箱范围。

系统会生成：

```
request_type = prewrite_review_failed
ok = false
```

工具不会执行，也不会让用户批准一份无法验证的修改。

## 八、预览怎样恢复

完整的写前预览主要保存在当前运行时的待执行事务中。Session JSONL 中已经保存了模型原始的工具调用，并记录这次暂停是否属于 `prewrite_review_only`。

如果进程重启并恢复 Session，系统可以从没有对应结果的工具调用中恢复待执行事务，然后基于当前文件状态**重新生成预览**，而不是盲目复用旧 diff。

这样可以避免恢复以后展示已经过期的修改内容。

## 九、它能否完全解决并发修改

快照校验可以显著降低“预览和执行不一致”的风险，但当前实现不是严格的文件事务：

```
检查摘要
→ 存在一个很小的时间窗口
→ 真正执行写入
```

如果另一个进程恰好在摘要检查之后、正式写入之前修改文件，理论上仍可能发生竞态。`edit` 和 `apply_patch` 在真正执行时还会重新验证部分内容，可以进一步降低风险，但 `write` 没有跨进程文件锁。

因此准确说法是：

> 当前实现提供了基于 SHA-256 快照的乐观并发检查，可以发现大多数确认期间的文件变化，但没有通过文件锁或原子 compare-and-swap 完全消除检查与写入之间的竞态窗口。

完整链路可以记成：

```
模型生成 ToolCall
→ 权限预检
→ 预览服务在内存中模拟修改
→ 生成 diff、统计和 SHA-256 快照
→ 保存待执行事务
→ 用户查看并确认
→ 重新计算当前文件摘要
→ 摘要一致：执行原始 ToolCall
→ 摘要不一致：拒绝并要求重新预览
```



# 用户反馈最终以什么形式返回模型？

用户反馈最终以**原工具调用对应的失败 `ToolResult`** 返回给模型，不是作为一条新的普通用户消息。

例如用户输入：

```
reject: 请保留原标题，只修改第二段
```

权限管理器会生成一个拒绝决定：

```
kind = DENY
feedback = 请保留原标题，只修改第二段
reason = 用户拒绝了权限请求：请保留原标题，只修改第二段
```

随后系统把它转换成类似这样的工具结果：

```
{
  "name": "write",
  "ok": false,
  "content": "用户拒绝了权限请求：请保留原标题，只修改第二段",
  "error": "用户拒绝了权限请求：请保留原标题，只修改第二段",
  "data": {
    "request_type": "permission_denied",
    "permission_request_id": "perm_write_xxx",
    "permission_decision": "deny",
    "permission_feedback": "请保留原标题，只修改第二段"
  }
}
```

写入 Session JSONL 时，它会成为一个 `tool_result` 消息部分，并保留：

```
tool_call_id
tool_name
ok = false
content
error
data.permission_feedback
```

这样它能够与模型之前生成的原始工具调用配对：

```
assistant:
  tool_call id = call_write_1

tool:
  tool_call_id = call_write_1
  ok = false
  permission_feedback = 请保留原标题，只修改第二段
```

下一次构造模型请求时，Provider 适配器会把这个结果转换为模型协议中的工具结果消息。模型看到的逻辑上下文是：

```
我刚才调用了 write
→ 工具没有执行成功
→ 原因是用户拒绝
→ 用户要求保留原标题，只修改第二段
```

然后模型可以重新读取文件、调整方案，再生成新的工具调用。

因此完整链路是：

```
用户输入 reject: <反馈>
→ 解析成 REJECT_WITH_FEEDBACK
→ 生成 DENY 决定
→ 不执行工具
→ 生成 ok=false 的 ToolResult
→ feedback 写入 ToolResult.content 和 data.permission_feedback
→ ToolResult 写入 Session JSONL
→ 下一次模型请求携带该工具结果
→ 模型根据反馈重新规划
```

一句话总结：

> 用户反馈会被包装成原工具调用的失败结果，通过 `content`、`error` 和 `permission_feedback` 返回模型，从而既保持工具调用与结果的协议配对，又让模型理解用户为什么拒绝以及应该怎样修改。

# Reject with feedback机制是怎么做的？
`Reject with feedback` 的核心作用是：

> 用户拒绝当前工具调用，同时把“为什么拒绝、希望模型怎样修改”的文字作为工具失败结果返回给模型。

它不是重新给模型发送一条普通用户消息，而是通过恢复待处理的权限事务，为原工具调用补上一条带反馈的失败结果。

## 完整执行链路

模型先生成文件修改工具，例如：

```
{
  "id": "call_write_1",
  "name": "write",
  "arguments": {
    "path": "README.md",
    "content": "新的内容"
  }
}
```

权限系统发现需要审批，便保存一份待执行事务，主要包括：

```
request_id
原始 ToolCall
PermissionRequest
写前预览和 diff
同一批中尚未执行的后续工具调用
```

注意，此时 `write` 的执行器还没有运行，文件也没有被修改。

随后 TUI 展示写前预览，并提示：

```
Or reply: reject: <feedback>
```

用户可以输入：

```
reject: 请保留原来的标题，只修改第二段
```

## 第一步：解析用户输入

界面输入解析器识别 `reject:` 或 `reject_with_feedback:` 前缀，将其转换成统一格式：

```
reject_with_feedback: 请保留原来的标题，只修改第二段
```

其中：

```
choice   = REJECT_WITH_FEEDBACK
feedback = 请保留原来的标题，只修改第二段
```

如果用户只输入 `reject`，却没有提供具体反馈，就退化成普通的 `Deny`。

## 第二步：恢复待执行权限事务

AgentLoop 使用原来的 `request_id` 恢复暂停中的权限事务：

```
根据 request_id 加载 PendingToolExecution
→ 确认恢复的是当前等待审批的工具
→ 将用户输入交给 PermissionManager
```

使用 `request_id` 的目的是保证用户审批或拒绝的，确实是之前展示的那次工具调用，而不是另一条工具调用。

## 第三步：生成带反馈的拒绝决定

权限管理器不会执行工具，而是生成：

```
PermissionDecision
├── kind = DENY
├── reason = 用户拒绝了权限请求：请保留原来的标题，只修改第二段
└── feedback = 请保留原来的标题，只修改第二段
```

这次拒绝只针对当前工具调用：

- 不会生成 `allow grant`。
- 不会生成长期 `deny grant`。
- 不会修改当前权限模式。
- 不会执行工具。

## 第四步：生成失败的 ToolResult

系统将拒绝决定包装成原工具调用对应的失败结果：

```
{
  "ok": false,
  "error": "用户拒绝了权限请求：请保留原来的标题，只修改第二段",
  "data": {
    "request_type": "permission_denied",
    "permission_request_id": "perm_write_xxx",
    "permission_decision": "deny",
    "permission_feedback": "请保留原来的标题，只修改第二段"
  }
}
```

这条结果会作为 `call_write_1` 唯一对应的 `tool_result` 写入 Session JSONL，从而保持模型要求的工具调用与工具结果配对关系：

```
assistant tool_call：call_write_1
        ↓
tool_result：ok=false + permission_feedback
```

## 第五步：再次调用模型

待执行权限事务被清除以后，AgentLoop 会继续运行，并再次构造模型请求。模型能够看到：

```
原来的 write 工具调用
+
这次调用被用户拒绝
+
用户给出的具体修改意见
```

模型可以根据反馈重新生成方案，例如：

```
重新读取 README.md
→ 保留原标题
→ 只修改第二段
→ 生成新的 write/edit 工具调用
→ 再次进入权限检查
```

系统不会自动修改原工具参数，也不会自动执行新的方案，修改方案仍然由模型重新生成。

## 同一批其他工具怎么处理

如果模型一次生成了多个工具调用：

```
tool A
tool B：等待用户审批
tool C
tool D
```

当用户对 B 使用 `Reject with feedback` 时：

- B 生成带反馈的失败结果。
- B 后面的 C、D 会被标记为跳过。
- B 之前已经执行成功的 A 不会回滚。
- 模型看到这些结果后重新决定下一步。

最终可以这样记：

> `Reject with feedback` 是一种带自然语言反馈的单次拒绝机制。它通过 `request_id` 恢复原待执行事务，不调用工具执行器，而是为原工具调用生成一条包含 `permission_feedback` 的失败结果并写入 Session，然后再次调用模型，让模型根据用户反馈重新规划和生成工具调用。

# 为什么 `python_exec` 和 `apply_patch` 不允许 `Allow always`？

FirstCoder 明确为 `python_exec` 和 `apply_patch` 设置了：

```
allow_always=False
allow_auto=False
```

这意味着两件事：

```
allow_auto=False
→ Standard 和 Aggressive 都不能自动放行

allow_always=False
→ 用户不能保存长期授权，只能逐次批准
```

原因可以从两个工具的权限建模看出来。

## `python_exec` 为什么不能长期授权

`python_exec` 可以执行任意 Python 代码：

```
python_exec(code="...")
```

不同代码的行为差异非常大，例如：

```
print("hello")              # 普通计算
Path("a.txt").write_text()  # 修改文件
os.remove("a.txt")          # 删除文件
requests.get(...)           # 网络访问
subprocess.run(...)         # 启动其他进程
```

权限系统为了向用户展示，只会截取最多前 200 个字符，构造一个目标描述：

```
python -c <前200字符的代码>
```

如果允许为它生成长期的 `COMMAND_PREFIX` 授权，就可能出现两个问题：

- Python 代码的能力无法通过一个命令前缀准确描述。
- 不同程序的前 200 个字符可能相同，但后面的危险操作不同。

例如：

```
# 前200字符相同
...普通初始化代码...
print("hello")
```

和：

```
# 前200字符相同
...普通初始化代码...
os.remove("important.db")
```

展示目标可能相同，但实际行为完全不同。因此每段 Python 代码都必须单独审批。

## `apply_patch` 为什么不能长期授权

`apply_patch` 一次调用可以：

- 新增文件。
- 修改文件。
- 删除文件。
- 移动文件。
- 同时操作多个文件。

它生成权限申请时，只把涉及的文件路径整理成目标描述，例如：

```
src/a.py, src/b.py, tests/test_a.py
```

但是相同的文件列表不代表相同的修改内容：

```
第一次：修复一个判断条件
第二次：删除整个函数
第三次：写入敏感逻辑
```

如果只根据文件路径保存 `Allow always`，以后对这些文件的任何补丁都有可能被直接放行；如果根据完整 Patch 内容授权，这条授权又几乎没有复用价值，而且 Scope 机制也无法准确表达多文件 Patch 的具体语义。

所以 `apply_patch` 必须逐次生成 diff，由用户针对本次实际修改进行确认。

## 它们进入 ASK 后会怎样

这两个工具都不提供 `Allow always`：

```
python_exec
→ Deny
→ Allow once

apply_patch
→ Deny
→ Allow once
→ 同时展示写前 diff
→ 可以 Reject with feedback
```

即使处于 Aggressive 模式，它们也不会自动执行，因为两者还设置了：

```
allow_auto=False
```

所以可以这样总结：

> `python_exec` 的行为无法通过代码前缀可靠限制，`apply_patch` 的影响无法通过一条路径 Scope 准确描述。为了防止长期授权被后续完全不同的代码或补丁复用，FirstCoder 同时关闭了自动放行和 `Allow always`，要求用户逐次审批。这里“为什么这样设计”是从当前权限模型和实现推导出的安全意图，源码本身没有单独写一段设计说明。





# 哪些工具没有配置 `ToolPermissionSpec`
当前 FirstCoder 中，没有配置 `ToolPermissionSpec` 的主要是内部控制类、计划类、会话类和部分进程管理工具。

## 没有 `ToolPermissionSpec` 的工具

|类别|工具|
|---|---|
|模型内部控制|`think`|
|用户交互|`ask_user`|
|任务计划|`task_create`、`task_update`、`task_revise`、`task_list`|
|任务边界|`task_boundary`|
|Skill|`load_skill`|
|上下文归档|`retrieve_archive`|
|多 Agent|`delegate`|
|后台任务控制|`background_status`、`background_cancel`|
|进程查看和控制|`process_status`、`process_logs`、`process_stop`|

这些工具进入权限感知注册表时，因为：

```
tool.permission is None
```

权限预检会直接返回 `None`：

```
没有 ToolPermissionSpec
→ 不构造 PermissionRequest
→ 不进入 grant 和权限模式判断
→ 不出现权限审批界面
→ 进入工具自身的执行逻辑
```

不过，没有 `ToolPermissionSpec` 不代表它们完全不受任何限制。它们仍然要经过：

- 工具名称和参数校验。
- Agent 角色的工具白名单。
- 工具自身的业务校验。
- AgentLoop 的状态和调用次数限制。
- 工具内部可能存在的安全检查。

例如 `task_update` 没有权限声明，但它需要校验 `expected_revision`；`delegate` 没有权限声明，但子 Agent只能使用角色允许的工具；`process_stop` 没有权限声明，但只能停止 FirstCoder 自己管理的进程。

## 配置了 `ToolPermissionSpec` 的工具

为了方便对照，下面这些工具配置了权限声明：

```
ls
view
grep
glob
tree
read_multi

write
edit
delete
apply_patch

shell
python_exec
diagnostics

git_status
git_diff
git_log

process_start

fetch
web_search

所有动态 MCP 工具
```

它们在调用时会：

```
ToolPermissionSpec + 模型参数
→ PermissionRequest
→ grant 匹配
→ standard/aggressive/bypass 默认策略
→ ALLOW / ASK / DENY
```

其中：

```
python_exec、apply_patch
→ allow_always=False

其他已配置权限声明的工具→ 默认 allow_always=True
```

但是否真的出现 `ASK`，仍然取决于具体参数、现有授权和当前权限模式。例如 `git_status` 配置了权限声明，但在项目内属于只读 Git 操作，通常会直接 `ALLOW`，所以用户通常看不到审批界面。

还要注意，`ask_user` 虽然会暂停并等待用户输入，但它不是权限审批：

```
ask_user
→ Agent主动向用户询问信息

权限 ASK
→ 权限系统询问用户是否允许执行敏感操作
```

一句话总结：

> FirstCoder 只有配置了 `ToolPermissionSpec` 的工具才会进入统一权限系统；没有配置的工具不会产生 `PermissionRequest`，但仍然受到参数校验、角色白名单和工具自身业务规则的限制。

# 使用工具时，最先进入的是是否匹配到授权规则，这个是进行的遍历吗？
是的，当前实现中，已有授权规则的匹配采用的是**内存列表遍历**，没有使用哈希索引、数据库索引或者路径树。

不过它不是工具调用后的第一个动作，完整顺序是：

```
模型生成工具调用
→ 校验工具名称和参数
→ 读取工具的 ToolPermissionSpec
→ 构造并规范化 PermissionRequest
→ 遍历已有 PermissionGrant
→ 没有匹配才进入 standard/aggressive/bypass 默认策略
```

FirstCoder 启动时会从 `permissions.json` 读取所有长期授权，转换为内存中的：

```
list[PermissionGrant]
```

每次权限预检时，大致执行：

```
matches = [
    grant
    for grant in grants
    if grant_matches(grant, request)
]
```

也就是逐条检查：

```
grant.action 是否等于 request.action？
        ↓
scope_type 对应的匹配规则是否成立？
```

例如请求是：

```
action = write_path
target = E:\project\src\config.py
```

系统会依次遍历：

```
规则1：read_path + exact_path
→ action 不同，不匹配

规则2：write_path + exact_path + config.py
→ action 相同、路径相同，匹配

规则3：write_path + path_tree + E:\project
→ action 相同、目标在目录树内，匹配
```

如果同时匹配多条规则，处理顺序是：

```
先从匹配结果中寻找 deny
→ 找到 deny，直接 DENY

没有 deny，再寻找 allow
→ 找到 allow，返回 ALLOW

allow 和 deny 都没有
→ 进入默认权限策略
```

因此，`deny grant` 的优先级高于 `allow grant`，与它们在文件中的先后位置无关。

Scope 的匹配方式根据类型不同：

```
EXACT_PATH
→ 比较规范化后的绝对路径

PATH_TREE
→ 判断目标是否等于目录，或者位于目录下面

COMMAND_PREFIX
→ 判断命令是否相同，或者以“前缀＋空格”开头

HOST
→ 比较规范化后的主机名

ENV_KEY
→ 忽略大小写比较变量名

MCP_TOOL
→ 比较具体 MCP 工具标识
```

所以当前授权匹配的时间复杂度是 `O(n)`，`n` 是授权规则数量。由于普通用户的 `permissions.json` 通常只有少量规则，这种实现简单且足够使用；如果以后积累成千上万条规则，可以按 `action` 和 `scope_type` 建索引，路径范围规则还可以使用前缀树来优化。

一句话总结：

> FirstCoder 会先把 `permissions.json` 加载成内存授权列表；每次权限请求都遍历这份列表，依次进行 action 和 Scope 匹配，deny 优先于 allow，没有匹配才进入当前权限模式的默认策略。




# 工具审查流程

```
模型生成工具调用
        ↓
检查工具名称和参数是否合法
        ↓
工具有没有 ToolPermissionSpec？
   ├─ 没有：不进入权限系统，直接进入工具执行
   └─ 有：根据声明生成 PermissionRequest
                ↓
        检查已有的长期授权/拒绝规则
          ├─ 命中 allow grant → ALLOW
          ├─ 命中 deny grant  → DENY
          └─ 没命中 → 进入默认权限策略
                         ↓
                根据权限模式和操作内容判断
                  ├─ ALLOW → 执行工具
                  ├─ ASK   → 暂停并询问用户
                  └─ DENY  → 不执行，返回失败结果
```

完整链路
```
模型生成工具调用
        ↓
校验工具名称和参数
        ↓
读取工具创建时定义的 ToolPermissionSpec
        ↓
根据审查规则提取 action、target 和 cwd
        ↓
构造 PermissionRequest
        ↓
检查已有的 allow/deny grant
        ↓
根据当前权限模式执行默认策略
        ↓
        ┌───────────────┬──────────────┐
      ALLOW            ASK            DENY
        ↓               ↓              ↓
检查写前审查      保存待执行事务      不执行工具
        ↓          暂停 AgentLoop       ↓
执行工具           用户作出选择      返回失败结果
                        ↓
                 允许或拒绝
```


FirstCoder 在创建工具时，会为需要权限控制的工具定义 `ToolPermissionSpec`，也就是权限审查规则，说明该工具属于什么操作、应该从哪个参数提取审查目标以及能否自动授权。模型调用工具时只负责生成工具名和参数，本地代码根据工具的审查规则构造 `PermissionRequest`。权限管理器先检查已有授权，再结合具体参数和当前权限模式，动态返回 `ALLOW`、`ASK` 或 `DENY`。Standard 默认比较谨慎；Aggressive 额外自动放行项目内普通写入和白名单验证命令；Bypass 默认跳过交互式权限审批，但仍受显式拒绝、写前审查、参数校验和工具内部安全规则约束。
