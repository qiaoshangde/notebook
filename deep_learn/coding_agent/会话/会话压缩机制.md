# 上下文压缩机制

本篇集中讲压缩策略与执行流程；字段含义见[会话运行状态](/E:/notebook/deep_learn/coding_agent/会话/会话运行状态.md)，消息投影规则见[会话视图](/E:/notebook/deep_learn/coding_agent/会话/会话视图.md)，日志恢复链路见[会话重建](/E:/notebook/deep_learn/coding_agent/会话/会话重建.md)。

阅读顺序：预算与任务边界 → 触发与流水线 → L1～L4 → 失败处理 → 一个完整示例。

## 一、上下文与持久化边界

每次主模型请求需要考虑固定输入、动态历史和输出预留三个部分；输出预留是预算，不是另外发送的一段消息。

### 1. 固定上下文

包括：

- 系统提示词；
- Agent行为规则；
- 项目规则；
- 工具名称、描述和参数Schema；
- 临时运行指令。

这部分通常不能通过L1～L4随意压缩。

### 2. 动态会话历史

包括：

- 用户消息；
- 助手回复；
- 助手发出的工具调用；
- 工具执行结果；
- 最近一次Checkpoint；
- Checkpoint之后的原始消息尾部。

这部分会随着任务运行不断增长，是上下文压缩的主要处理对象。

### 3. 输出预留

系统还需要为模型即将生成的回答预留Token，不能把整个上下文窗口都拿来放输入。

持久化边界：JSONL保留原始事件，SessionView按事件应用压缩替换，模型请求使用Checkpoint摘要与有效尾部。它们是同一份会话数据的不同表示，不是额外建立的三套独立记忆。


## 二、Token预算

项目目前没有使用模型对应的真实Tokenizer，而是采用Provider无关的近似估算。

### 文本Token估算

```
Token ≈ 字符数 ÷ 4，向上取整
```

### 图片Token估算

每张图片固定估算为：

```
1024 Token
```

### 默认窗口配置

如果模型没有明确配置上下文窗口，当前代码默认：

```
context_window = 200,000
output_reserve = 4,096
```

首先只使用上下文窗口的95%：

```
usable_window = context_window × 95%
```

再扣除输出预留：

```
input_capacity = usable_window - output_reserve
```

然后计算两个水位：

```
高水位 = input_capacity × 90%
低水位 = input_capacity × 72%
```

因此，低水位和高水位不是整个模型窗口的72%和90%，而是扣除了5%安全余量和输出预留后的输入容量比例。

### 固定开销与历史开销

预算会进一步拆成：

```
fixed_tokens =
    系统提示词
  + 工具定义

history_tokens =
    用户消息
  + 助手消息
  + 工具调用
  + 工具结果
  + Checkpoint等历史内容

input_tokens = fixed_tokens + history_tokens
```

如果固定上下文本身已经达到低水位，即使删除全部历史也无法完成压缩，管理器会直接返回：

```
fixed_context_over_budget
```

因为L1～L4主要处理会话历史，不能随意删除系统提示词和工具定义。

## 三、任务边界：分类、候选确认与任务哈希

上下文压缩中的L1需要区分“当前任务”和“旧任务”，因此系统先维护任务边界。

### 1. 任务分类是一次单独的模型请求

除会话第一条用户消息外，每收到一条新的真实用户消息，系统会先执行一次隐藏分类。

流程是：

```
用户发送消息
→ 隐藏任务边界分类
→ 更新任务状态
→ 必要时触发任务切换压缩
→ 正式请求主模型
```

分类请求和主请求是两次独立的模型调用。

#### 分类请求发送什么

分类请求包含：

```
任务分类专用系统提示词
+
当前有效会话历史
+
最新用户消息
```

当前有效历史可能包括：

- 用户消息；
- 助手回复；
- 工具调用；
- 工具结果；
- Checkpoint摘要。

所以，工具消息不是分类目标，但会作为判断依据提供给分类模型。

#### 分类请求不包含什么

它不提供工具：

```
tools = []
tool_choice = "none"
```

最大输出为：

```
512 Token
```

模型只能返回严格JSON：

```
{
  "decision": "same|new|uncertain",
  "basis_message_id": "当前用户消息ID"
}
```

无效时最多尝试3次；最终仍然失败，则按 `uncertain` 处理。

### 2. 分类和主请求使用什么模型

当前代码复用主Agent的同一个Provider和模型，但属于两次独立请求。

所以准确说法是：

- 独立请求：是；
- 独立模型：当前不是；
- 对用户可见：不是；
- 每次主模型调用前都分类：不是；
- 每条新用户消息通常分类一次：是；
- 工具循环中的后续模型请求再次分类：不会。

一个用户需求可能产生：

```
一次边界分类请求
+
多次主模型工具循环请求
```

### 3. 为什么不能简单并行

当前流程依赖分类结果完成：

- `active_task_hash`更新；
- 用户消息任务标记；
- 任务切换压缩；
- 主请求上下文构造。

如果分类请求和主请求同时发送，主请求发出时还不知道是否应该清理旧任务，因此分类结果无法影响当前主请求。

并行可能降低部分延迟，但不会减少Token，因为两个请求仍然都要发送。

后续更合理的优化是：

- 给分类器单独使用轻量模型，降低费用；
- 只提供当前任务摘要和最近几轮，减少分类输入Token；
- 规则优先，语义模糊时才调用模型。

### 4. same、new、uncertain的处理

#### 1. same

没有候选任务时：

```
decision = same
→ active_task_hash保持不变
→ 继续当前任务
```

源码会顺便把候选字段设置成 `None`、稳定计数设置成0。候选本来就是空时，这只是幂等重置，不产生实际变化。

存在候选任务时：

```
decision = same
→ 被程序解释为继续候选任务
→ 候选任务稳定计数增加
→ 达到默认2次观察后切换
```

#### 2. new

程序根据当前用户消息ID生成候选任务哈希：

```
candidate_hash =
    stable_hash(
        session_id
      + basis_message_id
      + 策略版本
    )
```

如果还没有活动任务，例如会话第一条消息，则直接把它初始化成活动任务。

如果已经存在活动任务，则默认先保存为候选，不立即切换：

```
active = task_A
candidate = task_B
stable_count = 1
```

#### 3. uncertain

```
active_task_hash保持不变
candidate_task_hash清空
stable_count归零
不触发任务切换
```

它采用的是保守策略。

### 5. task_hash的生成与消息标记

`task_hash`不是用户消息正文的语义哈希，也不是通过比较两条消息内容计算出来的。

它只是任务身份ID。

计算输入是：

```
session_id
+ 任务起点消息ID
+ 策略版本
```

因此：

```
两个哈希相等
```

只表示程序认为它们属于同一个任务身份，不表示两条消息语义相似。

真正判断任务是否相同的是：

```
模型输出same/new/uncertain
+
程序状态机
```

随后程序把判断结果转换成任务哈希，并写入消息元数据。

L1最终只是机械比较：

```
消息task_hash == active_task_hash
→ 当前任务

消息task_hash != active_task_hash
→ 旧任务候选
```

所以正确因果关系是：

```
模型做语义判断
→ 状态机维护任务身份
→ 程序生成/切换task_hash
→ task_hash用于后续确定性压缩
```

不是：

```
程序比较消息内容哈希
→ 自动判断是否为同一任务
```

### 6. 候选确认机制的现有问题

当前源码采用：

```
第一次new
→ 建立候选任务B

下一次same
→ 确认候选任务B
```

例如：

```
活动任务A：修改登录模块

用户：现在分析订单模块
分类：new
结果：建立候选任务B，但active仍然是A

用户：先看看订单创建流程
分类：same
结果：程序认为用户继续候选B
     将active切换为B
```

#### 为什么不是连续两次new

因为候选哈希包含当前用户消息ID。

连续两条消息都返回 `new` 时：

```
第一条消息ID不同 → candidate_B
第二条消息ID不同 → candidate_C
```

第二个候选与第一个候选不同，稳定计数会重新开始，不能确认B。

#### 这里存在语义问题

分类提示词要求模型判断最新消息是否延续“活动任务”，但程序在存在候选任务时，把 `same` 解释成延续“候选任务”。

模型并没有被显式告诉：

```
已确认活动任务是A
待确认候选任务是B
请判断最新消息延续A还是B
```

它只能通过最近对话自行推断。

因此，`same`在程序中有两种隐含含义：

```
没有候选时：
same = 继续active任务

存在候选时：
same = 继续candidate任务
```

这是当前设计中比较脆弱的地方。

#### 旧任务历史会不会影响分类

会有这种风险。

候选任务尚未确认时，任务切换压缩还没有执行，因此分类请求里可能同时存在：

- 大量旧任务历史；
- 候选新任务第一条消息；
- 新任务第一轮产生的助手和工具消息；
- 最新用户消息。

最近消息通常会让模型倾向于判断用户正在继续候选任务，但代码没有显式保证模型一定以候选任务作为比较对象。

#### 更合理的改进方式

可以把分类输出改成：

```
same_active
same_candidate
new
uncertain
```

或者显式提供：

```
当前活动任务：
修改登录模块

待确认候选任务：
分析订单模块

最新用户消息：
先看看订单创建流程
```

还可以直接在第一次高置信度 `new` 时切换任务，但必须同时提高L1的可恢复性，避免误判造成信息丢失。

#### 另一个潜在问题

第一次 `new` 尚未确认时，Agent仍然使用旧的 `active_task_hash` 运行这一轮。

因此，这一轮新任务产生的部分助手消息和工具过程可能暂时带着旧任务哈希。下一轮确认后，源码会重新标记候选起点用户消息和当前用户消息，但不一定完整重标中间产生的所有助手与工具内容。

这可能导致新任务第一轮的部分内容后续仍被当作旧任务内容，是任务边界实现中需要进一步完善的地方。

## 四、四种触发方式与压缩目标

当前源码有四种触发方式：

```
AUTO
TASK_HASH_CHANGED
MANUAL
PROMPT_TOO_LONG
```

必须区分：

- 管理器级触发：决定是否启动一次压缩；
- 层级内部条件：决定启动后哪些层需要继续处理。

### 1. AUTO

每次准备主模型请求前，系统计算Token。

只有：

```
input_tokens >= high_watermark
```

才自动启动压缩。

目标是：

```
low_watermark
```

如果低于高水位，普通AUTO直接跳过。达到阈值后还会检查自动熔断和无效果指纹，匹配时也可能跳过；这些状态字段及严格条件见[会话运行状态](/E:/notebook/deep_learn/coding_agent/会话/会话运行状态.md)。

### 2. TASK_HASH_CHANGED

任务切换经过稳定确认后启动。

目标是：

```
low_watermark × 2/3
```

特殊参数是：

```
force_old_task_compaction = true
required_levels = ("l2", "l3")
```

因此它会：

```
强制执行L1旧任务裁剪
→ 必须进入L2检查
→ 必须进入L3检查
→ 仍然超过目标才执行L4
```

“必须进入”不等于一定发生内容变化。没有合格候选时，对应层的变更数量可以是0。

### 3. MANUAL

用户输入：

```
/compact
```

触发MANUAL。

#### 1. 输入不超过2000 Token

不设置更激进的自定义目标，通常因为已经满足默认预算而不产生变化。

#### 2. 输入超过2000 Token

先计算：

```
proposed =
    min(
        低水位 - 1,
        当前输入 × 60%
    )
```

再保护固定上下文：

```
target =
    max(
        proposed,
        fixed_tokens + 1
    )
```

只有：

```
target < 当前输入
```

才采用这个自定义目标。

所以手动压缩通常比AUTO更激进，但不允许目标低于无法压缩的固定上下文。

#### 3. 什么都没输入时

假设只有系统提示词和工具定义：

```
input_tokens = fixed_tokens
```

如果不超过2000，直接不设置自定义目标。

如果超过2000：

```
target至少为fixed_tokens + 1
```

这个目标反而不小于当前输入，因此也不会设置自定义目标。

最终通常返回：

```
Manual compact skipped
```

不会因为目标不可能达到而无限压缩。

#### 4. 高于高水位还能不能手动

程序允许。

正常Agent流程中，AUTO会在下一次主请求前自动处理，因此高水位以上通常不需要用户手动。

但以下情况仍可能手动：

- 恢复一个很大的旧会话，还没发起主请求；
- AUTO熔断；
- 用户希望压得比AUTO更低；
- 用户在主请求前先执行 `/compact`。

手动调用不受AUTO高水位限制，也不因自动熔断而直接跳过。固定输入达到低水位时，仍会被管理器的固定开销检查拒绝。目标通常低于低水位，但 fixed_tokens + 1 托底可能使它等于低水位。

### 4. PROMPT_TOO_LONG

主模型请求已经发送给Provider，但Provider认为输入超过真实上下文窗口，直接拒绝请求。

Provider错误信息可能包含：

```
context length
prompt too long
maximum context
```

本地统一归类为：

```
ProviderErrorKind.PROMPT_TOO_LONG
```

它表示输入过长，不是模型输出过长，也不是模型生成一句“我觉得输入太长”。

目标是：

```
low_watermark
```

它与AUTO的目标相同；但这条恢复路径会强制继续尝试L4，因此整体恢复行为仍比普通AUTO更激进。

### 两种激进策略的设计解释

以下是根据行为作出的推断，不是代码直接声明的设计理由：任务切换降低目标并强制检查旧内容，主要是为新任务腾空间、减少旧任务干扰；主请求超长说明本地估算与Provider限制存在偏差，因此当前实现额外尝试L4，但代价是增加摘要调用。两者激进的位置不同，不能把它们的目标或流程混为一谈。

## 五、程序化流水线：何时继续、何时停止

普通AUTO触发只看：

```
整体input_tokens是否达到高水位
```

不会因为：

- 单条工具结果过长；
- 消息数量过多；
- 某轮工具结果总量过大；

自动绕过高水位启动管理器。

当前配置中：

```
l2_result_target_tokens = 800
large_tool_result_tokens = 1200
```

800是当前正常传入的单结果目标；1200主要是缺少有效单结果目标时的回退配置。

单结果压力的真正作用是：

```
压缩管理器已经因为某个原因启动
        ↓
程序化流水线发现某条derived结果仍超过800 Token
        ↓
即使整体已经达到目标，也允许继续检查L2/L3
```

它是流水线内部的继续条件，不是独立启动条件。

---

### 提前停止的条件

不会。

普通顺序是：

```
L1
→ 重新估算
→ 达到目标则停止

L2
→ 重新估算
→ 达到目标则停止

L3
→ 重新估算
→ 达到目标则停止

L4
```

但如果还存在必须处理的后续候选，即使达到目标，也可能继续检查下一层。

例如：

- 任务切换要求L2、L3必须检查；
- L3存在明确失效、重复候选；
- 某个派生工具结果仍超过单结果目标。

所以不是简单地：

```
达到目标后永远停止
```

而是：

```
达到目标
+ 没有required level
+ 没有mandatory candidate
+ 没有单结果压力
→ 停止
```

## 六、L1：旧任务普通对话裁剪

### 1. L1处理什么

L1只处理旧任务中的普通文本消息。

主要条件包括：

```
消息task_hash与active_task_hash不同
+ part.kind == text
+ 尚未被压缩
+ 不是最新用户消息
+ 不破坏工具调用事务
```

正常AUTO压缩下，还要求：

```
current_turn - created_turn >= 8
```

也就是旧任务内容至少冷却8轮。

任务切换触发时：

```
force_old_task_compaction = true
```

会绕过8轮冷却，立即裁剪已确认的旧任务普通文本。

### 2. L1不会处理什么

不会直接处理：

- 当前任务普通对话；
- 最新用户消息；
- 没有task_hash的消息；
- 工具结果；
- 包含工具调用的助手消息；
- 已经被压缩的内容；
- Checkpoint覆盖范围之外不应重复处理的历史。

### 3. L1压缩成什么

L1不是摘要，而是刻意遗忘。

源码直接把文本变成：

```
content = ""
compaction_state = "trimmed"
```

ContextBuilder发现存在裁剪内容后，向模型上下文加入一次：

```
[Earlier dialogue trimmed]
```

无论裁掉多少条普通对话，通常只加入一个统一标记。

它不会生成：

```
登录任务已经完成
任务名称：登录模块
完成内容：……
```

也不会调用LLM总结旧任务。

### 4. 原始内容是否删除

底层JSONL原始事件仍然存在，但模型有效上下文看不到正文。

而且L1没有像L3一样提供 `archive_id` 和恢复工具。

因此：

```
底层审计数据：仍存在
模型有效工作记忆：已遗忘
普通Agent工具：不能直接恢复L1文本
```

### 5. L1是否过于粗糙

这是合理的担心。

风险包括：

- 分类模型可能误判任务切换；
- 任务切换会绕过8轮冷却；
- L1不生成语义摘要；
- L1不提供归档取回接口；
- 错误裁剪可能让模型失去仍然需要的事实。

默认稳定窗口能降低误判风险，但不能彻底解决。

更稳妥的方案包括：

- L1前生成旧任务简短摘要；
- 对L1文本也建立可恢复归档；
- 提取Pinned Facts后再裁剪；
- 显式区分active和candidate任务；
- 只有高置信度任务切换才强制裁剪；
- 任务切换后延迟若干轮再执行L1。

## 七、L2：内容感知的工具结果压缩

### 1. L2不是普通消息截断

L2不会处理所有非系统消息，也不会处理普通用户和助手文本。

它遍历当前有效消息尾部，但只处理符合条件的工具结果：

```
part.kind == tool_result
+ 已经成功发送给模型至少一次
+ 生命周期为derived
+ 尚未被压缩
+ 没有处于归档取回保护期
```

新产生但模型尚未看过的工具结果受保护，不能提前有损压缩。

### 2. 为什么只处理derived

`derived`表示可以重新生成或者属于派生输出，例如：

- 搜索结果；
- 测试日志；
- 编译输出；
- Git Diff；
- Shell输出；
- 部分结构化查询结果。

当前刚读取的源码通常属于 `fresh`，不会因为路由器支持源码类型就自动进入L2。是否进入L2首先由生命周期决定。

### 3. 内容类型如何判断

判断规则写在代码中，主要采用：

- 工具名称提示；
- 正则表达式；
- JSON解析；
- 内容结构特征。

支持的类型包括：

```
SEARCH_RESULTS
GIT_DIFF
BUILD_OUTPUT
JSON_ARRAY
JSON_OBJECT
SOURCE_CODE
HTML
PLAIN_TEXT
```

例子：

```
工具名为rg或grep
→ 搜索结果

包含diff --git、--- a/、+++ b/、@@
→ Git Diff

包含FAILED、ERROR、Traceback、pytest
→ 构建或测试输出

能被json.loads解析
→ JSON

包含def、class、import、function等结构
→ 源码

包含html/body标签
→ HTML

前面都不匹配
→ 普通文本
```

### 4. 不同内容如何压缩

压缩器也是确定性代码，不调用LLM。

例如：

- 搜索结果保留文件路径、行号和代表性命中；
- Git Diff保留文件头、Hunk和统计信息；
- 构建输出保留错误、失败和关键日志；
- JSON保留结构、字段和代表性值；
- HTML保留主要结构；
- 普通文本保留头尾预览。

普通文本Fallback比较接近截断，但整个L2不能简单称为截断。

### 5. L2处理一条还是全部

当L2执行时，它扫描当前有效尾部中的所有合格 `derived tool_result`，不是只处理超过800 Token的那一条。

不过必须满足：

- 原始结果至少约40 Token；
- 路由器能产生压缩版本；
- 压缩版本确实比原文更小。

已经执行过L2的内容会被标记为：

```
l2_route_compacted
```

后续L2不会重复处理。

### 6. L2会不会改变Agent记忆

会改变模型可见的工作记忆。

过程是：

```
保存原始工具结果
→ 将原始结果写入归档
→ 生成内容感知压缩版本
→ 记录压缩替换事件
→ 后续模型看到压缩版本
```

因此：

- 原始JSONL事实仍然存在；
- 原始工具结果归档仍然存在；
- SessionView应用压缩替换；
- 模型看到的是压缩后的内容。

它不是只修改临时请求而完全不改变会话状态；压缩替换会持久化。

## 八、L3：归档替换与按需取回

### 1. L3处理什么

L3比L2更激进，会把完整工具结果或L2压缩结果替换成归档占位符。

主要生命周期包括：

#### stale

旧读取结果已经失效。

例如：

```
读取user.py
→ 后来修改user.py
→ 第一次读取结果变成stale
```

#### superseded

旧读取结果被后来的读取结果替代。

```
第一次读取user.py
→ 第二次重新读取user.py
→ 第一次结果被superseded
```

#### duplicate

重复出现的派生工具结果。

#### derived

搜索、日志、Diff等可以重新生成的结果。

### 2. 哪些是必须处理候选

以下生命周期属于L3 mandatory候选：

```
duplicate
superseded
stale
```

它们即使在整体预算已经达到目标时，也可能继续被归档。

单条仍超过目标的 `derived` 结果也可能继续进入L3。

### 3. L3处理顺序

候选优先级大致是：

```
duplicate
→ superseded
→ stale
→ 超过单结果目标的derived
→ 其他derived
```

然后根据体积、轮次和在尾部的位置排序。

### 4. L3占位符

完整结果会变成类似：

```
[Tool result archived]
archive_id=ar_xxx
tool=shell
status=success
lifecycle=superseded
original_tokens=3500
summary=shell result is superseded
Use retrieve_archive(...) to inspect the original.
```

占位符最大约480字符。

### 5. 原始结果如何保存

归档采用内容寻址：

```
archive_id = SHA-256内容摘要的一部分
```

保存：

- 原始文本；
- 内容哈希；
- 字符数；
- Token估算；
- 创建时间；
- Schema版本。

读取时会重新校验SHA-256。如果内容或元数据不一致，则拒绝读取。

归档失败时，L3不会替换原始工具结果。

### 6. 如何渐进式取回

模型可以调用：

```
retrieve_archive
```

支持参数：

- `archive_id`：归档ID；
- `query`：只取关键词附近的行；
- `max_chars`：限制返回字符数；
- `full=true`：请求更完整内容。

默认最大返回：

```
6000字符
```

硬上限：

```
12000字符
```

因此可以渐进披露：

```
先看占位符摘要
→ 按关键词查局部
→ 必要时再取更完整内容
```

取回结果会成为一条新的工具结果，不是永久恢复原历史位置。新取回结果在当前轮受到再次压缩保护。

### 7. L3会不会破坏工具调用序列

不会删除工具消息，只替换工具结果内容。

仍然保留：

```
assistant tool_call
→ tool tool_result
```

因此Provider要求的工具调用配对仍然合法。

## 九、L4：语义摘要与Checkpoint提交

### 1. L4什么时候执行

通常在：

```
L1～L3后仍然没有达到目标
```

才执行。

但 `PROMPT_TOO_LONG` 是特殊情况：即使程序化压缩已经达到目标，管理器仍然会继续尝试L4。

### 2. L4处理什么

L4只总结会话历史，不总结：

- 系统提示词；
- 工具Schema；
- Provider能力；
- 稳定系统前缀。

如果没有旧Checkpoint：

```
L4输入 = 当前有效会话历史
```

如果已经有Checkpoint：

```
L4输入 =
    上一个Checkpoint摘要
  + Checkpoint之后的有效消息尾部
```

不会每次都重新总结最早的全部原始历史。

另外，构造L4摘要Prompt时，每条消息正文最多保留约4000字符，超过部分会先标记为截断。

### 3. L4输出结构

L4固定生成七个部分：

1. 当前目标；
2. 已知事实与硬约束；
3. 已确认的决定及理由；
4. 相关文件与当前实现状态；
5. 已运行命令及有效结果；
6. 当前错误与未解决事项；
7. 下一步（可立即执行）。

输出最大约：

```
1200 Token
```

如果某一项没有历史证据，要求填写“无”，不能编造。

### 4. 模型是否决定Checkpoint边界

当前默认实现中，模型只生成摘要正文，不负责决定Checkpoint边界。

这是之前容易说错的地方。

边界由本地程序选择：

```
covered_until_message_id
tail_start_message_id
```

程序尽量选择一个较靠后的合法尾部起点，同时保证剩余尾部的工具调用序列合法。

模型系统提示词中甚至明确写着：

```
不要选择checkpoint边界
```

随后L4服务再次验证边界：

- 边界必须位于当前有效尾部；
- 被覆盖消息必须位于保留尾部之前；
- 不能切断工具调用和工具结果；
- 不能隐藏尚未成功发送给模型的工具结果；
- 源上下文指纹必须一致。

### 5. L4结果怎么提交

L4先在内存中生成候选Checkpoint，然后用候选重新构建模型上下文并估算Token。

只有：

```
candidate_input_tokens < target_tokens
```

才提交Checkpoint事件。

如果：

```
candidate_input_tokens >= target_tokens
```

结果被标记为：

```
still_over_budget
```

候选作废，不写入会话。

所以：

- 成功提交的L4一定低于目标；
- L4本身不保证一定能够成功；
- 不会提交一个仍然超限的Checkpoint。

### 6. 压缩后模型看到什么

```
新的Checkpoint摘要
+
Checkpoint之后保留的原始消息尾部
```

不是只剩一条摘要，也不是所有原始消息都消失。

### 7. L4是不是无限重试

不是。

失败原因不同，策略不同：

- `prompt_too_long`：允许有限处理；
- `timeout`：允许有限重试；
- `no_summary`：允许有限重试；
- `invalid_tool_sequence`：失败；
- `unconsumed_boundary`：失败；
- `still_over_budget`：当前Fallback直接失败；
- 重复源指纹：跳过；
- 自动压缩熔断打开：跳过。

L4不会把一个失败摘要先提交，再继续总结失败摘要。只有合法且低于目标的候选才会提交。这里的不提交只针对L4候选；L1～L3的替换事件在进入L4前已经记录，L4失败不会整体回滚这些程序化压缩结果。

自动L4连续失败还会记录失败次数，并可能暂时打开熔断器，避免不断消耗模型调用。

## 十、失败兜底：普通摘要、stronger与两种超长错误

第一次L4通常使用：

```
summary_mode = default
```

Prompt表示：

```
常规压缩
```

只有发生特定失败并进入Fallback时，才可能使用：

```
summary_mode = stronger
```

额外提示：

```
更强压缩，优先保留可恢复事实。
```

因此：

```
进入L4
```

不等于：

```
直接使用最激进摘要Prompt
```

而且 `still_over_budget` 当前不会自动改成stronger再试，而是直接失败。

---

### 两种PROMPT_TOO_LONG错误

这是最容易混淆的部分。

#### 场景A：主Agent请求太长

```
Agent向主模型发正常请求
→ Provider发现输入超过真实限制
→ 返回Prompt Too Long
→ Agent启动上下文恢复压缩
```

这是管理器级触发：

```
ContextWindowTrigger.PROMPT_TOO_LONG
```

流程是：

```
目标设为低水位
→ 执行L1～L3程序化压缩
→ 程序化层达到目标可以提前停止
→ 仍然执行一次普通L4
→ 成功后重试主模型请求一次
```

如果重试后仍然超长，错误继续抛出，不会无限循环恢复。

#### 场景B：L4摘要请求本身太长

L4也需要把历史提交给模型生成摘要：

```
L4摘要请求
→ Provider又返回Prompt Too Long
```

这时进入L4内部兜底：

```
尝试更强程序化压缩
→ 如果达到目标，直接成功
→ 如果仍不够，使用stronger模式再尝试一次L4
```

所以：

```
主模型Prompt Too Long
```

和：

```
L4摘要模型Prompt Too Long
```

是两个不同阶段的错误。

## 十一、压缩失败后，前面已经做的修改还在吗？

在。当前整条L1～L4链路不是“全部成功才提交、任意失败就全部回滚”的事务。

### 提交顺序

```text
L1～L3在克隆视图上生成替换结果
→ 写入 compaction_completed（包含替换记录）
→ 如果还需要L4，生成摘要候选
→ 校验边界、工具序列与压缩后预算
→ 合法且严格低于目标，才写入 checkpoint_created
→ 记录L4完成或失败事件
```

所以有三个不同的结果：

| 情况 | 保留的结果 |
|---|---|
| L1～L3已经满足目标 | 保留程序化替换，不创建新Checkpoint |
| L1～L3有修改，L4失败 | 已写入的替换仍然有效；失败的摘要候选不成为新Checkpoint |
| L4候选通过检查并提交 | 保留前面替换，并新增Checkpoint |

例如，L2把一份构建日志缩短了，随后L4生成的摘要仍然超预算。整次压缩可以报告失败，但下一次重建SessionView时，构建日志仍是L2缩短后的版本。“失败”表示最终目标未完成，不代表所有阶段都没有效果。

依据：[压缩编排](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/compaction/service.py)、[事件写入](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/events.py)、[Checkpoint提交](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/checkpoint/service.py)。

### 如果中途进程退出呢？

恢复只能看到已经完整写入、能够解析的事件。如果程序化替换事件已写入，而Checkpoint尚未写入，恢复后保留前者，不会凭空补出后者。归档文件也可能已经写入，但替换事件尚未写入；此时不能仅凭“归档文件存在”就认定视图已经替换。

这不等于系统已经保证断电安全。JSONL追加、归档文件写入和Checkpoint写入不是一个跨文件事务；日志损坏、半行写入等问题需要另外验证，不能从append-only推导出事务原子性。

复习问题：压缩失败是否意味着Token完全没减少？为什么不能把失败候选写成Checkpoint？在哪个写入点退出，恢复后的视图会不同？

## 十二、如何评估压缩质量，而不只是看Token减少？

### 当前项目已经验证了什么？

相关测试覆盖未消费结果保护、L2/L3候选选择、归档原文、工具调用配对、Checkpoint边界、预算检查和有限重试。例如：[程序化压缩测试](/E:/agent/后端agent开发资料/FirstCoder/tests/test_context_compaction_pipeline.py)、[L4测试](/E:/agent/后端agent开发资料/FirstCoder/tests/test_context_llm_compact.py)、[压缩管理器测试](/E:/agent/后端agent开发资料/FirstCoder/tests/test_context_window_manager.py)。

其中L4测试使用FakeSummarizer等可控替身，适合验证“给定这个摘要或异常，程序是否正确处理”。这不是让真实模型反复总结，再测量关键事实保留率。

`/context`可以查看预算、未消费结果数量、归档数量、边界状态和近期压缩记录。它是运行观察工具，不会自动判断摘要是否遗漏用户约束。依据：[上下文检查器](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/inspect/service.py)。

因此，不能把“测试通过”“压缩后低于目标”或者一次整体Benchmark成绩，直接表述为“记忆召回准确率已经验证”。这里核对的测试没有提供真实摘要的准确率结论。

### 建议怎样评估？

以下是建议补建的评估方案，不是当前已实现功能。

| 维度 | 具体检查 | 指标示例 |
|---|---|---|
| 压缩收益 | 输入到底减少多少；是否转移成昂贵的摘要调用 | 压缩前后Token、摘要调用成本、耗时 |
| 关键事实保留 | 用户约束、已做决定、文件路径、报错和未完成事项有没有丢 | 保留的标注事实数 / 应保留事实总数 |
| 事实正确性 | 摘要有没有编造修改、把失败说成成功 | 有原始证据支持的事实数 / 摘要中可核验事实总数 |
| 按需取回 | 只给压缩后上下文时，能否找到需要的归档证据 | 目标证据取回成功率、额外工具次数 |
| 后续任务效果 | 压缩后能否继续正确修改和验证 | 任务通过率、重复工作次数、违反约束次数 |

可用一份带标准答案的会话做例子：用户明确要求“不能修改公共接口”，工具返回了某个测试失败的具体断言，Agent尚未修复。压缩后再问“有哪些不可违反的约束？失败证据是什么？下一步做什么？”，检查是否保留了这三类信息。摘要写成“测试已通过”，即使Token省了很多，也属于质量失败。

### 怎样让对比有意义？

固定会话输入、模型配置、任务与判分标准，比较未压缩、仅程序化压缩、包含L4的几组结果。若未压缩上下文超过模型真实窗口，应改用可运行的较短对照集或另外说明基线限制，不能把无法发送的请求当作正常基线。

真实模型存在波动，需要多次运行并报告样本数；事实类问题优先用原始日志和明确规则判分，模型评审仅作为辅助。事实保留与任务成功率都要看：摘要能答对一道追问，不代表它一定能完成后续编码任务。

复习问题：Token压缩率高为什么不一定好？机制单测与真实摘要评估有什么区别？事实遗漏与事实编造如何分别计分？归档取回失败是找不到ID、取回内容不足，还是模型没有主动取回？

## 十三、完整示例：一次AUTO压缩

假设：

```
高水位：90,000
低水位：72,000
当前输入：95,000
```

执行：

```
L1裁剪旧任务对话
95,000 → 88,000
仍高于72,000
```

继续：

```
L2压缩派生工具结果
88,000 → 76,000
仍高于72,000
```

继续：

```
L3归档失效、重复工具结果
76,000 → 68,000
已经低于72,000
```

停止，不执行L4。

如果L3后仍然是：

```
74,000
```

才执行L4。

## 十四、设计原则与局限

可以总结成六点。

### 1. 先规则，后语义

```
L1～L3：确定性程序规则
L4：模型语义压缩
```

先使用更可控的规则，最后才让模型总结。

### 2. 从低风险到高风险

```
旧任务普通对话
→ 派生工具结果压缩
→ 工具结果归档
→ 整体工作状态总结
```

### 3. 不直接删除底层事实

原始JSONL事件通常保留，压缩主要改变模型有效视图。

但“原始数据存在”不代表“模型还能直接看到”，尤其是L1。

### 4. 保护未消费工具结果

工具结果至少成功发送给模型一次后，才能进入有损L2/L3处理。

### 5. 保持工具调用完整性

任何压缩和Checkpoint都不能切断：

```
assistant tool_call
→ tool result
```

### 6. 压缩结果必须有实际收益

- L2结果必须比原文小；
- L3归档必须成功；
- L4必须低于目标；
- 不满足则不提交替换。

---

### 已知局限

#### 1. 分类请求增加成本和延迟

每条新用户消息通常多一次隐藏模型请求，而且输入包含当前有效历史。

优化方向：

- 小模型；
- 本地分类模型；
- 规则优先；
- 只提供任务摘要和最近消息。

#### 2. active与candidate语义不清晰

模型只返回 `same`，程序却在不同状态下解释为：

- 继续active；
- 继续candidate。

分类Prompt没有明确描述候选任务，存在契约不一致。

#### 3. L1比较激进

L1不总结、不归档，只从模型有效上下文隐藏旧任务普通文本。误分类可能造成较大影响。

#### 4. Token估算不精确

字符数除以4不能完全匹配不同模型Tokenizer，因此需要高低水位和Prompt Too Long兜底。

#### 5. L4仍然可能丢失语义

即使采用七段结构，模型摘要仍可能遗漏细节。原始日志存在，但模型恢复时主要依赖Checkpoint和消息尾部。

#### 6. L4边界选择较激进

本地程序会尽量保留较少但合法的原始尾部，其余内容交给Checkpoint覆盖。如果摘要质量不足，可能损失近期细节。

#### 7. PROMPT_TOO_LONG路径成本较高

真实Provider拒绝后，目标仍是普通低水位，但当前代码即使程序化阶段达到目标，仍继续尝试L4。这有利于进一步留出余量，但会增加一次模型摘要调用。

## 十五、面试总结

> 我把上下文管理分成任务边界、Token预算、程序化压缩和语义Checkpoint四部分。系统在每次主模型请求前估算固定上下文和历史上下文的Token占用，达到高水位后，以低水位为目标依次执行L1到L4。L1裁剪旧任务普通对话，L2按搜索结果、Diff、构建日志和JSON等内容类型压缩派生工具结果，L3将失效、重复或过大的工具结果归档为可按需取回的索引，前三层仍无法达到预算时，L4才通过模型生成七段式开发Checkpoint。
> 
> 除高水位AUTO外，系统还支持任务切换、手动压缩和Provider实际返回Prompt Too Long三种触发。底层会话采用append-only JSONL保存，压缩主要改变提供给模型的有效上下文视图，同时保护未消费工具结果和工具调用配对。当前不足主要是任务边界分类需要额外模型请求、active与candidate的语义契约不够明确、L1裁剪较激进，以及字符近似Token与真实Tokenizer存在误差。

## 十六、L4专题：Checkpoint、摘要Prompt与tail边界

这一节集中回答L4压缩中最容易混淆的问题，重点说明：L4生成的Checkpoint长什么样、已有Checkpoint时再次压缩哪些内容、tail到底按什么规则确定、未消费工具结果如何保护，以及当前边界算法存在哪些缺陷。

### 问题1：L4的核心作用是什么？

L4不会修改或删除JSONL中的旧消息，而是创建一个由“语义摘要”和“历史边界”组成的新Checkpoint。以后构造主模型请求时，Checkpoint覆盖范围内的旧消息不再逐条发送，而是由摘要代替；从tail起点开始的近期消息仍然保留原文。

因此，L4成功后的有效上下文是：

```
稳定系统前缀
+ Checkpoint摘要
+ Checkpoint之后保留的原始tail
```

稳定系统前缀包括主Agent的系统提示词、项目规则、工具Schema和临时运行指令等。L4只处理不断增长的会话历史，不压缩这些稳定输入。

JSONL中的原始用户消息、助手消息、工具调用和工具结果仍然保留。Checkpoint改变的是后续请求的投影方式，不是把旧事件从日志中物理删除。

### 问题2：L4生成的Checkpoint长什么样？

Checkpoint不是完整Session快照，主要保存摘要、覆盖边界、来源指纹和生成元数据。写入JSONL的事件大致如下：

```json
{
  "id": "evt_xxx",
  "session_id": "sess_xxx",
  "type": "checkpoint_created",
  "payload": {
    "id": "ckpt_xxx",
    "session_id": "sess_xxx",
    "summary": "## 当前目标\n……\n\n## 已知事实与硬约束\n……",
    "tail_start_message_id": "msg_101",
    "covered_until_message_id": "msg_100",
    "source_fingerprint": "source_xxx",
    "created_at": "2026-09-09T00:00:00Z",
    "sequence": 2,
    "strategy_version": "v1",
    "metadata": {
      "created_by": "l4_llm_compact",
      "summary_prompt_scope": "conversation_history_only",
      "retry_count": 0,
      "base_checkpoint_id": "ckpt_previous",
      "source_message_ids": [
        "ckpt_previous_summary",
        "msg_80",
        "msg_81",
        "msg_100",
        "msg_101"
      ]
    }
  },
  "created_at": "2026-09-09T00:00:00Z"
}
```

关键边界字段是：

```
…… → msg_98 → msg_99 → msg_100 → msg_101 → msg_102
      └────── 摘要覆盖范围 ──────┘    └── 原始tail ──┘
                         ↑                 ↑
             covered_until_message_id   tail_start_message_id
```

其中：

- `covered_until_message_id`表示旧历史被摘要覆盖到哪一条真实消息；
- `tail_start_message_id`表示从哪一条真实消息开始继续保留原文；
- `sequence`用于从多个Checkpoint中选择最新版本；
- `source_fingerprint`用于标识本次Checkpoint所依据的L4输入；
- `base_checkpoint_id`表示本次摘要是否建立在上一个Checkpoint之上；
- `source_message_ids`记录实际交给L4摘要器的消息ID；
- `summary_prompt_scope=conversation_history_only`明确表示摘要范围只有会话历史。

后续投影给主模型时，Checkpoint会变成一条合成的user消息：

```
[Checkpoint summary]
## 当前目标
……

## 已知事实与硬约束
……
```

主模型不会收到Checkpoint对象的全部元数据，只会看到摘要正文以及其后的真实tail。

### 问题3：第一次L4和已有Checkpoint后的再次L4，输入范围有什么不同？

第一次执行L4时，没有旧Checkpoint：

```
L4输入 = 当前有效会话历史
```

这里的“当前有效会话历史”已经可能经过L1～L3处理。例如旧文本可能已经被裁剪，工具结果可能已经被L2缩短或者被L3替换成归档占位符。L4接收的是程序化压缩后的视图，不是无条件重新读取全部原始正文。

已经有Checkpoint时，再次执行L4的输入是：

```
上一次Checkpoint摘要
+ 上一次Checkpoint保留的原始tail
+ 上一次Checkpoint之后新增的消息
```

例如：

```
旧Checkpoint已经覆盖msg_1～msg_10
旧tail从msg_11开始
后来又产生msg_12～msg_15
```

再次执行L4时，摘要器看到：

```
ckpt_1_summary
msg_11
msg_12
msg_13
msg_14
msg_15
```

它不会重新读取`msg_1～msg_10`的原文，而是使用`ckpt_1_summary`代表这些旧历史。因此，L4是递进式、层级式摘要：

```
第一次：旧历史 → Checkpoint 1
第二次：Checkpoint 1摘要 + 新历史 → Checkpoint 2
第三次：Checkpoint 2摘要 + 新历史 → Checkpoint 3
```

### 问题4：L4不会总结哪些内容？

L4会先排除`role=system_meta`的内部状态消息，而且不会把主Agent的系统提示词、工具Schema和Provider能力说明混入摘要输入。

因此，必须区分两个不同的System Prompt：

```
主Agent System Prompt
→ 指导主模型如何完成编码任务
→ 不进入L4摘要内容

L4摘要器自己的System Prompt
→ 指导摘要模型如何生成Checkpoint摘要
→ 只在这次独立摘要请求中使用
```

这样做是为了避免将稳定规则误写进动态摘要，恢复时污染系统提示词的保护边界。

### 问题5：L4的摘要提示词是什么？

L4会发起一次不带工具的独立模型请求：

```
tools = []
tool_choice = "none"
max_tokens = 1200
```

System Prompt是：

```text
你是 FirstCoder 的上下文压缩器。输出简洁的 coding handoff；必须且只能使用指定的七个 Markdown 标题，每个恰好一次；只在标题下写有证据支持的事实。不要选择 checkpoint 边界。
```

常规模式下，User Prompt的主要结构是：

```text
摘要模式：常规压缩。

只能按以下 coding handoff 格式输出。每个标题必须恰好出现一次；若历史中没有某项的证据，写“无”：
## 当前目标
## 已知事实与硬约束
## 已确认的决定及理由
## 相关文件与当前实现状态
## 已运行命令及有效结果
## 当前错误与未解决事项
## 下一步（可立即执行）

需要压缩的会话历史：

[msg_1] role=user
……

[msg_2] role=assistant
……
```

如果进入更强摘要模式，第一行改为：

```text
摘要模式：更强压缩，优先保留可恢复事实。
```

构造Prompt时，每条消息中有内容的part会被拼成文本，连续过多的空行会被折叠；每条消息最多取约4000个字符，超过部分添加`...[truncated]`。

摘要模型只生成正文，不生成边界。`tail_start_message_id`和`covered_until_message_id`由本地程序选择。模型输出后，本地还会进行格式归一化，保证七个标题各出现一次，缺失部分填“无”。

### 问题6：摘要模型看到哪些消息，与最终被Checkpoint替代哪些消息，是一回事吗？

不是。这是理解L4时最容易混淆的地方。

摘要模型会看到本次完整的L4来源：

```
旧Checkpoint摘要
+ 旧tail
+ 新增消息
```

新Checkpoint最终真正替代的是：

```
旧Checkpoint所代表的历史
+ 当前真实消息中位于新tail之前的部分
```

从新的`tail_start_message_id`开始，消息虽然也进入过摘要模型的Prompt，但仍会以原文形式出现在后续主模型请求中。因此，“进入摘要Prompt”不等于“最终不再保留原文”。让摘要模型同时看到近期tail，有助于生成连续的交接摘要。

### 问题7：程序按最近几条消息或最近几个turn保留tail吗？

都不是。当前实现没有“保留最近N条消息”或“保留最近N个turn”的固定参数。

它使用的规则是：

> 从最后一条真实消息开始向前试探，找到最短的、工具调用序列合法的消息后缀，作为初步tail。

这里的“消息后缀”是指：

```
某个候选tail起点
一直到当前最后一条消息
```

“最短”意味着程序首先尝试只保留最后一条消息；如果不合法，才逐条向前扩大。

### 问题8：按实际执行顺序，tail是怎么找到的？

完整顺序如下。

第一步，构造L4来源。如果有旧Checkpoint，来源是“旧Checkpoint摘要 + 旧tail + 新消息”；如果没有旧Checkpoint，来源是当前全部有效会话历史。

第二步，排除旧Checkpoint的合成摘要消息。合成摘要会进入L4摘要Prompt，但不能成为`tail_start_message_id`或`covered_until_message_id`。边界候选必须是真实消息。

第三步，确认至少存在两条真实候选消息。因为L4既要覆盖至少一条消息，又要保留至少一条tail；不足两条时无法建立这种边界。

第四步，先尝试最后一条真实消息：

```
真实消息：msg_11、msg_12、msg_13、msg_14

第一次候选tail：
[msg_14]
```

第五步，对`msg_14`到最新消息这一段按时间顺序做工具序列校验。这里不会检查`msg_11～msg_13`，因为它们正是准备被新Checkpoint覆盖的部分。

第六步，如果`[msg_14]`不合法，将候选起点向前移动一条：

```
第二次候选tail：
[msg_13, msg_14]
```

仍然不合法时继续扩大：

```
第三次候选tail：
[msg_12, msg_13, msg_14]
```

第七步，找到第一个工具序列合法的后缀后立即停止搜索。假设最终选中：

```
tail = [msg_13, msg_14]
```

那么：

```
tail_start_message_id = msg_13
covered_until_message_id = msg_12
```

第八步，边界确定后才构造L4 Prompt并调用摘要模型。也就是说，默认摘要模型不会参与tail选择。

第九步，摘要返回后，本地重新检查边界顺序、工具序列以及未消费工具结果保护。全部通过后，才生成候选Checkpoint。

第十步，用候选Checkpoint构造一次主模型有效上下文并重新估算Token。只有严格低于目标Token，才将Checkpoint写入JSONL。

用伪代码表示初步tail搜索：

```python
candidates = 当前真实消息

for index in range(len(candidates) - 1, 0, -1):
    candidate_tail = candidates[index:]
    if 工具调用序列合法(candidate_tail):
        tail_start = candidates[index]
        covered_until = candidates[index - 1]
        break
```

### 问题9：“候选tail内部从前向后检查”具体检查哪个范围？

检查范围是：

```
候选tail起点
→ 后面的消息
→ 当前最新消息
```

不是：

```
上次Checkpoint起点
→ 候选tail起点之前
```

例如：

```
上次Checkpoint后的真实消息：
msg_10、msg_11、msg_12、msg_13、msg_14

当前候选tail起点：msg_13
```

工具序列校验只检查：

```
[msg_13, msg_14]
```

即将被摘要覆盖的：

```
[msg_10, msg_11, msg_12]
```

不参与这一次候选tail的工具序列校验。后面的未消费结果检查才会扫描上次Checkpoint后的全部真实消息。

### 问题10：什么叫“工具调用序列合法的tail”？

这里的“合法”只表示工具调用事务满足Provider要求，不表示语义完整，也不表示保留了完整问答轮次。

校验器按时间从前向后遍历候选tail，并维护：

```
pending_tool_call_ids
```

处理规则是：

```
遇到assistant tool_call：
    把tool_call_id加入pending集合

遇到tool_result：
    它的tool_call_id必须已经在pending集合中
    匹配成功后从pending集合移除

遇到下一条user或assistant消息：
    pending集合必须为空

遍历到tail末尾：
    pending集合必须为空
```

因此必须满足：

1. 每个工具结果在当前tail内都有对应的assistant工具调用；
2. 每个assistant工具调用在当前tail内都有对应的工具结果；
3. 不能从工具结果中间切入，产生孤立的`tool_result`；
4. 不能保留一个缺少结果的`tool_call`；
5. 一次并行调用多个工具时，对应结果必须全部存在；
6. `tool_call`和`tool_result`必须携带有效且匹配的`tool_call_id`；
7. 一组工具调用没有全部闭合前，不能进入下一条普通user或assistant消息。

它不检查：

- 是否保留了最近N条消息；
- 是否保留了最近N个turn；
- 是否保留了完整的user-assistant问答；
- tail在语义上是否包含足够信息。

因此更准确的说法是“工具调用序列合法的消息后缀”。

### 问题11：普通消息情况下，最终可能只保留最后一条吗？

会。

例如：

```
msg_11 user       提出需求
msg_12 assistant  分析需求
msg_13 user       补充要求
msg_14 assistant  给出阶段结果
msg_15 user       提出当前问题
```

程序第一次尝试：

```
tail = [msg_15]
```

这条消息没有孤立工具结果，也没有未完成工具调用，因此工具序列合法。程序会立即选择：

```
covered_until_message_id = msg_14
tail_start_message_id = msg_15
```

因此，当前实现可能只保留最后一条真实消息。它依赖Checkpoint摘要保存此前的重要事实，而不是强制保留最近几个完整turn。

### 问题12：最后几条包含一次工具调用时，tail怎么确定？

假设：

```
msg_13 user       要求修改代码
msg_14 assistant  tool_call(call_1)
msg_15 tool       tool_result(call_1)
```

第一次尝试：

```
tail = [msg_15]
```

它不合法，因为`tool_result(call_1)`在候选tail中找不到前置的`tool_call(call_1)`。

第二次尝试：

```
tail = [msg_14, msg_15]
```

检查过程：

```
msg_14：把call_1加入pending
msg_15：找到result(call_1)，从pending移除call_1
遍历结束：pending为空
```

因此选择：

```
covered_until_message_id = msg_13
tail_start_message_id = msg_14
```

### 问题13：一次并行调用多个工具时，tail怎么确定？

假设：

```
msg_3 assistant
    tool_call(call_1)
    tool_call(call_2)

msg_4 tool_result(call_1)
msg_5 tool_result(call_2)
```

搜索过程是：

```
[msg_5]
→ 失败，孤立的result(call_2)

[msg_4, msg_5]
→ 失败，两个结果都找不到前置tool_call

[msg_3, msg_4, msg_5]
→ 成功，call_1和call_2都有对应结果
```

因此整个并行工具事务必须一起保留：

```
tail_start_message_id = msg_3
```

### 问题14：未消费的工具结果是怎么判断的？

工具序列完整只能说明消息格式合法，不能说明主模型已经看到工具结果。因此，初步tail确定并且摘要返回后，还要执行第二阶段的未消费保护检查。

运行状态保存：

```
consumed_tool_result_part_ids
```

每个工具结果写入会话时都有自己的`tool_result part_id`。某次主模型请求成功返回后，本地才把这次有效请求中携带的工具结果part ID记录为已消费。

L4检查时，先扫描上次Checkpoint后的全部真实消息，建立：

```
tool_call_id → 对应assistant消息索引
```

然后继续从前向后遍历全部`tool_result`：

```
part_id在consumed_tool_result_part_ids中
→ 已消费，可以被Checkpoint覆盖

part_id不在consumed_tool_result_part_ids中
→ 未消费，必须保护
```

对于未消费结果，程序通过`tool_call_id`找到对应assistant工具调用的位置。保护起点不是结果消息本身，而是整个工具事务的assistant调用位置。

如果有多个未消费工具结果，程序取最早的工具事务位置：

```
earliest_protected_index
```

最后比较：

```
candidate_tail_start_index > earliest_protected_index
```

如果成立，说明候选tail起点位于未消费工具事务之后，这个事务将被Checkpoint隐藏，因此候选失败。

### 问题15：工具序列检查和未消费检查分别扫描哪一段？

假设：

```
上次Checkpoint的tail起点 = msg_10
新候选tail起点 = msg_13
最新消息 = msg_14
```

两个阶段的范围不同：

```
工具序列检查：
[msg_13, msg_14]

未消费结果检查：
[msg_10, msg_11, msg_12, msg_13, msg_14]
```

工具序列检查只回答：“如果从msg_13开始给Provider看，工具调用结构是否完整？”

未消费检查回答：“准备隐藏的msg_10～msg_12中，是否还有主模型从未看过的工具结果？”

所以未消费检查不是在找到候选边界后继续倒序寻找，而是单独从头到尾扫描上次Checkpoint后的整个真实tail。

### 问题16：未消费工具结果位于候选tail之前时，当前代码会自动扩大tail吗？

不会。

例如：

```
索引0：msg_10 user
索引1：msg_11 assistant tool_call(call_1)
索引2：msg_12 tool_result(call_1)，尚未消费
索引3：msg_13 assistant 普通回复
索引4：msg_14 user
```

初步工具序列搜索可能直接选择：

```
tail = [msg_14]
candidate_tail_start_index = 4
```

未消费扫描发现：

```
earliest_protected_index = 1
```

因为：

```
4 > 1
```

候选边界会隐藏`msg_11～msg_12`这次未消费工具事务，所以本次L4返回：

```
failure_reason = unconsumed_boundary
```

当前实现不会返回边界搜索步骤，把tail改成：

```
[msg_11, msg_12, msg_13, msg_14]
```

而是直接让本次L4失败。

### 问题17：顺序执行多个工具时，如果上下文满了，后面的工具还没有执行怎么办？

正常执行链路中，“上下文满了”不会中断正在执行的一批工具。上下文容量只在准备下一次模型请求时检查，不是在每执行一个工具后检查。

假设模型一次返回：

```
assistant
    tool_call(call_1)
    tool_call(call_2)
    tool_call(call_3)
```

系统先把完整assistant工具调用消息写入JSONL，再执行这一批工具：

```
执行call_1 → 写入result_1
执行call_2 → 写入result_2
执行call_3 → 写入result_3
```

全部工具执行结束后，系统才准备下一次Provider请求：

```
重建SessionView
→ 估算上下文
→ 必要时执行压缩
→ 调用模型
```

JSONL本身可以继续增长，受模型窗口限制的是下一次请求，不是工具执行过程。

如果因为权限审批、用户输入、取消、进程异常等原因真的留下了没有结果的工具调用，例如：

```
msg_10 assistant
    call_1
    call_2
    call_3

msg_11 result(call_1)
msg_12 result(call_2)
缺少result(call_3)
```

那么包含`msg_10～msg_12`的候选tail遍历结束后，`pending_tool_call_ids`中仍有`call_3`，工具序列不合法。向前加入更老的消息也无法补上未来缺失的结果，所以L4最终找不到安全边界，返回`no_summary`，不创建Checkpoint。

正常审批恢复链路会先为原调用补上最终结果，取消和中断恢复也会尝试追加失败或中断结果。系统不会带着半截工具事务继续调用主模型。即使异常状态漏到请求构建阶段，ContextBuilder也会再次校验工具序列并拒绝发送。

### 问题18：`unconsumed_boundary`有重试机制吗？

在同一次L4流程中没有。

`unconsumed_boundary`被捕获后直接返回失败，不会：

- 再次调用摘要模型；
- 切换到stronger摘要；
- 重新运行更强的程序化压缩；
- 自动向前扩大tail；
- 提交Checkpoint。

上层Fallback也不会处理它。当前Fallback只对以下情况进行有限尝试：

```
prompt_too_long
→ 更强程序化压缩，必要时再做stronger L4

timeout
→ stronger L4重试

no_summary
→ stronger L4重试
```

`unconsumed_boundary`直接映射为`fail`。这是合理的一部分，因为它不是摘要质量问题，重新生成同样的摘要不能改变边界；不合理的部分是系统没有重新计算一个受未消费事务保护的更长tail。

### 问题19：一次出现`unconsumed_boundary`后，后面是不是永远都会失败？

不一定，取决于工具结果的消费状态能否发生变化。

如果当前上下文只是超过自动压缩目标，但仍低于模型硬容量，例如：

```
自动目标：80,000 Token
当前输入：100,000 Token
模型硬容量：128,000 Token
```

那么L4失败后，原始请求仍有可能发送给主模型：

```
主模型看到尚未消费的tool_result
→ 主模型成功返回
→ 本地记录该tool_result part_id已消费
```

以后再次触发L4时，同一个工具事务已经可以被Checkpoint覆盖，原来的边界可能通过检查。

如果消息和`consumed_tool_result_part_ids`都没有变化，重新执行L4仍会选择相同的初步tail，也会再次失败。单纯添加更多后续消息通常也不能解决旧的未消费事务，关键变化必须是工具结果真正被模型消费，或者边界算法得到修正。

### 问题20：如果未消费结果存在，同时上下文已经超过模型硬容量，会怎样？

这是最严重的情况。管理器会把失败原因进一步标记为：

```
unconsumed_result_over_budget
```

此时形成：

```
未消费工具结果不能被Checkpoint隐藏
→ 必须先发给主模型

但原始上下文已经超过模型硬容量
→ 无法发给主模型完成消费
```

数据不会被错误删除，但Agent可能无法继续推进。这是活性问题，而不是数据正确性问题。

### 问题21：系统会不会对相同失败无限自动重试？

不会无限重试。自动压缩失败会增加：

```
auto_compact_failure_count
```

连续失败达到3次后，自动压缩熔断器打开约30分钟：

```
auto_compact_failure_count = 3
→ auto_compact_disabled_until被设置
→ 后续AUTO返回circuit_open
```

这能避免反复调用摘要模型和持续消耗资源，但不能解决不合适的tail边界。手动压缩和特定恢复触发需要按各自入口的规则处理，不能把自动熔断理解为所有压缩永久关闭。

### 问题22：当前L4边界处理算不算项目缺陷？

算，但需要准确区分“安全保护”和“恢复缺陷”。

正确的部分是：

```
发现工具结果尚未被主模型消费
→ 拒绝建立会隐藏它的Checkpoint
```

这保证了关键工具结果不会在第一次成功投影前就被有损摘要覆盖，是正确的失败关闭策略。

缺陷在于：

```
初步tail选择没有使用consumed_tool_result_part_ids
→ 先选出一个过于靠后的tail
→ 甚至已经调用摘要模型
→ 事后才发现未消费边界冲突
→ 不调整tail，直接失败
```

它会导致：

1. 浪费一次本来可以提前避免的摘要模型调用；
2. 状态不变时重复选择同一错误边界；
3. 只能依靠未来一次成功主模型响应改变消费状态；
4. 在“未消费结果 + 超过模型硬容量”时可能阻断Agent继续运行。

因此可以定性为：

> 普通场景下，它是效率和健壮性缺陷；在未消费工具结果与硬容量超限同时出现时，会升级为可能阻断执行的功能性缺陷。它不是会错误丢失数据的缺陷，因为当前代码宁可失败也不会隐藏未消费结果。

### 问题23：更合理的tail算法应该怎样设计？

更合理的执行顺序是：

```
1. 构造当前L4来源

2. 在调用摘要模型前，扫描全部真实tail

3. 根据consumed_tool_result_part_ids找出所有未消费工具结果

4. 通过tool_call_id找到每个未消费结果所属事务的assistant起点

5. 得到最早保护位置earliest_protected_index

6. 按现有规则寻找工具序列合法的最短tail

7. 如果最短tail起点晚于earliest_protected_index，
   将tail起点向前调整到最早受保护事务

8. 再次验证调整后的工具调用序列

9. 使用最终边界构造摘要Prompt并调用模型

10. 构造候选Checkpoint并重新估算Token

11. 低于目标则提交；仍然超限则明确返回容量错误
```

可以概括为：

```python
structural_start = 找到工具序列合法的最短后缀起点()
protected_start = 找到最早未消费工具事务起点()

final_start = min(structural_start, protected_start)
```

这里的`min`表示选择时间上更早的位置，从而保留更长的原始tail。

调整后仍然必须重新检查：

- 工具事务是否完整；
- Checkpoint边界是否位于真实tail内；
- 摘要后是否严格低于目标Token；
- 来源指纹是否仍然一致。

这样既保留当前“未消费结果绝不被隐藏”的安全属性，又避免因为边界选择过晚而直接失败。

### 问题24：如何用一句话记住当前tail算法？

> 当前FirstCoder的L4先从最后一条真实消息开始向前扩大，寻找最短的、工具调用结构完整的消息后缀作为初步tail；摘要生成后，再扫描上次Checkpoint之后的全部真实消息，检查这个边界会不会隐藏未消费工具结果。若发生冲突，当前代码直接让L4失败，不会自动把tail向前扩展到受保护事务，因此这里存在效率、健壮性和极端情况下的可继续执行性缺陷。

## 十七、L3专题：归档文件、JSONL替换事件与按需取回

这一节集中说明L3归档的物理存储方式、JSONL中保存的内容、`archive_id`的生成方式，以及模型如何通过`retrieve_archive`重新取得原始工具结果。

### 问题1：L3归档是单独的文件，还是JSONL中的一条事件？

两者都有，但职责不同：

> 原始工具结果的可取回副本保存在独立归档文件中；JSONL保存原始会话事实，以及“将哪个消息片段替换成哪个归档占位符”的压缩事件。

不能把它简单理解成只写了一个JSONL事件。`retrieve_archive`真正读取的是独立归档文件，不是每次反向扫描JSONL寻找旧的工具结果。

同时也不能说原始内容只存在于归档文件。工具第一次执行完成时，完整结果已经作为`tool_result`事件写入JSONL；由于JSONL只追加，L3不会回头删除这条原始事件。L3会额外建立独立归档副本，供后续工具安全、快速地按`archive_id`读取。

### 问题2：归档文件保存在哪里？

FirstCoder默认数据目录是：

```text
<项目根目录>/.firstcoder
```

L3归档目录是：

```text
<项目根目录>/.firstcoder/archives/<session_id>/
```

每个`archive_id`对应两个文件：

```text
.firstcoder/
└── archives/
    └── sess_xxx/
        ├── ar_abc123....txt
        └── ar_abc123....json
```

目录按Session隔离。同一个`archive_id`出现在不同Session中时，也会位于各自的Session目录下，当前Session的取回工具不能任意读取其他Session的归档。

### 问题3：`.txt`和`.json`分别保存什么？

`.txt`保存完整原始工具结果，例如：

- 完整测试日志；
- 完整Git Diff；
- 完整搜索结果；
- 完整Shell输出；
- 其他被L3归档的`tool_result`正文。

`.json`保存用于描述和校验归档的元数据，大致如下：

```json
{
  "archive_id": "ar_abc123...",
  "content_sha256": "abc123...",
  "original_chars": 35842,
  "original_tokens": 8961,
  "created_at": "2026-09-09T10:00:00Z",
  "schema_version": "v2"
}
```

其中：

- `content_sha256`用于校验原文有没有被修改；
- `original_chars`记录原始字符数；
- `original_tokens`记录归档时估算的Token数；
- `created_at`记录创建时间；
- `schema_version`用于判断当前代码是否支持这种归档格式。

### 问题4：`archive_id`是怎么生成的？

`archive_id`由原始工具结果正文生成：

```text
原始工具结果UTF-8文本
→ 计算SHA-256
→ 取前32个十六进制字符
→ 添加ar_前缀
```

即：

```text
archive_id = ar_<原始内容SHA-256的前32位>
```

因此它是内容寻址ID。相同原始内容会得到相同`archive_id`。在同一Session中重复保存相同内容时，已有文件通过完整性检查后可以直接复用，不必重复写入另一份相同归档。

文件写入采用临时文件加替换的方式：先在目标目录写临时文件、刷新到磁盘，再替换为正式文件，避免正常写入过程中留下只有一半内容的正式归档。

### 问题5：L3归档和写入JSONL的完整顺序是什么？

完整执行顺序是：

```text
1. 工具执行完成

2. 完整tool_result先作为正常会话事件写入JSONL

3. 后续触发上下文压缩

4. L3识别出可以归档的tool_result

5. 根据原始正文生成archive_id

6. 将完整正文写入：
   archives/<session_id>/<archive_id>.txt

7. 将哈希、字符数、Token数等写入：
   archives/<session_id>/<archive_id>.json

8. 根据归档信息生成短占位符

9. 确认占位符确实比原始内容更小

10. 向Session JSONL追加compaction_completed事件

11. 后续重建SessionView时应用replacement

12. 模型看到归档占位符，不再直接看到完整原文
```

如果归档文件写入或完整性校验失败，L3会跳过这次替换，继续保留原始工具结果，不会只留下一个无法取回的占位符。

### 问题6：L3归档占位符长什么样？

占位符大致如下：

```text
[Tool result archived]
archive_id=ar_abc123...
tool=shell
status=success
lifecycle=superseded
original_tokens=8961
summary=shell result is superseded: newer output exists.
Use retrieve_archive(archive_id, ...) to inspect the original.
```

它通常不超过约480个字符，只保留帮助模型判断“是否值得取回”的信息。

占位符对应的MessagePart metadata还会包含：

```json
{
  "archive_id": "ar_abc123...",
  "original_content_sha256": "abc123...",
  "original_tokens": 8961,
  "compaction_state": "archived",
  "compacted_by": "l3_archive",
  "lifecycle": "superseded"
}
```

占位符仍然是原工具调用对应的`tool_result` part，保留原有`part_id`和`tool_call_id`关系。因此L3只替换结果正文，不会破坏：

```text
assistant tool_call
→ tool_result
```

这条Provider要求的工具事务结构。

### 问题7：JSONL中的`compaction_completed`记录什么？

L3不会修改已经存在的`tool_result`事件，而是在JSONL末尾追加`compaction_completed`。其中会保存替换记录，例如：

```json
{
  "type": "compaction_completed",
  "payload": {
    "event": {
      "replacements": [
        {
          "message_id": "msg_tool_result",
          "source_part_id": "part_result",
          "replacement_part": {
            "id": "part_result",
            "kind": "tool_result",
            "content": "[Tool result archived]\narchive_id=ar_abc123...\n...",
            "metadata": {
              "archive_id": "ar_abc123...",
              "compaction_state": "archived"
            }
          }
        }
      ],
      "archive_ids": [
        "ar_abc123..."
      ]
    }
  }
}
```

关键字段含义是：

- `message_id`：要修改SessionView中的哪条消息；
- `source_part_id`：要替换这条消息中的哪个part；
- `replacement_part`：重放到这里时，应该使用的短占位符；
- `archive_ids`：本次压缩涉及的归档ID集合。

### 问题8：会话重建时，归档替换是怎么恢复的？

重放JSONL时的顺序是：

```text
先读到原始tool_result事件
→ SessionView中暂时得到完整工具结果

继续读到compaction_completed事件
→ 根据message_id和source_part_id找到原part
→ 使用replacement_part替换

最终SessionView
→ 只展示归档占位符
```

因此三个层次分别是：

```text
JSONL：
保存原始历史事实，以及后续的压缩替换事件

archives目录：
保存retrieve_archive真正读取的原始内容副本和校验元数据

重建后的SessionView：
应用替换后，看到归档占位符
```

原始内容在旧JSONL事件中还存在，不代表主模型仍然能直接看到它。模型请求使用的是重建并投影后的SessionView。

### 问题9：模型怎么知道可以取回原始内容？

模型在上下文中看到占位符中的：

```text
archive_id=ar_abc123...
Use retrieve_archive(archive_id, ...) to inspect the original.
```

当前Session的工具列表中还会注册一个Session绑定的：

```text
retrieve_archive
```

模型判断当前任务需要原始证据时，可以生成工具调用：

```json
{
  "archive_id": "ar_abc123..."
}
```

模型不需要也不能指定`.firstcoder/archives/...`的本地文件路径。工具创建时已经绑定当前`session_id`，执行器会使用：

```text
当前session_id + archive_id
```

定位归档文件。

### 问题10：`retrieve_archive`有哪些参数？

工具参数可以表示为：

```json
{
  "archive_id": "ar_abc123...",
  "query": "可选的搜索文本",
  "max_chars": 6000,
  "full": false
}
```

其中：

- `archive_id`必填；
- `query`可选，执行不区分大小写的字面文本搜索；
- `max_chars`默认6000，允许范围为1～12000；
- `full`默认false，表示是否直接读取原始正文模式；
- 不允许传入Schema之外的额外参数。

### 问题11：不传`query`，也不设置`full=true`时返回什么？

默认调用：

```json
{
  "archive_id": "ar_abc123..."
}
```

不会直接返回整个原始工具结果，而是返回诊断性预览，主要包括：

```text
Archive metadata
原始内容头部片段
原始内容尾部片段
提示使用query或full=true继续读取
```

这样模型可以先低成本判断归档内容是否与当前任务相关，再决定是否进行更精确的第二次取回。

### 问题12：按`query`局部取回是怎么做的？

例如模型调用：

```json
{
  "archive_id": "ar_abc123...",
  "query": "AssertionError",
  "max_chars": 6000
}
```

程序会：

```text
1. 按行拆分原始内容

2. 不区分大小写搜索AssertionError

3. 每个命中保留命中行前2行和后2行

4. 合并重叠的上下文窗口

5. 为返回内容添加原始行号

6. 不连续的窗口之间加入[... omitted ...]

7. 将总返回量限制在max_chars以内
```

返回可能类似：

```text
117: running test_login
118: expected status 200
119: AssertionError: assert 500 == 200
120: response body: internal error
121: test_login failed
```

如果没有匹配行，返回：

```text
No matching lines found.
```

### 问题13：`full=true`是否一定返回整个归档？

不一定。

调用：

```json
{
  "archive_id": "ar_abc123...",
  "full": true,
  "max_chars": 12000
}
```

会进入原始正文读取模式，但仍然受到：

```text
max_chars <= 12000
```

限制。如果原文超过上限，只返回前面的限长内容，并在结果数据中标记：

```json
{
  "truncated": true
}
```

所以`full=true`的准确含义是“不做关键词窗口或头尾诊断，直接读取原文正文”，不是允许一次把任意大的日志完整塞回模型上下文。

### 问题14：取回归档时会进行哪些完整性检查？

`retrieve_archive`读取`.txt`和`.json`后会验证：

1. metadata使用的Schema版本是否受支持；
2. metadata中的`archive_id`是否与请求一致；
3. `.txt`实际内容的SHA-256是否与metadata一致；
4. `archive_id`是否确实由该内容的SHA-256生成；
5. metadata中的原始字符数是否与实际内容一致。

如果文件缺失、内容被篡改、metadata损坏、ID不匹配，或者当前Session中不存在该归档，工具统一返回安全错误：

```text
The requested archive is unavailable or failed integrity validation.
```

错误不会向模型暴露实际本地路径。

### 问题15：为什么`retrieve_archive`只能读取当前Session的归档？

这个工具是在创建Session工具注册表时按Session绑定的。模型只传`archive_id`，执行器隐式使用当前`session_id`查找：

```text
archives/<当前session_id>/<archive_id>.txt
archives/<当前session_id>/<archive_id>.json
```

因此，即使模型知道其他Session的`archive_id`，普通调用也不会自动切换到其他Session目录。

如果系统显式执行Session fork，归档复制器可以把源Session需要的归档文件复制到新Session目录。复制完成后，新Session通过自己的绑定工具读取新目录中的副本，而不是越权读取源Session目录。

### 问题16：取回后的内容会恢复到原来的历史位置吗？

不会。`retrieve_archive`不会把旧占位符原地改回完整正文。

执行链路是：

```text
assistant调用retrieve_archive
→ 工具读取独立归档文件
→ 返回局部或限长原文
→ 返回内容作为新的tool_result写入会话末尾
→ 再次调用主模型
```

原来的历史位置仍然保留短占位符，取回内容成为当前轮的一条新工具结果。

返回数据还会包含：

```json
{
  "archive_retrieval": true,
  "compaction_protected_until_turn": 11,
  "archive_id": "ar_abc123...",
  "query": "AssertionError",
  "full": false,
  "match_count": 2,
  "returned_chars": 850,
  "truncated": false,
  "original_tokens": 8961,
  "content_sha256": "abc123..."
}
```

`compaction_protected_until_turn`用于保护刚取回的结果，避免主模型还没使用，它马上又被L2或L3重新压缩。保护期结束后，这条新的派生工具结果仍可能按照正常生命周期再次进入压缩。

### 问题17：归档、替换和取回的完整链路是什么？

```text
完整tool_result写入JSONL
→ L3判断结果符合归档条件
→ 使用原文生成archive_id
→ 原文写入archives/<session_id>/<archive_id>.txt
→ metadata写入archives/<session_id>/<archive_id>.json
→ 生成短归档占位符
→ JSONL追加compaction_completed替换事件
→ 重建SessionView时应用占位符
→ 主模型只看到占位符、摘要和archive_id
→ 模型按需调用retrieve_archive
→ 工具按当前session_id定位并校验归档文件
→ 返回头尾诊断、关键词窗口或限长原文
→ 取回内容作为新的tool_result写入会话
→ 主模型基于取回内容继续推理
```

一句话总结：

> L3使用“独立文件保存可取回原文，JSONL记录不可变原始事实和后续替换关系”的组合方案。每个归档在当前Session目录中拥有一个正文`.txt`和一个metadata `.json`；模型通过占位符中的`archive_id`调用Session绑定的`retrieve_archive`，按头尾预览、关键词窗口或者限长原文三种方式取回，结果作为新的工具消息加入当前会话。
