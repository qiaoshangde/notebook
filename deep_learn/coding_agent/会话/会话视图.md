| 字段            | 含义                |
| ------------- | ----------------- |
| `session_id`  | 当前会话的唯一标识         |
| `messages`    | 当前有效的消息序列         |
| `checkpoints` | 已经持久化的 Checkpoint |
| `metadata`    | 会话级元数据            |
| `task_plan`   | 当前最新的任务计划         |


面试里我会先这样概括：

> `SessionView` 是 FirstCoder 根据 JSONL 事件日志重放出来的当前会话快照。它不保存第二份数据，而是把底层事件整理成消息、Checkpoint、元数据和任务计划，方便上下文构建、恢复和任务控制等模块直接读取。

下面可以逐个字段回答。

## 1. `session_id`

> `session_id` 用来标识这份视图属于哪个会话。因为系统可能同时存在多个 Session，重建、压缩、归档和状态查询时，都需要靠它把数据归属到正确会话。

它主要用在：

- 从对应的 `{session_id}.jsonl` 重建会话视图。
- 生成上下文指纹，区分不同 Session 的上下文。
- 上下文压缩成功后，把事件写回正确会话。
- L2、L3 压缩时，把大型工具结果存入正确 Session 的归档目录。
- `/context` 等检查命令返回当前会话标识。

例如上下文检查报告直接使用 `view.session_id`：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\inspect\\service.py)。

需要强调：

> `session_id` 通常不会作为聊天内容发送给模型，它主要服务于程序内部的隔离、关联和持久化。

---

## 2. `messages`

> `messages` 保存根据事件日志重建出来的当前有效消息。它包括用户消息、模型回复、工具调用、工具结果和后台通知等。每条消息内部又拆成多个 Part，例如文本、工具调用、工具结果和归档占位符。

数据结构可以理解为：

```
messages
└── AgentMessage
    ├── role
    └── parts
        ├── text
        ├── tool_call
        ├── tool_result
        └── archive_placeholder
```

定义可以在 [messages.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\messages.py) 看到。

### 在模型请求构建时怎么用？

模型请求构建是它最核心的使用场景。

FirstCoder不会把 `view.messages` 不加处理地全部发送给模型，而是按照下面的规则选择：[builder.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\projection\\builder.py)

```
SessionView.messages
        ↓
根据最新 Checkpoint 确定有效 tail
        ↓
处理重复工具调用
        ↓
校验 tool_call 与 tool_result 是否配对
        ↓
过滤已被裁剪的空消息
        ↓
转换成 Provider ChatMessage
```

### 到底用了几条 messages？

这里不是固定取最近 10 条或者最近 20 条，而是分两种情况。

#### 没有 Checkpoint

使用全部 `view.messages`：

```
if checkpoint is None:
    return view.messages
```

也就是说，如果视图中有 20 条消息，初始候选范围就是这 20 条。

但经过投影以后，最终发给 Provider 的数量可能少于或多于20条：

- `system_meta` 不会发送。
- 被完全裁剪的普通消息可能不会发送。
- 一条包含多个工具结果 Part 的内部消息，可能投影成多条 Provider 消息。
- 系统提示词不在 `view.messages` 中，但会额外加入 Provider 请求。

#### 存在 Checkpoint

只使用从 `tail_start_message_id` 开始到最后的所有真实消息，再额外添加一条 Checkpoint 摘要。

假设：

```
view.messages 一共 20 条
最新 Checkpoint 的 tail_start_message_id 指向第 15 条
```

那么候选上下文是：

```
1 条 Checkpoint 摘要
+ 第 15～20 条真实消息，共 6 条
```

也就是：

```
Checkpoint summary + 6 条 tail messages
```

对应代码在 [builder.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\projection\\builder.py) 和 [builder.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\projection\\builder.py)。

所以面试时最好说：

> FirstCoder不是按固定消息条数截断，而是使用“最新 Checkpoint 摘要加 Checkpoint 后面的完整消息尾部”。如果还超过 Token 预算，就先进行上下文压缩，再重建视图和请求，而不是简单删除前 N 条消息。

### messages 还在哪里使用？

除了构建请求，还用于：

- 恢复会话时统计用户轮数。
- 查找已完成的工具结果，保证工具调用幂等。
- 查找中断后尚未完成的工具调用。
- 上下文压缩时寻找可以裁剪或归档的消息 Part。
- UI 展示本轮新增消息。
- 检查工具调用和工具结果的顺序是否合法。

例如恢复时会扫描工具结果：[recovery.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\runtime\\recovery.py)。

## 3. `checkpoints`

> `checkpoints` 保存会话历史中已经持久化的所有 Checkpoint。Checkpoint本质上描述了两件事：前面一段历史的摘要，以及摘要之后应该从哪条真实消息继续。

一个 Checkpoint 中最关键的是：

```
summary
    旧历史的摘要

tail_start_message_id
    后面的真实消息从哪里开始

covered_until_message_id
    摘要覆盖到哪条消息
```

定义位于 [checkpoint.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\checkpoint.py)。

### 为什么是列表？

因为一个长会话可能经历多次语义压缩：

```
Checkpoint 1
Checkpoint 2
Checkpoint 3
```

事件日志会保留所有 Checkpoint，保证历史可审计。

但构建当前请求时，通常只使用最新的一个。这里也不是简单地取列表最后一个，而是按照：

```
sequence
→ created_at
→ checkpoint id
```

选择最新 Checkpoint：[models.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\checkpoint\\models.py)。

### 在哪里使用？

主要有四个地方：

1. 构建模型请求  
    使用最新 Checkpoint 的摘要，再选取它后面的消息。
    
2. 上下文压缩  
    L1、L2、L3 一般只处理最新 Checkpoint 后面的有效 tail，避免重复压缩已经被摘要覆盖的旧消息。
    
3. 上下文状态检查  
    `/context` 会显示最新 Checkpoint、tail 消息数量和边界是否合法。
    
4. L4 语义压缩  
    创建新的摘要和 Checkpoint，进一步推进历史边界。
    

面试里可以总结为：

> `messages` 保存完整的当前消息事实，`checkpoints` 决定本次模型请求从这些事实中选哪一段，并用什么摘要代替旧历史。

## 4. `metadata`

> `metadata` 保存会话级的附加属性，例如标题、Fork 来源以及创建会话时的上下文协议版本。它描述的是整个 Session，而不是某一条消息。

它来自两类事件：

```
session_created
session_metadata_updated
```

重建视图时，这些事件会按照顺序合并：[store.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\infrastructure\\jsonl\\store.py)。

合并规则是：

- 新字段加入字典。
- 已有字段被新值覆盖。
- `None` 不会删除旧字段。
- `session_id` 是保留字段，不能通过普通 metadata patch 篡改。

相关规则位于 [metadata.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\metadata.py)。

### 在哪里使用？

这里需要实事求是地说：

> 当前版本中，`SessionView.metadata` 主要承担会话描述和信息保留职责，并不会进入模型上下文。

具体来说：

- 重建 SessionView 时合并并保留。
- 压缩流程复制 SessionView 时，也会复制 metadata，避免候选视图丢失会话属性。
- 会话标题、Fork 来源等用户可见功能会使用相同的 Session 元数据事件。

不过，Session 的目录列表等入口有自己的索引和目录投影，并不一定直接读取 `SessionView.metadata`。

因此它目前和 `messages` 相比，业务使用较少。面试中可以把它描述为：

> 这是为会话级扩展预留的统一字段，不应该混入普通消息，也不应该直接发送给模型。

## 5. `task_plan`

> `task_plan` 保存当前最新的结构化任务计划。它不是历史计划列表，而是把多次计划更新事件依次重放后，得到的最新计划快照；如果当前没有计划，它就是 `None`。

计划更新时会校验：

- 计划结构是否合法。
- `previous_revision` 是否等于当前版本。
- 新版本是否正好递增 1。
- 事件版本是否和计划内部版本一致。

最后才会执行：

```
view.task_plan = plan
```

重放逻辑位于 [store.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\infrastructure\\jsonl\\store.py)。

### 在模型请求构建时怎么用？

如果 `task_plan` 不为空，会把当前计划渲染成一条临时的 system 消息，加入系统提示词：[request.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\agent\\preparation\\request.py)。

也就是说：

```
view.task_plan
    ↓
渲染当前任务、状态和依赖关系
    ↓
生成 1 条 system ChatMessage
    ↓
随本次请求发送给模型
```

这里发送的是当前计划快照，不是所有历史计划版本。

### 还在哪里使用？

- 判断是否应该暴露相应的 Planning 工具。
- `task_create`、`task_update` 等工具读取或修改当前计划。
- Agent准备结束任务时，检查是否还有未完成任务。
- 如果还有未完成任务，会生成一条协调指令，要求模型继续执行或说明阻塞原因。

最终完成检查位于 [policy.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\planning\\application\\policy.py)。

因此，`task_plan` 解决的是：

> 模型说“做完了”不等于任务真的做完了，程序还会根据结构化计划进行一次确定性检查。

## 一段完整的面试表达

> `SessionView` 是 FirstCoder根据 append-only JSONL 事件日志重建出来的当前会话快照。它有五个字段：`session_id` 负责会话隔离和数据关联；`messages` 保存当前有效的用户、模型和工具消息，构建请求时不是固定取最近 N 条，而是没有 Checkpoint 就使用全部消息，有 Checkpoint 就使用一条摘要加边界后的完整 tail；`checkpoints` 保存历次摘要边界，但当前请求只选择最新的一个；`metadata` 保存标题、Fork 来源这类会话级属性，它不会进入普通模型上下文；`task_plan` 保存最新的结构化计划，会作为一条临时 system 消息加入请求，同时用于工具暴露和任务完成校验。这个设计的核心价值是把不可变事件流水转换成各业务模块都容易读取的当前状态。

另外，`@dataclass(slots=True)` 中的 `slots=True` 主要是限制对象只能拥有预定义字段，并减少实例的内存开销，它不影响事件重放逻辑。
