# 会话重建：按当前重构后的代码阅读

> 本文按当前源码更新。旧版的 `AgentSession.create/resume` 已不再是当前构造入口；现在由 `SessionRuntimeFactory` 负责创建、恢复和组装运行对象。以下代码块是阅读用的简化流程，省略了依赖注入，不是可直接独立运行的脚本。

围绕一个问题阅读：

> 输入一个 session_id 和已有 JSONL，最后怎样得到一个可以继续聊天的 AgentSession？

## 第一步：先看测试，理解输入输出

先看 [会话恢复端到端测试](/E:/agent/后端agent开发资料/FirstCoder/tests/test_agent_e2e.py)。

核心流程是：

```text
创建原 AgentSession
→ 完成第一轮聊天并写入 JSONL
→ 根据同一个 session_id 恢复
→ 得到新的 AgentSession
→ 新建 AgentLoop，继续下一轮聊天
```

恢复不是让旧对象、线程或协程“复活”，而是根据持久化数据创建新的运行对象。

## 第二步：看恢复与组装入口

入口在 [SessionRuntimeFactory.resume](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/factory.py:77)：

```python
def resume(self, request):
    prepared = prepare_resumed_session_runtime(self.store, request.session_id)
    return self._build(request, prepared)
```

请求对象是 `ResumeSessionRuntimeRequest`。会话ID之外，当前的 AGENTS.md、Skill 目录、权限管理器、沙箱环境等由调用方提供，而不是从旧 JSONL 完整恢复。

### 第一组：重放日志

[prepare_resumed_session_runtime](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/assembly.py:42) 先执行：

```python
runtime_state = replay_runtime_state(store, session_id)
view = store.rebuild_session_view(session_id)
```

得到两份不同用途的数据：

- SessionView：消息、Checkpoint、metadata、TaskPlan。
- SessionRuntimeState：任务哈希、消费标记、压缩控制状态等。

当前是两次完整事件读取和重放，不是只从最新 Checkpoint 开始读取日志。Checkpoint 控制下一次模型请求使用哪些历史，不是 JSONL 的恢复起点。

### 第二组：推导运行索引

继续根据 `view.messages` 计算：

```text
known_message_ids：已知消息ID
turn_counter：恢复当前轮次
tool_result_message_ids：已记录工具结果的调用ID到消息ID映射
```

随后创建事件写入器，设置恢复后的轮次。这些索引不需要作为独立快照保存。

工具结果索引用于避免重复执行已有结果的同一调用，不等于对所有外部副作用提供“严格只执行一次”的保证。

### 第三组：重新组装运行依赖

工厂的 `_build` 会解析 Skill 目录，创建计划运行服务、工具注册表、写前审查对象等，再把写入器、恢复状态及当前权限和沙箱依赖组装成 AgentSession。

因此可以概括为：

```text
SessionRuntimeFactory.resume
= 两次事件重放
+ 推导运行索引
+ 重新创建或注入当前环境依赖
```

权限管理器是调用方传入的当前对象；不要理解成此处从 Session JSONL 恢复了旧权限模式和所有授权配置。

## 第三步：看 SessionView 怎么重建

打开 [JsonlSessionStore.rebuild_session_view](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/jsonl/store.py:56)：

```python
view = SessionView(session_id=session_id)
for sequence, event in enumerate(self.list_events(session_id), start=1):
    self._apply_event(view, event, sequence=sequence)
return view
```

真正的事件分流在同一文件的 `_apply_event`：

| 事件 | 对视图的影响 |
|---|---|
| session_created、session_metadata_updated | 合并 view.metadata |
| user_message、assistant_message、tool_result、background_notification | 追加 view.messages |
| checkpoint_created | 追加 view.checkpoints |
| task_plan_updated | 校验并恢复 view.task_plan |
| compaction_completed | 按事件中的替换记录更新已有 MessagePart |
| message_part_metadata_updated | 更新已有 Part 的 metadata |

SessionView 不是简单筛选日志，而是按顺序应用事件后的最终视图：

```text
事件1：写入原始工具结果 A
事件2：压缩事件，把 A 替换成 B
事件3：更新 Part metadata
→ 视图中是 B 及更新后的 metadata
→ JSONL 中原始事件仍然保留
```

## 第四步：看 SessionRuntimeState 怎么重建

打开 [replay_runtime_state](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/replay.py:13)。

它同样创建空状态、遍历完整事件日志、逐条应用事件，但恢复的是运行控制状态，不是消息内容。

事件更新哪些字段、哪些字段无法原样恢复，统一见[会话运行状态](/E:/notebook/deep_learn/coding_agent/会话/会话运行状态.md)。这里重点观察重放器如何根据event.type分流，以及它与SessionView重放使用同一份日志。

## 第五步：看恢复后怎样继续聊天

下一次主模型请求由 [AgentRequestPreparation.prepare](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/agent/preparation/request.py:67) 准备。

简化顺序：

```text
修复中断的工具事务、检查取消
→ 追加待处理指导和后台通知
→ session.rebuild_view()
→ 根据当前视图选择工具定义、构建系统前缀
→ context_service.prepare() 检查预算、按需压缩并生成投影
→ 用投影消息和工具定义构建 ChatRequest
→ 调用 Provider
```

恢复时得到的 SessionView 并不是永久缓存，继续请求时仍会重新获取当前视图。

模型消息由[ContextBuilder](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/domain/projection/builder.py)生成，再与工具定义一起构成ChatRequest。Checkpoint如何影响消息范围、实际发送几条消息，统一见[会话视图](/E:/notebook/deep_learn/coding_agent/会话/会话视图.md)。工具结果已消费的记录时机见《会话运行状态》。

## 第六步：最后看外层入口

用户输入 `/resume`，进入 [会话命令处理器](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/app/commands/session.py:111)：

```python
result = self.resume_service.resume(args[0])
self.current_session = result.session
self.on_resume(result.session)
```

[ResumeService](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/lifecycle/resume.py:31) 的顺序是：

```text
验证日志Schema
→ 查询并校验会话目录记录
→ bootstrap.resume(session_id)
→ 恢复待处理的权限执行状态
→ 返回 ResumeResult
```

其中 Bootstrap 把当前环境配置交给运行工厂。外层服务负责校验和恢复入口编排，不负责逐条归并事件。

## 恢复后的状态一定与退出前相同吗？

不一定。必须同时检查“运行时怎样更新”和“日志怎样重放”，不能只看事件是否写入。

### 当前已经确认的边界

`candidate_task_basis_message_id`写入任务边界事件，但当前运行状态重放器没有恢复该字段。这会让恢复后的候选依据消息ID缺失，即使候选哈希已经恢复。`system_prompt_fingerprint`不同：它本来就在下一次构建系统前缀时重新计算，不应把这种重新计算与漏恢复字段混为一谈。

依据：[任务边界事件](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/domain/task_boundary/service.py)、[运行状态重放器](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/replay.py)、[前缀构建](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/prompts.py)。

### 两套更新规则还应怎样对照？

下面是源码层面值得验证的一致性边界，不应表述为已完成了端到端故障复现：

| 场景 | 运行时与重放规则的区别 |
|---|---|
| 候选已有但还未达到确认阈值，又观察到same | 运行时可以继续累计候选；重放器对未confirmed的same会清空候选。默认阈值2常会直接确认，但更高阈值需要专门验证 |
| 程序化压缩成功，没有创建L4 Checkpoint | 自动模式管理器会清空失败状态；重放compaction_completed的分支仅恢复指纹和历史，没有对应的清空逻辑 |
| 失败计数与成功清零 | 管理器实时更新主要按mode判断；重放失败事件按trigger=auto判断，而L4成功事件会清零。非普通AUTO路径需逐项对照 |

这说明“运行内存中的状态”和“只重放相同日志得到的状态”需要契约测试约束。不能因为普通会话恢复测试通过，就推导所有压缩与任务切换分支都一致。

### 建议怎样验证恢复一致性？

以下是建议测试，不代表本次已经实现或运行：

```text
使用正常应用入口完成一段操作
→ 记录退出前的可恢复状态与视图
→ 销毁运行对象
→ 从相同JSONL恢复
→ 比较应恢复字段、消息Part和Checkpoint边界
→ 再执行下一步，比较控制决策是否一致
```

重点用例：新任务候选尚未确认时恢复；自动失败后仅L1～L3成功再恢复；L4失败但程序化替换已写入时恢复；Checkpoint已写入而完成事件尚未写入时恢复。

对当前时间相关字段比较语义，例如“熔断是否仍有效”，不要一律要求重新构造后的所有对象与时间戳完全相等。权限管理器、线程、工具实例属于重新构造的依赖，不属于日志原样恢复的对象。

复习问题：为什么append-only不等于完整恢复？怎样区分重新计算字段与漏恢复字段？状态看起来相同后，为什么还要比较下一步行为？
