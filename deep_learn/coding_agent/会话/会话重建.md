# FirstCoder 会话重建

> 本文只讲 FirstCoder 当前代码中的会话重建流程。`SessionRuntimeFactory` 负责创建、恢复和组装运行对象。以下代码块是阅读用的简化流程，省略了依赖注入，不是可直接独立运行的脚本。

围绕一个问题阅读：

> 输入一个 session_id 和已有 JSONL，最后怎样得到一个可以继续聊天的 AgentSession？

## 第一步：先看测试，理解输入输出

先看 [会话恢复端到端测试](/E:/agent/后端agent开发资料/FirstCoder/tests/test_agent_e2e.py)。

核心流程是：

```text
创建 AgentSession
→ 完成第一轮聊天并写入 JSONL
→ 根据同一个 session_id 恢复
→ 得到新的 AgentSession
→ 新建 AgentLoop，继续下一轮聊天
```

恢复不是让旧对象、线程或协程“复活”，而是根据持久化数据创建新的运行对象。

## 第二步：看恢复与组装入口

入口在 [SessionRuntimeFactory.resume](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/factory.py:77)：

```python
def resume(self, request):
    prepared = prepare_resumed_session_runtime(self.store, request.session_id)
    return self._build(request, prepared)
```

请求对象是 `ResumeSessionRuntimeRequest`。会话 ID 之外，AGENTS.md、Skill 目录、权限管理器、沙箱环境等由调用方提供，不属于 Session JSONL 的恢复内容。

### 第一组：重放日志

[prepare_resumed_session_runtime](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/assembly.py:42) 先执行：

```python
runtime_state = replay_runtime_state(store, session_id)
view = store.rebuild_session_view(session_id)
```

得到两份不同用途的数据：

- SessionView：消息、Checkpoint、metadata、TaskPlan。
- SessionRuntimeState：任务哈希、消费标记、压缩控制状态等。

恢复过程会进行两次完整的事件读取和重放，不是只从最新 Checkpoint 开始读取日志。Checkpoint 控制下一次模型请求使用哪些历史，不是 JSONL 的恢复起点。

### 第二组：推导运行索引

继续根据 `view.messages` 计算：

```text
known_message_ids：已知消息ID
turn_counter：恢复当前轮次
tool_result_message_ids：已记录工具结果的调用ID到消息ID映射
```

随后创建事件写入器，设置恢复后的轮次。这些索引不需要作为独立快照保存。

工具结果索引用于避免重复执行已有结果的同一调用，不等于对所有外部副作用提供“严格只执行一次”的保证。

### 第三组：重新组装运行依赖

工厂的 `_build` 会解析 Skill 目录，创建计划运行服务、工具注册表、写前审查对象等，再把写入器、恢复状态及当前权限和沙箱依赖组装成 AgentSession。

因此可以概括为：

```text
SessionRuntimeFactory.resume
= 两次事件重放
+ 推导运行索引
+ 重新创建或注入当前环境依赖
```

权限管理器由调用方传入；Session JSONL 不负责恢复权限模式和全部授权配置。

## 第三步：看 SessionView 怎么重建

打开 [JsonlSessionStore.rebuild_session_view](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/jsonl/store.py:56)：

```python
view = SessionView(session_id=session_id)
for sequence, event in enumerate(self.list_events(session_id), start=1):
    self._apply_event(view, event, sequence=sequence)
return view
```

真正的事件分流在同一文件的 `_apply_event`：

| 事件 | 对视图的影响 |
|---|---|
| session_created、session_metadata_updated | 合并 view.metadata |
| user_message、assistant_message、tool_result、background_notification | 追加 view.messages |
| checkpoint_created | 追加 view.checkpoints |
| task_plan_updated | 校验并恢复 view.task_plan |
| compaction_completed | 按事件中的替换记录更新已有 MessagePart |
| message_part_metadata_updated | 更新已有 Part 的 metadata |

SessionView 不是简单筛选日志，而是按顺序应用事件后的最终视图：

```text
事件1：写入原始工具结果 A
事件2：压缩事件，把 A 替换成 B
事件3：更新 Part metadata
→ 视图中是 B 及更新后的 metadata
→ JSONL 中原始事件仍然保留
```

## 恢复后的状态一定与退出前相同吗？

不一定。必须同时检查“运行时怎样更新”和“日志怎样重放”，不能只看事件是否写入。

### 当前已经确认的边界

`candidate_task_basis_message_id`写入任务边界事件，但当前运行状态重放器没有恢复该字段。这会让恢复后的候选依据消息ID缺失，即使候选哈希已经恢复。`system_prompt_fingerprint`不同：它本来就在下一次构建系统前缀时重新计算，不应把这种重新计算与漏恢复字段混为一谈。

依据：[任务边界事件](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/domain/task_boundary/service.py)、[运行状态重放器](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/replay.py)、[前缀构建](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/runtime/prompts.py)。

### 两套更新规则还应怎样对照？

下面是源码层面值得验证的一致性边界，不应表述为已完成了端到端故障复现：

| 场景 | 运行时与重放规则的区别 |
|---|---|
| 候选已有但还未达到确认阈值，又观察到same | 运行时可以继续累计候选；重放器对未confirmed的same会清空候选。默认阈值2常会直接确认，但更高阈值需要专门验证 |
| 程序化压缩成功，没有创建L4 Checkpoint | 自动模式管理器会清空失败状态；重放compaction_completed的分支仅恢复指纹和历史，没有对应的清空逻辑 |
| 失败计数与成功清零 | 管理器实时更新主要按mode判断；重放失败事件按trigger=auto判断，而L4成功事件会清零。非普通AUTO路径需逐项对照 |

这说明“运行内存中的状态”和“只重放相同日志得到的状态”需要契约测试约束。不能因为普通会话恢复测试通过，就推导所有压缩与任务切换分支都一致。

### 建议怎样验证恢复一致性？

以下是建议测试，不代表本次已经实现或运行：

```text
使用正常应用入口完成一段操作
→ 记录退出前的可恢复状态与视图
→ 销毁运行对象
→ 从相同JSONL恢复
→ 比较应恢复字段、消息Part和Checkpoint边界
→ 再执行下一步，比较控制决策是否一致
```

重点用例：新任务候选尚未确认时恢复；自动失败后仅L1～L3成功再恢复；L4失败但程序化替换已写入时恢复；Checkpoint已写入而完成事件尚未写入时恢复。

对当前时间相关字段比较语义，例如“熔断是否仍有效”，不要一律要求重新构造后的所有对象与时间戳完全相等。权限管理器、线程、工具实例属于重新构造的依赖，不属于日志原样恢复的对象。

复习问题：为什么append-only不等于完整恢复？怎样区分重新计算字段与漏恢复字段？状态看起来相同后，为什么还要比较下一步行为？

## 补充专题：从 L1/L2 压缩替换到百万事件级会话恢复

这一节整理从“L1 和 L2 压缩后会向 JSONL 写入什么”开始的连续讨论。它把上下文压缩、SessionView 重建、一次 Turn 中的重复重放、百万事件性能、状态快照与尾部事件重放，以及 SessionRuntimeState 的生命周期串成一条完整主线。宁可与前文有少量重复，也保留问题演进中的关键思考。

### 问题一：L1 和 L2 压缩后，会向 JSONL 写入什么？

提问时的推测是：

> JSONL 只追加、不修改，因此系统应该向 JSONL 追加一次压缩情况。真正被修改的是 SessionView 中的消息；以后重放 JSONL 时，先得到原消息，再读取压缩情况并修改 SessionView。

这个方向基本正确，但“修改 SessionView”需要说得更准确。L1、L2 不会修改原始 JSONL 消息，也不会直接修改一个长期常驻的 `session.view`。它们先克隆当前 SessionView，修改这份工作副本；随后把替换结果作为事件追加到 JSONL，最后再通过日志重放得到正式生效的 SessionView。

完整流程是：

```text
从 JSONL 重建当前 SessionView
→ CompactionPipeline 克隆一份工作 SessionView
→ 在工作副本上依次执行 L1、L2、L3
→ 每次有效替换都生成一条 replacement
→ 汇总成 CompactionEvent
→ 向 JSONL 追加 compaction_completed 事件
→ 再次重放 JSONL
→ 原始消息先被恢复
→ compaction_completed 中的 replacements 再覆盖对应 MessagePart
→ 得到压缩后的有效 SessionView
→ 将有效 SessionView 投影成发送给模型的消息
```

这里要区分“消息”和“事件”：`user_message`、`assistant_message`、`tool_result` 会在 SessionView 中形成消息；`compaction_completed` 是描述状态变化的事件，不会额外形成一条用户或模型消息。它的作用是告诉重放器：应当把哪个原始 MessagePart 替换成哪个压缩后的 MessagePart。

L1～L3 的程序化压缩通常共用一条 `compaction_completed`，并不是 L1 写一条、L2 再写一条。事件的简化结构如下：

```json
{
  "type": "compaction_completed",
  "payload": {
    "trigger": "auto",
    "target_tokens": 20000,
    "before_tokens": 28000,
    "after_tokens": 18000,
    "status": "success",
    "event": {
      "levels_attempted": ["l1", "l2"],
      "stopped_at": "l2",
      "changed_parts": 2,
      "source_part_ids": [
        "part_old_dialogue",
        "part_tool_result"
      ],
      "output_part_ids": [
        "part_old_dialogue",
        "part_tool_result"
      ],
      "replacements": [
        {
          "message_id": "msg_old",
          "source_part_id": "part_old_dialogue",
          "replacement_part": {
            "id": "part_old_dialogue",
            "message_id": "msg_old",
            "kind": "text",
            "content": "",
            "metadata": {
              "compaction_state": "trimmed",
              "compacted_by": "l1_old_task_dialogue"
            }
          }
        },
        {
          "message_id": "msg_tool",
          "source_part_id": "part_tool_result",
          "replacement_part": {
            "id": "part_tool_result",
            "message_id": "msg_tool",
            "kind": "tool_result",
            "content": "压缩后的工具结果",
            "metadata": {
              "compaction_state": "l2_route_compacted",
              "archive_id": "archive_xxx",
              "original_tokens": 3000,
              "replacement_tokens": 300
            }
          }
        }
      ]
    }
  }
}
```

上面只是用于理解字段的简化示例。当前 L1、L2 生成的 replacement 会继续使用原来的 MessagePart ID，因此 `source_part_id` 和 replacement 中的 `id` 通常相同；变化的是 `content` 和 `metadata`。

如果一次自动压缩没有产生有效替换，某些分支会写入 `compaction_skipped`；另一些已经进入程序化压缩但没有改变 Part 的路径，可能记录 replacements 为空的 `compaction_completed`。不能把“触发了压缩检查”理解为“一定修改了消息”。

- 触发和编排：[ContextWindowManager.compact_if_needed](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/compaction/service.py:71)

### 问题二：L1 和 L2 分别修改什么？

L1 是旧任务普通对话裁剪。它只处理符合旧任务和冷却条件的普通用户文本、模型文本，并保护最新用户消息以及包含工具调用的完整 Assistant 消息。L1 不是生成一句更短的自然语言摘要，而是有意忘记旧任务的普通文本。

压缩后的 Part 仍沿用原来的 `message_id`、`part_id` 和 `kind`，但正文变为空，并写入压缩元数据：

```python
MessagePart(
    id=原来的_part_id,
    message_id=原来的_message_id,
    kind=原来的_kind,
    content="",
    metadata={
        ...,
        "compaction_state": "trimmed",
        "compacted_by": "l1_old_task_dialogue",
        "original_tokens": 原始Token数,
        "content_fingerprint": 原文指纹
    }
)
```

构造 Provider 上下文时，不会为每个被裁剪 Part 生成一个占位消息，而是在有效尾部存在 L1 裁剪内容时加入一个聚合提示：

```text
[Earlier dialogue trimmed]
```

L1 的实现位于 [L1TaskTrimService](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/compaction/layers/l1_task_trim/service.py:27)。

L2 是工具结果的路由压缩。它不会处理所有工具结果，而是重点处理已经被模型消费、生命周期允许压缩、当前没有检索保护、尚未压缩过的派生工具结果。它会先识别内容类型，再使用对应压缩器：

```text
构建/测试输出 → 保留错误、失败和关键信息
Git Diff       → 保留主要变更
搜索结果       → 保留关键匹配
JSON           → 保留结构和代表性字段
HTML           → 提取主要内容
源代码         → 保留关键片段
普通长文本     → 生成较短预览
```

只有 replacement 的 Token 数确实小于原文时，L2 才会采用替换。采用后，它保留原 `part_id`，把 `content` 换成压缩内容，并加入 `compaction_state=l2_route_compacted`、`archive_id`、`original_content_sha256`、`original_tokens`、`replacement_tokens`、`lifecycle`、`lifecycle_reason` 和 `compacted_by` 等元数据。

原始工具结果事件仍然留在 JSONL；此外 L2 会把原文写入独立工具结果归档，replacement 通过 `archive_id` 指向归档，便于后续按需取回。L2 的实现位于 [L2ToolReductionService](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/application/compaction/layers/l2_tool_reduction/service.py:30)。

### 问题三：压缩 replacement 是怎样在 SessionView 中生效的？

JSONL 重建器按事件顺序执行：

```text
读到 user_message / assistant_message / tool_result
→ 构造原始 AgentMessage 和 MessagePart
→ 追加到 view.messages

读到 compaction_completed
→ 取出 event.replacements
→ 为当前消息建立 (message_id, part_id) 索引
→ 使用 message_id + source_part_id 找到原 Part
→ 用 replacement_part 替换原 Part
```

因此，磁盘中的事实仍然是“原始消息事件 + 后续压缩替换事件”；调用 `rebuild_session_view()` 得到的则是按顺序应用全部事件后的有效视图。

假设日志中依次出现：

```text
事件1：tool_result，Part A 内容为3000 Token原文
事件2：compaction_completed，把 Part A 替换成300 Token版本
事件3：message_part_metadata_updated，继续更新 Part A 的metadata
```

最终 SessionView 中看到的是 300 Token 的 Part A，并包含事件3更新后的 metadata；原始 3000 Token 的事件仍在 JSONL。

重建和 replacement 应用位于：

- [JsonlSessionStore.rebuild_session_view](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/jsonl/store.py:56)
- [`_apply_compaction_replacements`](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/jsonl/store.py:128)

### 问题四：工作副本替换完成后，什么时候更新正式 SessionView？

FirstCoder 没有一个长期保存并不断原地修改的 `session.view`，所以不存在 `session.view = compressed_view`。

自动压缩成功时的真实顺序是：

```text
第一次 context_snapshot()
→ 从 JSONL 重建压缩前 SessionView
→ CompactionPipeline 克隆工作副本
→ L1/L2 在工作副本中进行替换
→ 使用工作副本估算压缩后的 Token 和校验结果
→ 向 JSONL 写入 compaction_completed
→ ContextService 发现压缩成功
→ 第二次调用 context_snapshot()
→ 再次从 JSONL 重建 SessionView
→ 在重放中应用 compaction_completed.replacements
→ 得到正式用于本次 Provider 请求的压缩视图
```

因此存在两个不同的“生效”时刻：

1. L1/L2 替换工作副本后，内存中立即有一个用于试算的临时压缩视图。
2. `compaction_completed` 持久化后再次重放 JSONL，得到正式的、可恢复的压缩 SessionView。

`ContextService.prepare()` 在压缩成功后明确再次执行：

```python
view = request.session.context_snapshot().view
messages, budget = self._project_and_budget(view=view, ...)
```

所以正常成功路径中，新的 Provider 请求使用的是重新重放 JSONL 后的视图，不只是流水线中的临时工作副本。

### 问题五：每次模型请求前都会重建 SessionView 吗？

会。每次正式准备 Provider 请求时，当前代码都会重新获取 SessionView。一个包含工具调用的 Turn 会发生：

```text
第一次模型调用前
→ 重建 SessionView

模型返回 tool_call
→ assistant_message 写入 JSONL
→ 工具执行
→ tool_result 写入 JSONL

第二次模型调用前
→ 再次重建 SessionView
→ 因此能够看到刚写入的 tool_call 和 tool_result
```

但进一步检查当前调用链后，需要补充一个重要事实：一次 Provider 请求的准备阶段并不只是重建一次，而是通常至少两次。

```text
AgentRequestPreparation.prepare()
→ session.rebuild_view()                         第1次
→ 根据这份View选择工具定义、构建系统前缀

ContextService.prepare()
→ session.context_snapshot()
→ context_snapshot内部再次调用rebuild_view()   第2次
→ 进行上下文投影、Token预算和压缩判断
```

第一处在 [AgentRequestPreparation.prepare](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/agent/preparation/request.py:67)，第二处在 [ContextService.prepare](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/context/api.py:37)。

这两次分别服务于请求输入准备和 Context 模块，但都从同一个 JSONL 重建完整 SessionView，因此存在重复工作。当前没有一个请求级共享快照贯穿工具筛选、系统前缀、上下文投影和预算估算。

### 问题六：一个 Turn 会不会重建很多次？

会。一个用户 Turn 不等于一次模型请求。一个 Turn 中可能包含第一次模型调用、一轮或多轮工具调用后的模型续跑、TaskPlan 对账调用、完成门禁调用和 Prompt Too Long 压缩重试。

每发生一次正式 Provider 请求，当前请求准备链路通常至少重建两次 SessionView。因此只看正式 Provider 请求，可以粗略理解为：

```text
没有工具调用：
1次Provider请求 × 至少2次重建
≈ 至少2次

有1轮工具调用：
2次Provider请求 × 至少2次重建
≈ 至少4次

有3轮工具调用：
4次Provider请求 × 至少2次重建
≈ 至少8次
```

这些数字还没有计算任务边界分类、消息 metadata 标记、待审批工具恢复等其他调用 `rebuild_view()` 的位置。

压缩发生时重建次数会更多。压缩流水线要反复计算程序化压缩前 Token 数、每一层执行前后 Token 数、整个程序化压缩后的 Token 数、L4 候选视图 Token 数以及压缩持久化后的正式视图 Token 数。

当前预算估算回调为了获取 `data_root`，使用：

```python
request.session.context_snapshot().data_root
```

而 `context_snapshot()` 会完整重建 SessionView。也就是说，即使预算估算实际针对传入的工作副本，仅仅为了取得一个数据目录，也会产生额外重建。这是明确的优化点，不是上下文压缩算法本身的必要成本。

### 问题七：JSONL 达到百万事件后，当前实现会怎样？

当前 FirstCoder 的 JSONL Session 存储适合中小型会话，不适合百万事件级会话。

设：

```text
N = 当前JSONL事件数量
R = 一个Turn中完整重建的次数
```

`JsonlSessionStore.list_events()` 会从文件开头读取所有非空行，将每一行解析成 `SessionEvent` 并先放进列表；`rebuild_session_view()` 再遍历这个列表归并 SessionView。因此：

```text
单次重建时间：O(N)
单次重建临时内存：O(N)
一个Turn的重建时间：O(R × N)
```

当前 L1/L2/L4 上下文压缩不会删除 JSONL 中的原始事件。它只改变有效 SessionView 和模型投影，所以“模型看到的上下文可能已经很短”不等于“底层 JSONL 重放已经变快”。

当前还有一个更严重的放大点：每次 `JsonlSessionStore.append_event()` 写入一条事件后，都会调用 `SessionIndex.update_event()`；后者为了重新计算会话目录摘要，又调用 `_load_session_events()` 全量读取该 Session 的 JSONL。

因此百万事件下不只是读视图慢，连追加一条事件也可能再次扫描百万行。证据：

- 全量事件读取与视图重建：[store.py](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/jsonl/store.py:35)
- 每次写入后的目录索引更新：[index.py](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/index.py:27)
- 索引更新中的全量读取：[index.py](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/infrastructure/index.py:107)

所以不能只依赖 L4 Checkpoint 解决百万事件恢复。Checkpoint 只改变下一次模型请求从哪里投影历史，Session 恢复仍然从日志第一行开始。

### 问题八：当前项目有没有持久化的全状态快照？

没有。当前有三个容易被混淆的对象。

第一，`SessionContextSnapshot`：

```python
@dataclass(frozen=True, slots=True)
class SessionContextSnapshot:
    view: SessionView
    runtime_state: SessionRuntimeState
    current_turn: int
    data_root: Path
```

它只是当前请求期间使用的临时内存包。创建它时，SessionView 已经通过完整 JSONL 重放得到；它不会写入磁盘，不能加速进程重启后的恢复。

第二，`checkpoint_created`：

```text
旧历史
→ LLM生成语义摘要
→ 保存摘要和tail边界
→ Provider只接收摘要+Checkpoint后的消息
```

它是模型上下文 Checkpoint，不是 Session 存储快照。恢复时仍然要读取 Checkpoint 之前的原始事件，才能构造完整 SessionView。

第三，`session_index.json`：

它用于 `/sessions`、`/resume` 等列表页面快速显示会话标题、状态、最近输出等摘要，不包含完整 SessionView 和 SessionRuntimeState，也不能作为恢复起点。

所以当前恢复仍然是：

```text
完整读取JSONL
→ replay_runtime_state()重建SessionRuntimeState

再次完整读取JSONL
→ rebuild_session_view()重建SessionView

根据SessionView推导：
→ known_message_ids
→ turn_counter
→ tool_result_message_ids

重新创建：
→ ToolRegistry
→ PermissionManager相关运行对象
→ Writer
→ AgentSession
```

当前恢复入口的注释也明确说明：Checkpoint 不是 resume 的存储边界，底层事实仍来自完整事件日志。见 [ResumeService](/E:/agent/后端agent开发资料/FirstCoder/firstcoder/session/application/lifecycle/resume.py:1)。

### 问题九：能否在 JSONL 中定期写入完整状态快照，再执行尾部重放？

提出的方案是：

> 每隔一段时间向 JSONL 存储一次快照，快照保存当前所有 SessionView 和 SessionRuntimeState。恢复时从 JSONL 末尾向前查找最近快照，加载它，再顺序重放快照之后的事件。

这个核心思想是正确的，标准名称可以叫：

> 事件溯源中的状态快照与尾部事件重放（state snapshot + tail-event replay）。

假设：

```text
事件1
事件2
……
事件50000
状态快照：覆盖到sequence=50000
事件50001
……
事件51000
```

恢复时就可以：

```text
加载sequence=50000的状态快照
→ 得到当时的SessionView和SessionRuntimeState
→ 只重放50001～51000
→ 得到最新状态
```

恢复复杂度由“处理全部历史”降低为“加载最近快照 + 重放快照后的少量尾部事件”。这个思考的核心是正确的。

但是不建议把不断增大的全量快照持续追加进同一个 JSONL，原因有三点。

第一，JSONL 每行长度不固定，没有天然的倒序行索引。从末尾向前找快照需要自行实现分块倒读和换行定位；如果快照本身是一行很大的 JSON，读取和解析也很笨重。

第二，如果每次快照都保存“当前全部 SessionView”，快照会越来越大：

```text
第1次快照包含1万条状态
第2次快照包含2万条状态
第3次快照包含3万条状态
……
```

由于旧快照继续留在 append-only JSONL，历史状态会被反复复制，可能造成近似二次级的累计空间增长。

第三，事件是不可变的原始事实；快照是可以重新生成、格式可以升级、旧版本可以删除的派生数据。它们生命周期不同，分开保存更合理。

### 问题十：更合理的持久化快照结构是什么？

中等规模可以采用：

```text
sessions/sess_xxx/
├── events.jsonl
├── snapshot.json
└── snapshot.meta.json
```

百万事件级别更适合日志分段：

```text
sessions/sess_xxx/
├── manifest.json
├── snapshots/
│   ├── snapshot-0900000.json
│   └── snapshot-1000000.json
└── events/
    ├── events-0001.jsonl
    ├── events-0002.jsonl
    └── active.jsonl
```

快照至少应保存：

```json
{
  "snapshot_version": 1,
  "session_id": "sess_xxx",
  "last_applied_sequence": 1000000,
  "last_applied_event_id": "evt_xxx",
  "event_segment": "events-0100.jsonl",
  "event_byte_offset": 9283712,
  "view": {
    "session_id": "sess_xxx",
    "messages": [],
    "checkpoints": [],
    "metadata": {},
    "task_plan": {}
  },
  "runtime_state": {},
  "current_turn": 1200,
  "created_at": "...",
  "checksum": "..."
}
```

各字段作用：

- `last_applied_sequence`：快照已经折叠到第几条事件。
- `last_applied_event_id`：校验快照与日志边界是否一致。
- `event_segment + event_byte_offset`：直接定位尾部重放起点，不再扫描寻找最近快照。
- `view`：已应用压缩 replacement、metadata 更新和计划更新后的有效 SessionView。
- `runtime_state`：已应用消费事件、任务边界事件和压缩控制事件后的 SessionRuntimeState。
- `current_turn`：恢复 Writer 和当前轮次。
- `snapshot_version`：支持快照格式升级。
- `checksum`：识别未写完或损坏的快照。

`known_message_ids`、`tool_result_message_ids` 等派生索引可以从快照 View 重新计算；为了更快也可以一并保存，但必须把它们视为可重建的缓存，而不是新的事实来源。

### 问题十一：快照应怎样写入，才能保证崩溃恢复？

不能直接覆盖正式快照文件。推荐顺序是：

```text
确定一致性边界sequence=S
→ 从该边界复制当前物化SessionView和RuntimeState
→ 写入snapshot-S.tmp
→ 刷盘并校验完整性
→ 原子重命名为snapshot-S.json
→ 原子更新manifest中的latest_snapshot
```

可能出现的崩溃情况：

```text
快照尚未写完就崩溃
→ 临时文件无效
→ 继续使用上一个正式快照

快照完成后又追加了新事件
→ 快照仍然有效
→ 恢复时重放S之后的事件

最新快照损坏
→ 校验失败
→ 回退到前一个快照
→ 重放更多尾部事件
```

事件必须带稳定序号或者能够确定全序的日志位置；应用尾部事件时需要保证幂等，避免同一事件被重复应用。

### 问题十二：百万事件时，完整 SessionView 快照是否足够？

不够。如果快照仍然包含百万条消息，虽然省去了逐条重放，但仍然需要：

```text
读取一个巨大的快照文件
→ 解析百万条消息
→ 在内存中创建百万个对象
→ 请求前扫描、复制或索引这些对象
```

所以百万级系统还需要把“审计历史”和“当前请求读模型”分开：

```text
完整事件日志
→ 保存全部事实
→ 用于审计、导出、故障追踪

当前物化视图
→ 当前metadata
→ 当前TaskPlan
→ 当前RuntimeState
→ 最新Checkpoint
→ Checkpoint之后的活跃消息尾部

历史查看
→ 按页查询旧事件或旧消息
→ 不把全部历史一次性装入请求用SessionView
```

这可以理解成事件溯源加物化读模型，也可以进一步采用 CQRS 的职责分离：

```text
写模型：append-only事件日志
读模型：当前SessionView/RuntimeState物化表
恢复加速：版本化状态快照
历史查询：分页事件或归档
```

如果规模真的达到百万级，SQLite/WAL 往往比单个 JSONL 更合适。可以保留 `events` 表作为事件事实，同时在同一事务中更新消息、Part、TaskPlan 和 RuntimeState 的物化表。JSONL 可以继续作为审计导出格式，而不是高频查询和恢复的唯一存储。

### 问题十三：正常运行时还需要每次从持久化快照恢复吗？

不需要。持久化快照主要解决进程启动和 Session 恢复；正常运行时应维护一份增量物化状态：

```text
Session启动
→ 加载最近快照
→ 重放尾部事件
→ 得到内存SessionView和SessionRuntimeState

运行期间追加新事件
→ 先可靠写入事件日志
→ 将这一条事件应用到内存SessionView
→ 将这一条事件应用到内存SessionRuntimeState
→ 更新last_applied_sequence

模型请求前
→ 读取或复制当前内存物化视图
→ 不再从事件1开始重放
```

这样正常更新接近 `O(1)`，恢复成本接近“快照大小 + 尾部事件数量”。定期持久化快照，避免下次启动时尾部过长。

当前 FirstCoder 还没有这层常驻 SessionView。它把 JSONL 直接当作事实源，并在需要 View 时重新折叠全部事件。这种实现简单、容易验证，适合项目早期和中小会话；代价是长会话性能上限较低。

第一阶段最直接的优化不是立刻更换数据库，而是让一次请求共享一个 SessionContextSnapshot：

```text
模型请求开始
→ 创建一次SessionContextSnapshot
→ 工具筛选复用
→ 系统提示词构建复用
→ 上下文投影复用
→ Token预算复用
→ 请求结束后丢弃
```

特别是 Token 估算应直接复用第一次快照中的 `data_root`，而不是为了读取路径再次调用 `context_snapshot()`。这能消除同一次请求内部的明显重复重放，但不能从根本上消除单次 `O(N)`，所以后续仍要做增量物化和持久化快照。

### 问题十四：每次请求会不会重新构建 SessionRuntimeState？

不会。这里必须区分 SessionView 和 SessionRuntimeState：

| 对象 | 创建或恢复 Session 时 | 每次模型请求前 | 运行期间 |
|---|---|---|---|
| SessionView | 从 JSONL 重建 | 当前实现再次从 JSONL 重建 | 不作为长期权威对象保存 |
| SessionRuntimeState | 新建空状态或从 JSONL 重放 | 不重新重放，只做深拷贝 | 维护并修改 AgentSession 中的内存对象 |

恢复 Session 时执行：

```python
runtime_state = replay_runtime_state(store, session_id)
view = store.rebuild_session_view(session_id)
```

`replay_runtime_state()` 会完整遍历事件，根据事件恢复：

```text
provider_projection_consumed
→ consumed_tool_result_part_ids

task_boundary_observed
→ active_task_hash、candidate_task_hash等

checkpoint_created
→ latest_checkpoint_id、相关输入指纹

compaction_completed / compaction_skipped
→ 压缩历史、输入指纹、无效果指纹

llm_compaction_completed
→ L4结果、自动压缩失败计数、熔断状态
```

恢复完成后，`AgentSession` 持有这份内存状态。每次上下文请求创建 `SessionContextSnapshot` 时执行的是：

```python
SessionContextSnapshot(
    view=self.rebuild_view(),
    runtime_state=deepcopy(self.runtime_state),
    current_turn=self.current_turn,
    data_root=self.data_root,
)
```

因此：

```text
SessionView
→ 从JSONL重新重放

SessionRuntimeState
→ 从当前内存对象deepcopy
→ 不读取JSONL
```

`deepcopy` 只是隔离本次 Context 计算，不是重新恢复。Context 模块可能在副本中更新压缩失败计数、最新压缩指纹、熔断状态等；处理完成后，通过 `commit_context_runtime()` 把副本字段复制回 AgentSession 中的内存 RuntimeState。

### 问题十五：SessionRuntimeState 的修改怎样持久化？

正常运行时同时维护两层：

```text
JSONL状态变化事件
→ 持久化事实
→ 用于进程重启后的重放

AgentSession.runtime_state
→ 当前进程中的快速运行状态
→ 供后续请求直接读取和修改
```

例如工具结果被模型成功消费时：

```text
向JSONL追加provider_projection_consumed
→ 再把对应part_id加入内存consumed_tool_result_part_ids
```

系统不会每次把完整 `SessionRuntimeState` 序列化一遍，而是追加描述状态变化的事件。程序重启后，再把这些事件折叠成新的 RuntimeState：

```text
Session运行期间：
追加状态变化事件
+ 更新内存RuntimeState

Session恢复时：
重放状态变化事件
→ 重新生成RuntimeState
```

这也是为什么持久化快照需要同时保存 SessionView 和 RuntimeState：前者是消息、Checkpoint、metadata 和 TaskPlan 的当前读模型；后者是任务边界、消费标记和压缩控制等非自然语言状态。

不过，快照不能直接保存或恢复下列运行对象：

```text
线程、协程、Future
ToolRegistry和具体Tool实例
Provider客户端和网络连接
PermissionManager对象
锁
后台任务执行器
```

这些对象要根据当前配置重新创建。对于当前项目，权限模式也不是从 SessionRuntimeState 自动恢复；长期授权来自独立的 `permissions.json`。因此“保存 SessionView + RuntimeState”解决的是可折叠持久化状态，不等于把整个 Python 进程冻结后原样复活。

还有一个运行边界：如果两个进程同时打开同一个 Session，它们会各自维护一份内存 SessionRuntimeState。一个进程追加的新事件不会自动刷新另一个进程已经持有的 RuntimeState。当前设计更接近“同一 Session 同一时间只有一个主要运行实例”；要支持多进程并发，还需要单写者约束、版本检查或数据库事务。

### 问题十六：这段讨论形成的最终整体认识

可以把 FirstCoder 当前实现概括为：

```text
JSONL是唯一持久化事件事实源
        ↓
SessionView重放器
→ 消息、Checkpoint、metadata、TaskPlan
→ 应用compaction replacements
        ↓
SessionRuntimeState重放器
→ 任务哈希、工具结果消费、压缩控制状态
        ↓
重新创建Tool、Provider、权限和Writer等运行对象
        ↓
得到可继续运行的AgentSession
```

当前方案的优点：

- append-only，原始事实不被覆盖；
- 压缩替换可以审计和回放；
- SessionView 与 SessionRuntimeState 的职责清楚；
- 恢复逻辑确定，适合验证事件契约。

当前方案的限制：

- SessionView 每次需要时都全量重建；
- 一次 Provider 请求当前通常至少重建两次；
- 一个 Turn 内多轮工具调用会继续放大重建次数；
- Token 预算估算中还存在为了获取 `data_root` 而额外重建的问题；
- SessionRuntimeState 与 SessionView 恢复分别扫描日志；
- SessionIndex 每次事件追加后也会全量读取 Session 日志；
- 上下文压缩只减少模型输入，不减少 JSONL 重放成本；
- 百万事件下时间和内存开销都不可接受。

建议的演进顺序是：

```text
第一步：一次请求共享一个SessionContextSnapshot
→ 去掉请求内部重复重建

第二步：SessionIndex改成按新事件增量更新
→ 去掉每次append后的全量扫描

第三步：运行期间维护增量SessionView和RuntimeState
→ 新事件只应用一次

第四步：增加独立、版本化、原子写入的持久化状态快照
→ 恢复时执行“快照+尾部重放”

第五步：事件日志分段，历史按页查询
→ 避免单个超大JSONL

第六步：百万级场景使用SQLite/WAL或其他数据库物化读模型
→ 在保留事件审计能力的同时支持高效查询和事务更新
```

最终可以用一句话记住：

> FirstCoder 当前是“全量事件重放得到 SessionView，恢复时全量事件重放得到 SessionRuntimeState”；上下文 Checkpoint 只缩短模型输入，并不缩短持久化日志。面向超长会话，合理演进方向是“内存增量物化状态 + 独立持久化快照 + 尾部事件重放 + 分段事件日志”，而不是在同一个 JSONL 中不断追加越来越大的全量快照。
