
# 1、讲一讲后台工具调用是怎么做的？
FirstCoder 的后台工具调用，主要是为了解决耗时工具阻塞 Agent 主循环的问题。

当模型调用工具时，可以通过一个后台执行标记，表示这个工具不需要同步等待。工具执行层收到调用后，会先完成参数校验和权限检查，确认工具支持后台运行，再把真正的工具任务提交到线程池。

提交成功后，系统不会等待任务结束，而是立即返回一个包含后台任务 ID 的占位结果。这样既完成了这次工具调用的协议配对，也让 Agent 可以马上继续调用模型，处理其他任务。

后台任务执行完成后，结果会先进入完成队列。在下一次构建模型请求时，系统收集这些结果，并以独立的任务通知写入会话，让模型知道哪个后台任务成功、失败或者被取消。

另外，项目还提供了后台任务的状态查询和取消能力，并通过并发上限、会话隔离和协作式取消来控制运行风险。

我认为这个设计的核心是：把“工具调用已经受理”和“工具最终执行完成”拆成两个事件，从而实现非阻塞的 Agent 执行链路。

# 为什么真实结果不能继续作为原工具调用的第二个工具结果？

不能把真实结果作为原工具调用的第二个工具结果，主要是因为大模型的工具调用协议通常要求：一个 `tool_call_id` 只能对应一个工具结果。

后台任务启动时，FirstCoder 已经立即返回了“任务已受理”的占位结果。这个结果已经完成了原工具调用的配对：

```
tool_call(bg_0001)
    ↓
tool_result：后台任务已启动
```

如果任务完成后，再使用相同的 `tool_call_id` 返回第二个结果，就会变成：

```
同一个 tool_call
    ↓
两个 tool_result
```

这可能导致模型服务商拒绝请求，也会破坏会话历史的合法性。

另外，真实结果产生时，主循环可能已经进行了多轮模型调用。它在语义上已经不是原来那次同步调用的返回值，而是一个后来发生的异步事件。因此 FirstCoder 把它表示成独立的后台任务通知：

```
user: <task_notification>后台任务完成……</task_notification>
```

所以这套设计实际上区分了两个事实：

- 占位工具结果：表示“后台任务已经成功受理”；
- 后台任务通知：表示“异步任务最终执行完成”。

这样既满足工具调用协议，也能正确表达异步任务的时间关系。

可能的追问点：

1. 为什么占位结果必须是工具结果，而不能直接返回普通消息？
2. 为什么后台完成通知使用用户消息，而不是系统消息？

# 后台任务完成后，为什么不立即触发模型调用？

面试时我会这样回答：

后台任务完成后不立即触发模型调用，主要是为了保证模型调用仍然由主 Agent Loop 统一调度。

因为后台任务是在独立线程中执行的。它完成时，主循环可能正在：

- 调用模型；
- 执行其他工具；
- 压缩上下文；
- 等待用户授权；
- 准备结束当前任务。

如果后台线程直接发起模型请求，就可能出现多个线程同时修改会话、同时构建上下文，导致消息顺序混乱、状态竞争，甚至重复调用模型。

所以 FirstCoder 采用“先入队，后消费”的方式：

```
后台任务完成
    ↓
结果进入完成队列
    ↓
下一次模型请求开始前
    ↓
主循环统一收集结果
    ↓
写入 Session
    ↓
构建完整上下文并调用模型
```

这样做还有两个好处：

第一，可以批量处理通知。如果多个后台任务在相近时间完成，可以在一次模型请求中一起交给模型，避免每完成一个任务就调用一次模型，减少请求次数和成本。

第二，可以保证上下文一致。通知写入 Session 后，系统会和最新的用户消息、工具结果、任务计划一起构建请求，模型看到的是一个完整且顺序确定的会话状态。

所以我的理解是：后台线程只负责产生结果，不负责推进 Agent。Agent 的状态推进和模型调用始终由主循环负责。这是一种典型的“生产者—消费者”设计。

可能的追问点：

1. 如果后台任务完成后一直没有下一次模型请求，通知会丢失吗？
2. Agent 准备结束时，还有后台任务运行怎么办？
3. 多个后台任务同时完成时，通知顺序如何保证？

# 后台任务是如何取消的，能保证立即停止吗？

FirstCoder 的后台任务采用的是“协作式取消”，所以不能保证立即停止。

模型可以调用后台取消工具，并传入任务 ID。后台任务管理器找到任务后，会分两种情况处理。

如果任务还在线程池队列中、尚未开始执行，系统可以直接取消对应任务。这种情况下任务不会真正运行，状态会立即变成 `cancelled`。

如果任务已经开始执行，Python 线程本身不能被安全地强制终止。因此系统会：

- 把任务标记为已请求取消；
- 触发任务对应的取消令牌；
- 等待底层工具主动检查取消信号并退出。

执行链路可以概括为：

```
background_cancel(job_id)
    ↓
任务尚未开始 → 直接取消
    ↓
任务已经执行 → 设置 cancel_requested + 触发取消令牌
    ↓
底层工具检查取消信号后主动退出
```

因此能否及时停止，取决于底层工具是否支持取消。

例如一个长时间运行的工具会定期检查取消令牌，那么它可以很快结束；但如果工具正在执行一个不可中断的阻塞调用，或者完全忽略取消信号，那么实际代码仍可能继续运行到结束。

不过即使工具忽略了取消，FirstCoder 在最终结算时仍会根据 `cancel_requested` 把任务标记为 `cancelled`，不会把它当作正常完成，也不会据此自动完成关联的任务计划。

所以我会总结为：FirstCoder 能保证“取消意图和任务状态被正确记录”，但不能保证“底层工作立即物理停止”。这是线程模型下协作式取消的典型限制。

# 权限检查为什么必须发生在任务进入后台之前？

权限检查必须发生在任务进入后台之前，核心原因是：后台任务一旦启动，就可能立即产生真实副作用。

例如写文件、执行 Shell 命令或者修改代码。如果先提交后台任务、再向用户申请权限，就可能出现用户还没同意，操作已经执行了的问题。

另外，权限确认属于交互流程，需要主 Agent Loop 暂停并等待用户回答；后台线程不适合承担这种交互。如果后台任务执行到一半才请求权限，线程就可能长期挂起，主循环也难以正确恢复这次工具调用。

因此 FirstCoder 的顺序是：

```
模型发起工具调用
    ↓
参数和工具合法性校验
    ↓
权限预检
    ↓
需要确认 → 主循环暂停并等待用户
    ↓
权限通过
    ↓
冻结一份可信的工具调用
    ↓
提交后台线程执行
```

后台线程拿到的是已经通过权限检查的可信调用，因此执行时不会再次触发同一轮权限询问。

这样可以保证三个性质：

- 未授权的操作绝不会进入后台执行；
- 权限交互始终由主循环统一管理；
- 后台线程只负责执行，不负责和用户交互。

所以我会总结为：权限检查是后台任务提交的安全边界。只有获得授权的工具调用，才能从交互式主流程转移到非交互式后台执行环境。

可能的追问点：

# 后台任务状态是否会持久化，进程重启后能否恢复？

当前 FirstCoder 的后台任务状态不会完整持久化，进程重启后也不能恢复正在执行的后台任务。

后台任务管理器主要把这些信息保存在进程内存中：

- 任务 ID；
- 运行状态；
- Future 对象；
- 取消令牌；
- 执行结果；
- 已完成任务队列。

真正的执行载体是线程池。进程一旦退出，线程、Future 和内存中的任务状态都会消失。重启后会创建新的后台任务管理器，因此之前的任务无法继续执行，也无法通过状态查询工具找到。

不过，会话中已经写入 JSONL 的内容仍然存在，例如：

- 模型发起的后台工具调用；
- “后台任务已经启动”的占位工具结果；
- 已经收集并写入 Session 的完成通知；
- 已经更新的任务计划状态。

因此可能出现一种情况：

```
Session 中记录着 bg_0001 已启动
    ↓
进程在任务完成前崩溃
    ↓
重启后后台管理器中没有 bg_0001
    ↓
无法恢复，也收不到最终完成通知
```

所以当前实现更适合单进程、单次运行期间的异步任务调度，不是一个可靠的持久化任务队列。

如果需要支持重启恢复，我会把任务定义和状态存入数据库，并使用独立 Worker 执行。同时还需要补充：

- 全局唯一任务 ID；
- 任务租约和心跳；
- 超时任务重新调度；
- 幂等执行；
- 启动时状态对账；
- 结果持久化；
- 对“运行中但进程已消失”的任务进行失败或重试处理。

所以我会总结为：FirstCoder 持久化的是已经进入会话的事实，但没有持久化后台执行器的运行现场。

可能的追问点：

1. 为什么只保存任务状态还不足以恢复后台任务？
2. 什么是任务幂等，为什么恢复时必须考虑？
3. 如何判断一个 `running` 任务所在的进程已经死亡？

# 如何限制后台任务的数量和并发数？


FirstCoder 通过两个参数限制后台任务：`max_jobs` 和 `max_workers`。

`max_jobs` 控制最多允许多少个未结束的后台任务，默认是 8 个。这里既包括正在占用线程执行的任务，也包括已经提交但还在线程池中排队的任务。

每次提交任务时，后台任务管理器会在锁保护下统计状态为 `running` 的任务数量：

```
运行中和排队中的任务数
    ↓
是否达到 max_jobs
    ↓
达到上限 → 拒绝新任务
    ↓
没有达到 → 创建任务并提交线程池
```

达到上限后，系统会返回一个结构化工具错误，让模型知道后台容量已经用完，而不是无限创建任务。

`max_workers` 控制线程池中最多有多少个任务能真正同时执行，默认是 4 个。假设：

```
max_jobs = 8
max_workers = 4
```

那么最多可以接收 8 个后台任务，但同一时刻最多只有 4 个占用线程执行，其余任务在线程池队列中等待。

两者的区别是：

- `max_jobs` 限制系统接收任务的总容量，防止排队任务无限增长；
- `max_workers` 限制真正的执行并发，防止线程和系统资源被耗尽。

任务提交和状态修改都放在互斥锁中，因此即使多个请求同时提交任务，也不会因为并发竞争而突破容量限制。已经完成、失败或者取消的任务虽然还可以被查询，但不再占用 `max_jobs` 的运行容量。

所以我会总结为：FirstCoder 使用“准入上限加线程池并发上限”的双重控制，前者负责背压，后者负责资源隔离。

# 后台执行和同一轮多个工具并行执行有什么区别？

后台执行和同一轮多个工具并行执行，虽然都使用了并发，但解决的问题不同。

同一轮工具并行执行，主要解决的是“这一轮有多个互不影响的工具，如何更快地全部执行完”。例如模型同时读取三个文件，系统可以并行读取，但主循环仍然会等待这些工具全部结束，然后把真实结果一起发给模型。

```
模型一次返回多个工具调用
    ↓
多个工具并行执行
    ↓
等待这一批工具全部结束
    ↓
把真实工具结果一起发送给模型
```

所以它仍然属于当前工具轮次，只是把顺序执行优化成了并行执行。

后台执行解决的是“某个耗时任务不应该阻塞 Agent 继续工作”。系统提交任务后立即返回任务 ID，不等待真实结果，模型可以继续进入下一轮推理。

```
模型调用耗时工具
    ↓
提交后台任务
    ↓
立即返回占位结果
    ↓
模型继续处理其他事情
    ↓
任务完成后异步发送通知
```

两者主要有以下区别：

|对比点|同轮并行执行|后台执行|
|---|---|---|
|主循环是否等待|等待整批工具完成|不等待真实结果|
|返回给模型的内容|真实工具结果|先返回任务 ID，之后再通知结果|
|是否属于当前工具轮次|属于|实际任务跨越多个轮次|
|适合的任务|多个快速、独立的只读操作|耗时且可以独立进行的任务|
|工具调用协议|每个调用直接对应真实结果|原调用对应占位结果，真实结果作为异步通知|
|调度方式|当前批次并行调度|后台任务管理器和线程池调度|

举个例子：

如果模型要同时读取三个文件，适合同轮并行，因为模型下一步需要这三个文件的内容。

如果模型要运行完整测试，同时还可以继续分析代码，就适合后台执行，因为没有必要让整个 Agent 在测试期间一直等待。

所以我会总结为：同轮并行是“并行做完再继续”，后台执行是“先安排任务，主流程马上继续”。

1. FirstCoder 如何判断哪些工具可以同轮并行？
2. 为什么写文件工具通常不能随意并行执行？
3. 一个响应中的多个后台工具会如何调度？

# Agent 准备结束时，还有后台任务运行该怎么办？
Agent 准备结束时，如果还有与当前任务相关的后台任务正在运行，不能直接宣称任务已经完成。

FirstCoder 在开启“完成门禁”的运行模式下，会在模型返回最终回答后，再检查当前回合记录的后台任务状态。如果发现任务仍是 `running`，就会生成一条运行时指令，再调用一次模型，告诉它：

```
后台任务仍在运行，当前不能宣称任务完成。
```

整体流程是：

```
模型准备输出最终答案
    ↓
完成门禁检查执行证据
    ↓
发现相关后台任务仍在运行
    ↓
阻止直接结束
    ↓
追加完成检查指令
    ↓
再次调用模型处理
```

模型接下来可以选择：

- 使用状态查询工具检查任务；
- 继续处理其他工作；
- 明确告诉用户任务仍在运行；
- 等待后续通知后再做最终结论。

这里需要注意，完成门禁不会阻塞线程并一直等待任务结束，它只是阻止 Agent 在证据不足时错误地宣称“已经完成”。

另外，当前项目不是所有模式都默认开启这个机制：

- Benchmark 模式默认开启完成门禁；
- 普通交互模式默认没有开启。

因此在普通交互模式中，当前回合可能先结束，但后台任务仍然继续运行；完成结果会在后续发生模型请求时，通过后台任务通知进入会话。

所以我会总结为：FirstCoder 在严格运行模式下，通过完成门禁防止 Agent 带着未完成的后台任务错误收尾；但它采用的是继续推理和状态协调，而不是同步阻塞等待。

可能的追问点：

1. 完成门禁如何知道哪些后台任务和当前任务相关？
2. 为什么完成门禁不直接等待所有后台任务结束？
3. 普通交互模式为什么默认不开启完成门禁？
4. 如果后台任务失败，完成门禁会如何处理？
5. 完成门禁会不会导致模型无限调用？
6. 后台任务已经完成但通知还没写入 Session，会发生什么？
7. 如果后台任务只是长期运行的服务，Agent 应该如何判断任务完成？
8. 完成门禁和 TaskPlan 的最终状态校验有什么关系？


# 介绍一下门禁


完成门禁可以理解为 Agent 最终回答前的一次质量检查。它解决的问题是：模型可能主观上认为任务完成了，但从实际执行证据来看，任务还没有真正闭环。

例如模型修改完代码就直接说“已经修复”，但实际上可能存在这些问题：

- 修改后没有运行测试；
- 最近一次测试失败；
- 验证发生在修改之前，已经失效；
- 用户要求检查某个具体接口，但验证没有覆盖这个接口；
- 后台任务仍在运行或者已经失败；
- 验证命令只输出了信息，没有真正断言结果是否正确。

完成门禁就是在最终回答前检查这些风险。

## 它是怎么工作的？

### 1. 执行过程中收集证据

Agent 每执行完一个工具，系统都会记录与完成判断有关的证据，例如：

- 最近一次修改发生在什么时候；
- 使用了什么工具修改；
- 最近一次验证发生在什么时候；
- 验证是否成功；
- 验证是否发生在最后一次修改之后；
- 当前回合启动了哪些后台任务；
- 用户要求验证哪些具体目标和预期结果。

它不是让模型自己回忆有没有测试，而是由运行时维护一份结构化执行证据。

### 2. 模型准备结束

当模型返回普通文本、不再调用工具时，正常情况下 Agent Loop 就准备结束了。

FirstCoder 会先处理任务计划的最终对账，然后进入完成门禁检查：

```
模型准备输出最终回答
    ↓
TaskPlan 最终对账
    ↓
检查执行证据
    ↓
没有风险 → 正常结束
存在风险 → 暂时阻止结束
```

### 3. 根据证据生成未完成原因

门禁会检查几类问题。

第一类是后台任务：

```
后台任务仍在运行
后台任务执行失败，但结果尚未处理
```

第二类是修改和验证的顺序：

```
修改代码
    ↓
没有验证
```

或者：

```
验证通过
    ↓
又修改代码
    ↓
之前的验证已经不能证明最终状态
```

第三类是验证结果：

```
最近一次测试或检查失败
```

第四类是验收目标覆盖不足。

比如用户要求：

```
访问 /hello 接口必须返回 hello world
```

但 Agent 只检查了服务进程存在，没有真正访问接口，或者只执行了 `curl`，却没有断言响应内容，那么门禁仍然认为验收证据不足。

### 4. 生成运行时指令，再调用一次模型

如果发现风险，门禁不会自己运行测试，而是生成一条系统级运行时指令，大意是：

```
现在还不能结束。
当前仍存在以下验收风险：
- 最近一次修改之后没有验证
- 后台任务仍在运行

请使用工具完成验证或修复问题。
如果确实存在外部阻塞，需要准确说明阻塞原因，
不能在没有证据的情况下宣称任务成功。
```

然后 Agent 会再次调用模型。

模型可以根据指令：

- 继续调用测试工具；
- 查询后台任务；
- 修复验证失败的问题；
- 补充针对具体目标的验证；
- 确认无法完成时，明确说明真实阻塞。

如果模型重新调用了工具，工具执行完成后又会回到正常的工具循环。

### 5. 防止无限循环

完成门禁不会无限要求模型重新检查。

项目使用两个状态控制：

- 本轮是否已经触发过门禁；
- 本轮已经触发了多少次。

默认最多允许两次门禁机会。通常在状态没有发生变化时只触发一次。

如果第一次门禁之后，模型又修改了工作区，旧的验证证据可能再次失效，系统会允许重新检查一次；达到次数上限后，就不会继续无限追加门禁指令。

## 一个完整例子

假设用户要求修复登录接口：

```
模型修改登录代码
    ↓
模型直接回答“已经修复”
    ↓
完成门禁发现：修改后没有测试
    ↓
阻止结束，要求验证
    ↓
模型运行登录测试
    ↓
测试失败
    ↓
模型继续修复
    ↓
再次运行测试并通过
    ↓
完成门禁检查通过
    ↓
输出最终答案
```

这个机制保证最终回答尽量建立在执行证据上，而不是建立在模型的主观判断上。

## 当前项目的使用范围

FirstCoder 普通交互模式默认没有开启完成门禁，Benchmark 模式默认开启。

这说明当前项目主要把它作为严格任务执行和自动评测场景下的质量保障机制，而不是所有会话都强制启用。

## 总结表达

完成门禁是 FirstCoder 在最终回答前设置的一层证据校验机制。它持续记录修改、验证、后台任务和验收目标等执行证据。当模型准备结束时，系统会判断这些证据是否足以支持“任务已完成”。如果证据不足，就生成运行时指令让模型继续验证或修复；证据充分才允许正常收尾。它的核心价值是减少 Agent 没有验证就宣称完成的问题。

可能的追问点：

1. 完成门禁和 TaskPlan 最终对账有什么区别？
2. 系统如何判断一个工具属于修改工具还是验证工具？
3. 为什么测试通过后再次修改代码，会让原来的验证失效？
4. 如何判断验证是否覆盖了用户要求的具体目标？
5. 为什么普通交互模式默认不开启完成门禁？
6. 完成门禁为什么设置最大触发次数？
7. 如果模型收到门禁指令后仍然拒绝使用工具怎么办？
8. 完成门禁能否保证 Agent 的最终结果百分之百正确？

# 介绍一下任务计划对账

任务计划对账是 FirstCoder 在 Agent 准备输出最终答案前进行的一次计划状态检查。系统会从当前 Session 中重建最新的 TaskPlan，查看是否还有任务处于 `pending` 或 `in_progress`。如果没有任务计划，或者所有任务都已经是 `completed`、`cancelled`，就直接跳过；如果还有未完成任务，系统会生成一条运行时指令，再调用一次模型，提醒它继续完成剩余工作、使用任务更新工具修正任务状态，或者准确说明真实阻塞。这个过程不会自动把任务标记为完成，因为计划状态必须与实际执行情况对应，也不会为了汇报进度重新创建整个计划。同一个回合通常只对账一次，避免模型没有处理时产生无限循环。它主要检查的是“计划有没有正确收尾”，之后的完成门禁再检查“执行证据是否足以证明任务真的完成”。

任务计划对账，是指 Agent 准备输出最终答案时，再检查一次当前 TaskPlan，确保计划里的任务状态与 Agent 准备结束这个行为是一致的。

它主要解决一个常见问题：实际工作可能已经做完了，但任务计划里还有任务停留在 `pending` 或 `in_progress`；也可能确实还有工作没做，模型却准备直接回答“已经完成”。

## 它是怎么工作的？

当模型不再调用工具、准备结束本轮时，Agent 会从 Session 事件日志重新构建最新的 TaskPlan，而不是使用之前缓存的旧计划。

然后检查计划中是否存在非终态任务。

FirstCoder 把下面两种状态看作终态：

```
completed
cancelled
```

下面两种属于未完成状态：

```
pending
in_progress
```

因此判断流程是：

```
模型准备结束
    ↓
重新构建最新 TaskPlan
    ↓
没有 TaskPlan → 不需要对账
    ↓
所有任务都是 completed/cancelled → 不需要对账
    ↓
仍有 pending/in_progress → 生成对账指令
```

## 对账指令包含什么？

如果存在未完成任务，系统会生成一条运行时指令，告诉模型：

- 当前是线性计划还是 DAG 计划；
- 哪些任务仍然没有结束；
- 应该使用任务更新工具按任务 ID 修改状态；
- 不要为了汇报进度重新创建整个计划；
- 如果工作没有完成，就继续执行；
- 如果存在真实阻塞，就准确说明；
- 计划里还有必要任务未完成时，不要宣称全部完成。

例如当前计划是：

```
completed  inspect
in_progress implement
pending    verify
```

生成的指令大致是：

```
在结束前，请对账当前未完成的任务计划。

- [in_progress] implement：实现功能
- [pending] verify：运行测试

请继续完成必要工作，或者说明真实阻塞。
使用 task_update 更新任务状态，不要重新创建计划。
```

## 对账以后怎么继续？

这条对账指令会作为临时的运行时指令，再调用一次模型。

模型收到后可以：
- 继续调用工具完成剩余任务；
- 使用任务更新工具把已完成任务改成 `completed`；
- 把确定不再需要的任务改成 `cancelled`；
- 遇到真实阻塞时，在最终回答中说明原因。

如果模型继续调用工具，就会重新进入正常的工具执行循环。工具执行结束后，再回到最终处理流程，然后继续执行完成门禁。

完整顺序是：

```
普通模型与工具循环结束
    ↓
任务计划对账
    ↓
模型可以继续更新计划或者执行工具
    ↓
完成门禁
    ↓
最终回答
```

## 它会自动修改计划吗？

不会。
任务计划对账只负责发现未完成状态并生成指令，不会擅自把任务改成 `completed`。
因为系统只能看到计划状态，不能仅凭“模型准备结束”就判断任务真的完成。最终仍然需要模型根据实际执行情况，显式调用任务更新工具。
## 它是不是一个强制门禁？

准确地说，它更接近一次“收尾纠偏机会”，而不是无限阻塞的硬门禁。

同一个用户回合中，任务计划对账通常只触发一次。系统会记录：

```
task_plan_reconciliation_attempted = True
```

防止模型一直不更新计划时，系统反复追加同样的指令，造成死循环。

所以它能够提醒和推动模型完成计划收尾，但不能百分之百保证模型最终一定正确更新所有任务。

## 和完成门禁的区别

任务计划对账检查的是：

> 计划里的任务状态是否已经收尾。

完成门禁检查的是：

> 执行证据是否足以证明任务真的完成。

例如：

```
所有任务都标记为 completed
```

任务计划对账会通过。

但如果最后一次修改之后没有运行测试，完成门禁仍然可能不通过。

反过来，如果代码已经修改并且测试通过，但计划里还有任务处于 `in_progress`，那么执行证据可能没问题，但任务计划仍然需要对账。

## 总结表达

任务计划对账是 FirstCoder 在最终回答前进行的一次计划状态检查。系统会从 Session 中读取最新 TaskPlan，找出仍处于 `pending` 或 `in_progress` 的任务，并生成运行时指令，让模型继续完成工作、更新任务状态或者说明真实阻塞。它不自动篡改任务状态，而是给模型一次明确的收尾机会。完成对账后，系统才会继续执行完成门禁和最终回答流程。

# 介绍一下任务更新工具

FirstCoder 的任务更新工具叫 `task_update`，它用于增量修改已经存在的 TaskPlan，而不是重新创建整个计划。模型调用时会传入当前计划的版本号 `expected_revision`，以及一组按照稳定任务 ID 定位的更新内容，可以修改任务的状态、负责人和依赖关系，并且支持一次原子更新多个任务。执行时，系统先获取当前 Session 对应的进程内可重入锁和跨进程文件排他锁，然后从会话日志重建最新 TaskPlan，比较实际版本与 `expected_revision`。如果版本不一致，说明调用者依据的是旧计划，系统会拒绝更新并返回版本冲突；如果版本一致，就在内存中计算新的计划快照，校验任务 ID、状态、依赖关系和计划结构是否合法。校验通过后，新计划版本加一，并以 `task_plan_updated` 事件追加到 JSONL，其中记录旧版本号、修改内容和新的完整快照；以后重建 SessionView 时，就从这些事件恢复最新计划。如果提交的内容没有带来实际变化，则不会追加新事件，也不会增加版本号。因此它的并发控制是“悲观锁加乐观版本检查”的组合：进程内 `RLock` 和跨进程文件锁负责让读、改、写过程串行执行，`expected_revision` 负责识别等待锁期间已经过期的请求，避免旧状态覆盖新状态。

面试中可能继续追问：为什么同时需要文件锁和版本检查；为什么更新事件还要保存完整快照；批量更新如何保证原子性；版本冲突后模型如何重试；无变化更新为什么不增加版本号；任务依赖关系在更新时如何校验。


为什么需要 `expected_revision`；什么是乐观锁；批量更新为什么要保证原子性；任务状态之间有哪些合法转换；`task_update` 和 `task_revise` 有什么区别；发生版本冲突后模型应该如何处理。



这里的“并发操作”不是 TaskPlan 主动创建多个线程并行更新，而是防止两个独立执行上下文恰好同时修改同一个 Session。例如两个 Agent Loop、两个请求线程或者两个进程都调用了 `task_update`。在流式模式下，FirstCoder 会通过 `anyio.to_thread.run_sync` 把工具执行放到工作线程，避免阻塞事件循环；但同一轮里的 `task_update` 本身不会被当作只读工具并行执行，也不允许转成后台工具。真正发生并发时，两个更新会进入 [session_repository.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\planning\\infrastructure\\session_repository.py) 的 `mutation_lock`：同进程内先竞争当前 Session 对应的 `RLock`，跨进程再竞争同一个任务计划锁文件的排他锁。假设 A 和 B 都基于 revision 3 发起更新，A 先拿到锁，读取 revision 3，校验通过，生成 revision 4 并追加 JSONL，然后释放锁；B 此时才能进入，它会重新读取到 revision 4，但自己携带的 `expected_revision` 仍然是 3，于是触发版本冲突并拒绝写入。也就是说，系统允许请求并发到达，但真正的“读取—计算—追加事件”会被锁串行化，再通过版本号识别已经过期的请求。后台任务也不会在线程结束时直接修改计划，它只先进入完成队列，后续收集完成通知时才执行计划更新；如果这时碰到其他计划写入，同样走上述锁和版本校验。


`task_update` 是模型用来修改现有 TaskPlan 的工具。它不负责执行任务，也不负责创建计划，只负责修改计划里已有任务的状态、负责人或依赖关系。最常见的用法就是任务开始时把状态从 `pending` 改成 `in_progress`，任务真正完成后再改成 `completed`；如果任务确定不再需要，就改成 `cancelled`。所以你理解的“完成一个任务后，调用一次任务更新工具”是对的，这是它最典型的使用场景。只是它支持一次调用批量更新多个任务，所以不一定严格对应“一个任务一次调用”。

完整链路是这样的：

```
模型看到当前 TaskPlan 和 revision
    ↓
开始任务时调用 task_update
pending → in_progress
    ↓
模型执行真正的代码修改、搜索或测试
    ↓
任务完成后再次调用 task_update
in_progress → completed
    ↓
更新后的 TaskPlan 写入 Session JSONL
    ↓
下一次请求重新构建 SessionView
模型看到最新 TaskPlan
```

这里的状态更新不是系统根据普通工具执行结果自动完成的。比如模型执行了一次 `shell`，系统不会因此自动认为某个任务完成。模型需要根据实际结果主动调用 `task_update`。如果模型忘记更新，准备结束时任务计划对账会发现仍有 `pending` 或 `in_progress` 的任务，然后提醒模型调用 `task_update` 收尾。

模型调用 `task_update` 时，会携带两部分信息：当前计划版本号 `expected_revision`，以及要修改的任务。例如当前计划是 revision 3，模型想完成 `implement` 任务，就相当于提交：

```
{
  "expected_revision": 3,
  "updates": [
    {
      "id": "implement",
      "status": "completed"
    }
  ]
}
```

工具收到请求后，会进入 TaskPlanService。TaskPlanService 要做的不是简单改一个内存对象，而是完成一次完整的“读取—修改—写入”事务：它先从 Session 的 JSONL 重建最新 TaskPlan，然后检查版本号，计算新的计划，校验任务状态和依赖关系，最后追加一条新的 `task_plan_updated` 事件。原来的 JSONL 内容不会被覆盖，新事件中会保存旧版本号、修改内容以及新的完整计划快照。

因此，锁不是“写 JSONL 的时候才临时加一下”，而是包住整个 TaskPlan 更新过程：

```
获得锁
    ↓
从 JSONL 读取最新计划
    ↓
比较 expected_revision
    ↓
计算并校验新计划
    ↓
向 JSONL 追加 task_plan_updated
    ↓
释放锁
```

为什么要包住整个过程？因为任务更新属于典型的“先读后改再写”。如果只保护最后的 JSONL 写入，两个请求可能同时读到 revision 3，各自计算出 revision 4，然后依次写入两个互相冲突的 revision 4。虽然普通单 Agent Loop 通常是顺序执行的，但仓储层仍然要防御同一个 Session 被多个线程或多个进程同时访问的情况。

实际使用了两种真实锁：进程内使用当前 Session 对应的 `RLock`，保证同一个进程里的线程不能同时更新这份计划；跨进程使用 `portalocker` 文件排他锁，防止两个 FirstCoder 进程同时更新同一个 Session。在真实锁内部，还有一次 `expected_revision` 版本检查。这个版本检查不是锁，而是防止旧请求覆盖新状态的乐观并发控制。

例如 A、B 都基于 revision 3 更新计划，A 先拿到锁，成功写入 revision 4。B 随后拿到锁，会重新读取最新计划，发现实际版本已经是 4，而自己传入的 `expected_revision` 还是 3，于是拒绝更新，让模型重新读取计划后再重试。

所以最终可以这样理解：`task_update` 在任务开始、完成、取消或者负责人和依赖发生变化时使用；它通过稳定任务 ID增量修改 TaskPlan；更新结果以新事件追加到 Session JSONL；整个“读取、计算、写入”过程使用进程内锁和跨进程文件锁进行串行化，同时用 `expected_revision` 防止过期请求覆盖最新计划。

还有一个特殊情况：如果后台工具调用绑定了 `task_id`，后台任务成功完成并被收集时，系统可以直接调用 TaskPlanService 自动完成关联任务，不需要模型再显式调用 `task_update`。但这是后台任务联动的特殊路径，普通前台任务仍然主要依靠模型调用 `task_update` 更新状态。
