# FirstCoder 工具的分类

按**权限操作类型 action**整理 FirstCoder 工具。
这里的分类用于权限判断；前台／后台、串行／并行属于另一种执行方式分类，不在本表中混用。

以下清单覆盖当前项目的内置工具、会话与控制工具，以及动态 MCP 工具这一类别；
并不表示当前模型一定能看到所有工具，实际可见范围由注册配置、Agent 角色和运行时条件决定。

## 1. action 是什么，在哪里定义

`PermissionRequest.action` 表示权限操作类型。工具创建时，在本地 `ToolPermissionSpec` 中预先声明自己的 action，以及从哪个参数中提取检查目标；这份权限声明不发送给模型。

例如，`write` 和 `edit` 都声明 `action = WRITE_PATH`，并从调用参数 `path` 提取目标路径。它们进入同一个“写入路径”权限分支，再根据具体路径、当前权限模式和工具配置作判断。

```text
模型生成工具名称和具体参数
→ 本地读取工具的 ToolPermissionSpec
→ 提取 action、target、cwd 等字段
→ 构造 PermissionRequest
→ 匹配已有长期授权规则
→ 未命中时，按模式和 action 进入默认权限策略
→ 得到 ALLOW、ASK 或 DENY
```

这些字段分别回答不同问题：

| 字段或概念  | 回答的问题          | 示例                               |
| ------ | -------------- | -------------------------------- |
| 工具名    | 调用什么工具？        | `write`                          |
| action | 这属于哪类权限操作？     | `WRITE_PATH`                     |
| target | 本次操作针对什么目标？    | `src/app.py`                     |
| 权限模式   | 默认策略采用什么自动化程度？ | `standard`、`aggressive`、`bypass` |
| 权限决定   | 本次是否允许执行？      | `ALLOW`、`ASK`、`DENY`             |

## 2. 配置了权限声明的工具：按 8 种 action 分类

| action            | 含义          | 工具                                                  |
| ----------------- | ----------- | --------------------------------------------------- |
| `READ_PATH`       | 读取文件或目录     | `ls`、`view`、`grep`、`glob`、`tree`、`read_multi`       |
| `WRITE_PATH`      | 写入或修改文件     | `write`、`edit`、`apply_patch`                        |
| `DELETE_PATH`     | 删除文件或目录     | `delete`                                            |
| `EXECUTE_SHELL`   | 执行命令或代码     | `shell`、`python_exec`、`diagnostics`、`process_start` |
| `GIT_OPERATION`   | 执行 Git 操作   | `git_status`、`git_diff`、`git_log`                   |
| `NETWORK_REQUEST` | 发起网络请求      | `fetch`、`web_search`                                |
| `READ_ENV`        | 读取环境变量      | 当前没有单独声明此 action 的内置工具                              |
| `MCP_TOOL`        | 调用外部 MCP 工具 | 通过 MCP 适配器动态创建的所有工具                                 |

`READ_ENV` 已有枚举和权限策略，但不能因此推断项目存在一个 `read_env` 工具。

## 3. 没有配置权限声明的工具
没有（`ToolPermissionSpec`）

以下工具的 `permission` 为 `None`，不会为自身调用构造 `PermissionRequest`，因此不属于上表的 8 种 action。

| 类别 | 工具 |
|---|---|
| 思考与用户交互 | `think`、`ask_user` |
| 任务计划 | `task_create`、`task_update`、`task_revise`、`task_list` |
| 任务边界 | `task_boundary`（内部控制工具，不是普通主模型可用工具） |
| Skill 与归档 | `load_skill`、`retrieve_archive` |
| 子 Agent 委托 | `delegate` |
| 后台任务管理 | `background_status`、`background_cancel` |
| 长期进程管理 | `process_status`、`process_logs`、`process_stop` |

这些工具不进入统一的 grant／权限模式判断，但仍受工具可见范围、参数校验和各自业务规则约束。例如，`task_update` 仍要校验计划版本；`delegate` 创建的子 Agent 调用其他工具时，仍要遵守那些工具的权限规则。

`ask_user` 会向用户提问并等待回答，但这是普通用户交互，不属于权限系统的 `ASK`。

## 4. 同一个 action 内，工具仍然可以有不同配置

多个工具共用同一类权限策略，不代表它们每次都得到相同结果。结果还取决于目标参数、已有授权和以下本地声明：

| 字段 | 含义 | 当前特殊配置 |
|---|---|---|
| `allow_auto` | 默认策略是否允许自动放行，具体由相应 action 分支使用 | `python_exec`、`apply_patch`、动态 MCP 工具设置为 `False` |
| `allow_always` | 普通权限 ASK 时是否支持选择 Allow always 并创建长期授权 | `python_exec`、`apply_patch` 设置为 `False` |

两个字段默认都是 `True`。
`allow_auto=True` 只表示允许策略继续判断，不保证自动放行；
`allow_always=True` 也不代表已经存在长期授权。

例如，`write` 与 `apply_patch` 都属于 `WRITE_PATH`，但没有匹配 grant 时，Aggressive 可以在满足条件后允许 `write` 写入项目内普通文件，`apply_patch` 则因 `allow_auto=False` 返回 ASK。这里讨论的是默认权限策略，bypass 和已有 grant 要按完整流程判断；权限返回 ALLOW 后还可能有独立的写前审查。

## 5. action 分类容易混淆的边界

- `apply_patch` 统一声明为 `WRITE_PATH`。补丁即使包含删除、移动，也不会自动改成 `DELETE_PATH`。
- `shell("git status")` 属于 `EXECUTE_SHELL`，`git_status()` 属于 `GIT_OPERATION`。action 来自所调用工具的声明，不根据命令文本重新分类。
- `python_exec` 统一属于 `EXECUTE_SHELL`。代码里包含读文件、写文件或网络访问，也不会自动拆成多个权限申请。
- `web_search` 内部使用网络服务，工具本身声明为 `NETWORK_REQUEST`；通过通用 MCP 适配器创建的外部工具则声明为 `MCP_TOOL`。
- 支持写前预览的工具是 `write`、`edit`、`apply_patch`、`delete`，跨越 `WRITE_PATH` 和 `DELETE_PATH`。是否支持预览是另一项能力，不由 action 名称单独决定。


# 没有权限声明的工具

还有一些工具没有配置 `ToolPermissionSpec`，因此不会产生权限系统的 `ASK`，也不会显示上述选项，例如：

```
think
task_create
task_update
task_list
task_revise
delegate
background_status
background_cancel
process_status
process_logs
process_stop
retrieve_archive
load_skill
```

其中 `ask_user` 虽然也会暂停等待用户，但它是模型主动向用户提问，不属于权限审批。

## 最终结论

可以这样记：

```
普通权限 ASK
├─ 工具支持 allow_always
│  → Deny / Allow once / Allow always
│
└─ 工具不支持 allow_always
   → Deny / Allow once

写前审查单独要求确认
→ Deny / Apply reviewed change
```

所以，不同工具在 `ASK` 时看到的选项确实可能不同；但决定因素不只是工具名称，还包括工具的 `allow_always` 配置，以及这次暂停究竟来自权限策略还是写前审查。


# 哪些工具没有配置 `ToolPermissionSpec`
当前 FirstCoder 中，没有配置 `ToolPermissionSpec` 的主要是内部控制类、计划类、会话类和部分进程管理工具。

## 没有 `ToolPermissionSpec` 的工具

|类别|工具|
|---|---|
|模型内部控制|`think`|
|用户交互|`ask_user`|
|任务计划|`task_create`、`task_update`、`task_revise`、`task_list`|
|任务边界|`task_boundary`|
|Skill|`load_skill`|
|上下文归档|`retrieve_archive`|
|多 Agent|`delegate`|
|后台任务控制|`background_status`、`background_cancel`|
|进程查看和控制|`process_status`、`process_logs`、`process_stop`|

这些工具进入权限感知注册表时，因为：

```
tool.permission is None
```

权限预检会直接返回 `None`：

```
没有 ToolPermissionSpec
→ 不构造 PermissionRequest
→ 不进入 grant 和权限模式判断
→ 不出现权限审批界面
→ 进入工具自身的执行逻辑
```

不过，没有 `ToolPermissionSpec` 不代表它们完全不受任何限制。它们仍然要经过：

- 工具名称和参数校验。
- Agent 角色的工具白名单。
- 工具自身的业务校验。
- AgentLoop 的状态和调用次数限制。
- 工具内部可能存在的安全检查。

例如 `task_update` 没有权限声明，但它需要校验 `expected_revision`；`delegate` 没有权限声明，但子 Agent只能使用角色允许的工具；`process_stop` 没有权限声明，但只能停止 FirstCoder 自己管理的进程。

## 配置了 `ToolPermissionSpec` 的工具

为了方便对照，下面这些工具配置了权限声明：

```
ls
view
grep
glob
tree
read_multi

write
edit
delete
apply_patch

shell
python_exec
diagnostics

git_status
git_diff
git_log

process_start

fetch
web_search

所有动态 MCP 工具
```

它们在调用时会：

```
ToolPermissionSpec + 模型参数
→ PermissionRequest
→ grant 匹配
→ standard/aggressive/bypass 默认策略
→ ALLOW / ASK / DENY
```

其中：

```
python_exec、apply_patch
→ allow_always=False

其他已配置权限声明的工具→ 默认 allow_always=True
```

但是否真的出现 `ASK`，仍然取决于具体参数、现有授权和当前权限模式。例如 `git_status` 配置了权限声明，但在项目内属于只读 Git 操作，通常会直接 `ALLOW`，所以用户通常看不到审批界面。

还要注意，`ask_user` 虽然会暂停并等待用户输入，但它不是权限审批：

```
ask_user
→ Agent主动向用户询问信息

权限 ASK
→ 权限系统询问用户是否允许执行敏感操作
```

一句话总结：

> FirstCoder 只有配置了 `ToolPermissionSpec` 的工具才会进入统一权限系统；没有配置的工具不会产生 `PermissionRequest`，但仍然受到参数校验、角色白名单和工具自身业务规则的限制。
# 工具在创建时定义的权限审查规则（权限声明）长什么样？

在 FirstCoder 中，我把工具的权限声明理解为一份本地审查配置，主要说明“执行什么类型的操作、检查什么目标，以及允许怎样授权”。它一共有八个字段：
`action` 指定操作类型，例如读取、写入或者执行 Shell；
`target_arg` 指定从哪个调用参数提取目标，例如从 `path` 提取文件路径；
`target_value` 用来配置固定目标；复杂工具则通过 `target_builder` 这个本地函数计算目标，例如解析补丁涉及的路径。这三种目标来源的优先级是 `target_builder`、`target_value`、`target_arg`。
此外，
`cwd_arg` 指定从哪个参数提取工作目录，
`reason` 描述申请权限的原因，
`allow_auto` 表示是否允许默认策略自动放行
`allow_always` 表示普通审批是否支持长期授权，后两个字段默认都是 `True`。这些声明不发送给模型，模型只生成工具名和参数，本地程序再根据声明构造权限请求，最终由权限系统决定允许、询问还是拒绝。

可能的追问：
1. 为什么需要三种不同的目标构造方式？
2. `allow_auto=True` 为什么不代表一定自动执行？
3. 权限声明中的 `reason` 会影响允许或拒绝的判断吗？
4. 模型没有提供 `target_arg` 指定的参数时怎么办？
5. 多个工具声明相同的 action，为什么仍可能得到不同的权限结果？
