`SessionRuntimeState` 可以理解为：

> 根据同一份 JSONL 事件日志恢复出来的“Agent 控制面状态”。它不描述聊了什么，而是记录任务是否切换、压缩是否失败、哪些工具结果已经被模型看过等运行信息。

它和 `SessionView` 的关系是：

```
同一份 JSONL
   ├── 重放成 SessionView
   │      关注：消息、Checkpoint 内容、任务计划
   │
   └── 重放成 SessionRuntimeState
          关注：任务边界、压缩控制、消费状态
```

恢复入口在 [replay.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\replay.py)，字段定义在 [runtime_state.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\runtime_state.py)。

# 一、会话标识

## 1. `session_id`

```
session_id: str
```

表示这份运行状态属于哪个 Session。

主要用途：

- 生成任务哈希时参与计算，避免不同 Session 产生相同任务标识。
- 提交运行状态时检查状态是否属于当前 Session。
- 将压缩、Checkpoint、工具消费事件写入正确的 JSONL。
- 防止把其他 Session 的运行状态错误提交进来。

提交状态时会校验：

```
if updated_state.session_id != self.session_id:
    raise ValueError(...)
```

对应代码：[session.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\runtime\\session.py)

它不会作为聊天内容发送给模型。

# 二、任务边界状态

下面四个字段共同组成一个“小型任务切换确认状态机”。

```
active_task_hash
candidate_task_hash
candidate_task_basis_message_id
task_hash_stable_count
```

## 2. `active_task_hash`

```
active_task_hash: str | None = None
```

表示当前已经确认的逻辑任务标识。

例如：

```
任务A：修复登录接口
        ↓
active_task_hash = task_aaa

用户后来开始：
任务B：实现缓存
        ↓
确认切换后
active_task_hash = task_bbb
```

需要注意：它不是直接对用户任务文本做哈希。

FirstCoder根据：

```
session_id
+ basis_message_id
+ 策略版本
```

生成稳定的任务标识：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\task_boundary\\service.py)。

### 在哪里使用？

主要用于上下文压缩。

消息 Part 会被标记上它所属的 `task_hash`。L1 压缩比较：

```
消息的 task_hash != active_task_hash
```

满足时说明它属于旧任务，可以优先裁剪：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\compaction\\layers\\l1_task_trim\\service.py)。

它还会：

- 传给子 Agent，标识父任务。
- 显示在 `/context` 状态中。
- 在确认任务切换后触发一次针对旧任务的压缩。

---

## 3. `candidate_task_hash`

```
candidate_task_hash: str | None = None
```

表示“疑似出现了一个新任务，但还没有正式确认”。

为什么不一检测到新任务就修改 `active_task_hash`？

因为模型可能误判。例如用户说：

```
顺便帮我看看这个变量名
```

这可能是当前任务的补充，也可能是新任务。立即切换可能导致旧上下文被错误压缩。

所以系统先进入候选状态：

```
active_task_hash    = task_A
candidate_task_hash = task_B
```

等后续观察稳定后，才把候选任务提升为当前任务。

使用位置在任务边界判断服务：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\task_boundary\\service.py)。

---

## 4. `candidate_task_basis_message_id`

```
candidate_task_basis_message_id: str | None = None
```

保存候选任务最初基于哪条用户消息产生。

例如：

```
msg_100：继续修复登录问题
msg_101：现在帮我实现 Redis 缓存
```

如果 `msg_101` 被判断为新任务：

```
candidate_task_hash = task_B
candidate_task_basis_message_id = msg_101
```

这个字段的作用是：

- 记住新任务真正开始的位置。
- 后续确认任务切换时，把从候选消息开始的相关消息标记为新任务。
- 避免只给“确认切换的后一条消息”打标签，而遗漏最初提出新任务的消息。

使用位置：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\domain\\task_boundary\\service.py)。

---

## 5. `task_hash_stable_count`

```
task_hash_stable_count: int = 0
```

表示同一个候选任务已经连续得到多少次有效确认。

典型过程是：

```
当前任务：task_A

第一次判断出现新任务：
candidate = task_B
stable_count = 1

下一次判断仍支持 task_B：
stable_count = 2

达到阈值：
active_task_hash = task_B
candidate_task_hash = None
stable_count = 0
触发旧任务压缩
```

默认稳定阈值通常是2，但特定策略可以要求一次观察就确认。

状态变化实现在 [runtime_state.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\runtime_state.py)。

如果模型判断是 `uncertain`，或者确认仍属于原任务，候选状态通常会被清空。

### 这四个字段的整体关系

```
active_task_hash
       │
       │ 检测到疑似新任务
       ▼
candidate_task_hash
candidate_task_basis_message_id
task_hash_stable_count = 1
       │
       │ 再次确认
       ▼
active_task_hash = candidate_task_hash
清空 candidate 和 count
       │
       ▼
触发旧任务上下文压缩
```

# 三、Checkpoint状态

## 6. `latest_checkpoint_id`

```
latest_checkpoint_id: str | None = None
```

记录最近一次成功创建的 Checkpoint ID。

它会在重放下面这些事件时恢复：

- `checkpoint_created`
- 成功的 `llm_compaction_completed`

对应代码：[replay.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\replay.py)。

### 和 `SessionView.checkpoints` 重复吗？

有一点信息重叠，但职责不同。

```
SessionView.checkpoints
    保存所有 Checkpoint 的完整数据
    包括摘要、tail 边界、策略版本等

runtime_state.latest_checkpoint_id
    只记录最近一次 Checkpoint 的 ID
    用于运行控制和状态展示
```

真正构建模型上下文时，主要使用的是 `SessionView.checkpoints`，因为它需要摘要和边界。

`latest_checkpoint_id` 更多用于：

- `/context` 状态展示。
- 记录最近一次压缩结果。
- 在完整 Checkpoint 数据暂时不可用时提供运行状态信息。

上下文检查器会优先取 `SessionView` 中的最新 Checkpoint，否则才回退到这个字段：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\inspect\\service.py)。

# 四、自动压缩熔断状态

下面三个字段组成自动压缩的熔断器。

```
auto_compact_failure_count
auto_compact_disabled_until
last_auto_compact_failure_reason
```

## 7. `auto_compact_failure_count`

```
auto_compact_failure_count: int = 0
```

记录自动压缩连续失败次数。

默认逻辑是：

```
第一次自动压缩失败：1
第二次自动压缩失败：2
第三次自动压缩失败：3
                     ↓
                  打开熔断器
```

默认失败上限是3次：[runtime_state.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\runtime_state.py)。

成功执行一次自动压缩后会清零：

```
auto_compact_failure_count = 0
```

手动压缩失败通常不会影响自动压缩失败计数，因为手动操作不应该把自动机制永久熔断。

---

## 8. `auto_compact_disabled_until`

```
auto_compact_disabled_until: str | None = None
```

表示自动压缩暂停到什么时间。

默认连续失败3次后：

```
auto_compact_disabled_until = 当前时间 + 30分钟
```

这段时间内再触发自动压缩，会直接返回：

```
status = skipped
reason = circuit_open
```

检查逻辑位于 [service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\compaction\\service.py)。

时间到期后，熔断器会自动关闭并清空该字段。

它只阻止自动压缩，不代表手动压缩、任务切换压缩和 `prompt_too_long` 恢复一定都会被禁止。

---

## 9. `last_auto_compact_failure_reason`

```
last_auto_compact_failure_reason: str | None = None
```

保存最近一次自动压缩失败原因。

例如：

```
l4_service_missing
summary_validation_failed
fixed_context_over_budget
provider_error
```

主要用于：

- `/context` 和压缩状态命令展示。
- 排查为什么自动压缩被禁用。
- 区分“没有触发压缩”和“触发了但执行失败”。

自动压缩成功后，失败原因和失败次数会一起清空：[runtime_state.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\domain\\runtime_state.py)。

# 五、上下文一致性与去重

## 10. `system_prompt_fingerprint`

```
system_prompt_fingerprint: str | None = None
```

这是当前系统提示词的内容指纹。

系统提示词可能由很多部分组成：

- 基础规则
- `AGENTS.md`
- Skill目录
- Provider能力
- 权限策略
- 运行模式
- Benchmark任务

把这些输入构建成系统提示词后，会生成指纹并写入运行状态：[prompts.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\runtime\\prompts.py)。

主要用途：

- 判断当前使用的是哪一版系统提示词。
- 辅助 Prompt前缀缓存。
- 在 `/context` 中进行调试。
- 当模型、权限或项目指令改变时，帮助识别上下文环境已经变化。

它不是完整提示词，只是类似：

```
当前系统提示词版本的摘要身份证
```

---

## 11. `last_compaction_input_fingerprint`

```
last_compaction_input_fingerprint: str | None = None
```

记录最近一次已经处理过的压缩输入指纹。

L4 准备总结时会重新计算当前压缩源的指纹：

```
当前 source fingerprint
        ==
last_compaction_input_fingerprint
```

如果相等，说明同一段上下文已经处理过，不需要再次调用模型总结，返回 `duplicate_source`：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\compaction\\layers\\l4_semantic_summary\\service.py)。

它还用于：

- 防止相同历史被重复生成 Checkpoint。
- 恢复后知道最近处理过哪份上下文。
- `/context` 中显示最近一次压缩输入。

---

## 12. `last_no_effect_compaction_fingerprint`

```
last_no_effect_compaction_fingerprint: str | None = None
```

记录“上次尝试压缩，但没有任何内容可以继续压缩”的上下文指纹。

例如：

```
上下文触发自动压缩
        ↓
L1、L2、L3 都没有可处理内容
        ↓
记录当前 fingerprint
```

如果下一次上下文完全没变化，指纹仍然相同，系统就直接跳过，不再重复运行整套压缩流程：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\compaction\\service.py)。

它和上一个字段的区别是：

|字段|表示什么|
|---|---|
|`last_compaction_input_fingerprint`|这份输入已经被实际压缩或总结过|
|`last_no_effect_compaction_fingerprint`|这份输入尝试过，但压缩没有产生效果|

# 六、工具结果消费状态

## 13. `consumed_tool_result_part_ids`

```
consumed_tool_result_part_ids: set[str] = field(default_factory=set)
```

保存已经被投影进模型请求、可以认为模型已经看过的工具结果 Part ID。

这里的“consumed”不是说工具已经执行，而是：

> 工具结果已经进入过 Provider上下文，不再是模型尚未看到的新结果。

流程是：

```
工具执行完成
    ↓
生成 tool_result Part
    ↓
构建下一次模型请求
    ↓
该结果进入 Provider Projection
    ↓
写入 provider_projection_consumed 事件
    ↓
Part ID 加入 consumed_tool_result_part_ids
```

写入逻辑位于 [messages.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\session\\application\\runtime\\messages.py)。

### 为什么重要？

因为系统不能过早压缩模型还没看过的工具结果。

假设：

```
工具刚返回文件内容
        ↓
还没发送给模型
        ↓
压缩系统把结果归档了
```

模型可能第一次看到的就是一个归档占位符，丢失完成当前推理所需的信息。

所以 L3 归档要求：

```
part.id 必须位于 consumed_tool_result_part_ids 中
```

否则不允许归档：[service.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\context\\application\\compaction\\layers\\l3_tool_archive\\service.py)。

L4 创建 Checkpoint 时也不能跨过尚未消费的工具事务。

使用 `set` 是因为：

- 查询是否消费需要高效。
- 同一个工具结果可能被多次投影，但只需要记录一次。
- 从多个事件恢复时直接做集合并集。

# 一条完整链路

把这些字段串起来，可以看到它们是怎么协作的：

```
用户发送新消息
    ↓
系统判断任务边界
    ↓
更新 active/candidate task hash
    ↓
确认任务切换
    ↓
使用 active_task_hash 识别旧任务内容
    ↓
构建模型上下文
    ↓
用 consumed_tool_result_part_ids 保护未消费工具结果
    ↓
进行 L1/L2/L3/L4 压缩
    ↓
成功：
  更新 latest_checkpoint_id
  更新 last_compaction_input_fingerprint
  清空自动压缩失败状态

失败：
  failure_count + 1
  记录 failure_reason
  达到3次后暂停自动压缩30分钟
    ↓
把结果加入 recent_compaction_events
```

# 两个需要特别注意的源码边界

第一，`SessionRuntimeState` 虽然叫“可恢复运行状态”，但不是每个字段都原样从 JSONL 恢复：

- `system_prompt_fingerprint` 没有在运行状态重放器中恢复，而是在下一次构建系统提示词时重新计算。
- `candidate_task_basis_message_id` 会写入任务边界事件，但当前重放代码只恢复了候选哈希和稳定次数，没有恢复这个消息 ID。这是当前实现中一个值得关注的恢复缺口。

第二，运行状态不是独立文件。新 Session 使用默认值；恢复 Session 时，仍然读取原来的 JSONL，只是使用与 `SessionView` 不同的事件归并规则。

一句话总结：

> `SessionView` 回答“当前会话里有什么内容”，`SessionRuntimeState` 回答“Agent现在处于什么控制状态，以及接下来应该怎么运行”。
