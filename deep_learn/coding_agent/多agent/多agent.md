# 介绍一下多agent怎么做的

FirstCoder 的多 Agent 本质上是一个“父 Agent 通过工具委托子 Agent”的主从结构，并不是多个 Agent 共享上下文、自由聊天的群体协作系统。父 Agent 仍然是唯一的决策者，它负责理解用户需求、拆分任务和汇总结果；当它认为某项工作适合独立处理时，就调用 `delegate` 工具，指定子 Agent 的角色、具体任务、父任务摘要和可能涉及的文件路径。整体链路是：

```
父 Agent
  ↓ 调用 delegate
创建全新的子 Session
  ↓
启动一个新的 AgentLoop
  ↓
子 Agent 独立调用模型和工具
  ↓
返回总结、证据、修改文件和风险
  ↓
包装成 delegate 的工具结果
  ↓
父 Agent 继续判断和执行
```

`delegate` 是一个提供给父模型的普通工具，入口在 [delegate.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\tools\\infrastructure\\delegation\\delegate.py)。父模型可以选择四种角色：`researcher` 负责只读地搜索和理解代码；`reviewer` 负责审查调用链、代码差异和风险；`tester` 可以在只读工具之外使用 Shell 和 Python 做验证；`coder` 还可以使用写文件、编辑、删除和补丁工具完成代码修改。不同角色不是使用不同的 Agent 类（FirstCoder 的父子 Agent 共用同一套 AgentLoop 实现，但每个 Agent 都拥有独立的 AgentLoop 实例和 Session；角色差异由提示词、工具白名单、执行预算和隔离策略决定。），而是使用同一个 AgentLoop（不是同一个实例，而是根据这个agentloop类，给不同的参数，创建不同的对象），通过不同的角色提示词、工具白名单和运行预算表现出不同能力，这些配置定义在 [contracts.py](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\delegation\\contracts.py)。

父 Agent 发起委托后，[SubagentRunner](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\delegation\\application\\subagent.py) 会创建一个全新的子 Session。这个子 Session 不会复制父会话的完整消息历史，只记录父 Session ID、父任务哈希、子 Agent 角色和委托任务等关联信息。子 Agent 真正能看到的是父 Agent显式传入的任务、摘要、路径提示，再加上项目的 AGENTS.md、系统规则和自己允许使用的工具。这种方式可以避免把父 Agent 已经积累的大量上下文全部复制给子 Agent，也能降低无关信息对它的干扰。

子 Session 创建完成后，会通过 [AgentLoopChildExecutor](E:\\agent\\后端agent开发资料\\FirstCoder\\firstcoder\\agent\\adapters\\delegation.py) 再启动一个普通 AgentLoop。也就是说，子 Agent 不是一个简单的单次模型调用，它内部也可以经历“模型推理—调用工具—读取结果—继续推理”的完整循环。但它没有后台任务管理器，也不会注册 `delegate` 工具，因此不能继续创建孙 Agent，避免无限递归委托。子 Agent 如果执行到需要用户交互的权限确认，也无法直接询问用户，而是作为本次委托失败返回给父 Agent。

委托支持前台和后台两种方式。前台委托时，父 Agent 会等待子 Agent 完整执行结束，然后拿到最终总结，再继续自己的工具循环。后台委托时，使用的就是前面讲过的通用后台工具机制：父 Agent 立即获得后台任务 ID，子 Agent 在后台线程中执行，完成后再通过 `<task_notification>` 通知父 Agent。因此多个 researcher、reviewer 或 tester 可以作为多个后台任务并发运行，但它们之间没有直接通信，结果最终都由父 Agent收集和整合。

`coder` 角色的后台执行更特殊，因为它具有修改文件的能力。如果让后台 coder 直接操作父工作区，可能和父 Agent 或其他 coder 同时修改相同文件。因此 FirstCoder 要求后台 coder 必须运行在独立的 Git Worktree 中，每个 coder 使用单独的目录和分支，并重新创建以该 Worktree 为根目录的工具和权限管理器。子 Agent 完成后，系统只把修改文件列表、分支、Worktree 路径和 diff 摘要返回给父 Agent，不会自动合并到父工作区。这样父 Agent可以先审查结果，再决定如何处理；如果当前目录不是 Git 仓库，后台 coder 会被直接拒绝。前台 coder 则可以直接在父工作区执行，仍然接受正常的权限控制。

每类子 Agent 还有独立的调用次数和时间上限。例如 reviewer 的预算比较小，coder 和 tester 的预算更大，用来避免一次委托无限消耗模型调用和工具轮次。子 Agent 最终需要返回简洁报告，包括工作结论、证据、修改文件和潜在风险；父 Agent只接收这份结果，不会自动继承子 Agent 的完整思考过程和会话历史。

因此，FirstCoder 的多 Agent 可以概括为：父 Agent通过 `delegate` 工具按角色创建拥有独立 Session 和独立上下文的子 Agent，子 Agent使用受限工具完成一项明确任务，再把结构化结果返回父 Agent；多个子 Agent可以借助后台任务并发执行，具有写能力的后台 coder 则通过 Git Worktree 隔离修改。它属于受控的层级式任务委托，而不是完全自治、共享记忆的多 Agent 网络。



# 分别介绍一下四个子agent

FirstCoder 提供了 researcher、reviewer、tester 和 coder 四种子 Agent。它们底层使用同一套 AgentLoop，但拥有独立 Session、角色提示词、工具白名单和执行预算。父 Agent根据任务性质选择角色，子 Agent完成任务后只把总结和证据作为 `delegate` 工具结果返回。

| 子 Agent    | 主要职责             | 工具白名单                                                                                                                    | 特点                                                            |
| ---------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| researcher | 阅读代码、定位实现、收集证据   | `ls`、`view`、`grep`、`glob`、`tree`、`read_multi`、`git_status`、`git_diff`、`git_log`、`diagnostics`、`think`、`retrieve_archive` | 工具范围较广但全部只读，适合探索项目和梳理调用链，不能修改文件或执行任意命令                        |
| reviewer   | 审查代码差异、调用关系和潜在风险 | `view`、`grep`、`read_multi`、`git_status`、`git_diff`、`git_log`、`think`、`retrieve_archive`                                  | 比 researcher 更聚焦，主要围绕已有文件和 Git 差异进行审查，不负责实现修改                 |
| tester     | 执行测试、诊断问题、验证结果   | researcher 的全部只读工具，再加 `shell`、`python_exec`                                                                              | 可以运行测试命令和验证脚本，但没有文件修改工具，避免在验证过程中顺手改变被测代码                      |
| coder      | 实现功能和修复代码        | tester 的全部工具，再加 `write`、`edit`、`delete`、`apply_patch`                                                                    | 能读取、执行和修改项目，能力最完整；后台运行时必须使用独立 Git Worktree，避免与父 Agent同时修改父工作区 |

researcher 适合父 Agent不知道实现位置时进行大范围探索；reviewer 适合代码已经修改完成后，从调用链、差异和风险角度做独立审查；tester 适合运行测试、复现问题和收集验证证据；coder 适合把明确的实现任务交给子 Agent完成。四个角色都可以由父 Agent选择前台等待或者后台执行，不过后台 coder 必须运行在 Git Worktree 中，完成后只返回独立分支、修改文件和 diff 摘要，不会自动把代码合并回父工作区。

它们的执行预算也不同：reviewer 最小，因为审查任务通常比较聚焦；researcher 需要更大的搜索空间；tester 可能需要多轮运行和分析测试；coder 的工具轮次、模型调用次数和执行时间上限最大。无论是哪种角色，都不能继续调用 `delegate` 创建孙 Agent，也不能与其他子 Agent直接通信，最终结果统一交给父 Agent整合。

这套设计的核心是通过角色和最小工具权限限制子 Agent的行为边界：需要搜索就使用只读 researcher，需要审查就使用更聚焦的 reviewer，需要执行验证就使用 tester，只有确实需要修改代码时才使用 coder，从而降低误操作、上下文污染和并发修改风险。

可能的追问包括：
为什么 reviewer 的工具比 researcher 少；
tester 为什么不能修改代码；
后台 coder 为什么必须使用 Git Worktree；
四种角色为什么复用同一个 AgentLoop；
子 Agent的最终结果如何返回父 Agent；
为什么禁止子 Agent继续委托；
如何选择前台委托还是后台委托。

# tester 为什么不能修改代码；
FirstCoder 不让 tester 直接修改业务代码，主要是为了做角色隔离。tester 的职责是运行测试、复现问题、收集日志并判断实现是否符合预期，而不是顺手修复问题。这样可以避免 tester 为了让测试通过而同时修改实现，保证测试结论相对独立、可信。工具权限上，tester 可以读取代码，并使用 Shell、Python 执行测试和诊断，但没有 `write`、`edit`、`delete`、`apply_patch` 这些专门修改文件的工具；需要修改代码时，应把测试证据返回给父 Agent，再由 coder 负责实现。不过这里要说严谨一点：这属于工具层面的职责限制，并不是绝对的文件系统只读，因为 Shell 或测试命令仍可能生成缓存、覆盖率报告，理论上也可能执行修改文件的命令。因此更完善的实现还应该配合只读沙箱或命令级权限控制，真正从运行环境上限制 tester 修改源码。

可能的追问点：

1. tester 和 reviewer 的职责有什么区别？
2. tester 为什么需要 Shell 和 Python 工具？
3. Shell 可以修改文件，如何保证 tester 真正只读？
4. tester 发现问题后，怎样把结果交给 coder？
5. 为什么不让 tester 发现问题后直接修复？
6. tester 是否适合后台执行？
7. tester 执行测试产生的临时文件应该怎么处理？

# tester 发现问题后，怎样把结果交给 coder？
FirstCoder 中 tester 和 coder 不能直接通信，结果需要由父 Agent 中转。tester 完成测试后，会在最终报告中返回问题描述、复现步骤、测试输出、涉及文件和风险等信息；这些内容作为本次 `delegate` 工具的结果进入父 Agent 的 Session。父 Agent 再次调用模型时能够看到这份结果，然后决定是否创建一个 coder 子 Agent，并把 tester 提供的关键证据整理到新的委托任务中，例如失败现象、相关文件路径和预期行为。coder 会在新的独立 Session 中根据这些信息完成修复，修复后再把结果返回父 Agent；父 Agent还可以再次委托 tester 做回归验证。因此它的协作链路是：`tester → 父 Agent → coder → 父 Agent → tester 回归验证`。这种方式避免子 Agent 之间随意传递上下文，也让父 Agent 负责统一调度和判断。需要注意的是，系统不会自动把 tester 的完整 Session 复制给 coder，父 Agent 必须在新委托中传递必要信息；如果摘要遗漏了关键日志，coder 就可能缺少上下文。

可能的追问点：

1. 为什么不允许 tester 直接向 coder 发送消息？
2. 父 Agent 会把 tester 的完整上下文交给 coder 吗？
3. tester 的报告应该包含哪些信息？
4. coder 修复后是否必须再让 tester 验证？
5. tester 在后台运行时，结果怎样通知父 Agent？
6. 如果父 Agent 转述时遗漏关键信息怎么办？
7. coder 修复失败后，整个链路如何继续？

# 如果父 Agent 转述时遗漏关键信息怎么办？

如果父 Agent 在重新委托 coder 时遗漏了关键信息，当前 FirstCoder 没有自动检测或补全机制。新 coder 只会看到父 Agent传入的任务描述、摘要和路径提示，不会自动读取 tester 的完整子 Session。因此，它可能重新排查问题、做出错误判断，或者因为证据不足而返回无法完成。为了降低这种上下文损失，父 Agent应该采用结构化交接，至少传递失败的测试命令、预期结果与实际结果、关键报错、相关文件路径、原修改内容，以及后台任务对应的 Worktree 和 diff。新 coder也可以自己重新运行测试、检查当前代码来补充信息。如果仍然无法确认，就把缺失信息返回父 Agent，由父 Agent重新查看 tester 结果并发起新的委托。从架构改进上，可以让 `delegate` 支持引用 tester 的 `child_session_id`、测试产物或结构化报告，避免完全依赖父模型用自然语言转述。

一句话概括：
> 当前系统通过父 Agent摘要实现子 Agent间的信息传递，遗漏后只能重新调查或重新委托；更可靠的方案是结构化交接，并允许新子 Agent按权限读取旧子 Session的证据。
# tester 发现问题后，能否重新启动之前的 coder？

当前 FirstCoder **不能通过 `delegate` 恢复之前的 coder 子 Agent**。tester 将测试问题返回父 Agent 后，父 Agent只能再次调用 `delegate`，创建一个新的 coder 和新的子 Session，并把原 coder 的修改摘要、tester 的失败日志、相关文件和预期结果传给新 coder。

完整链路是：

```
coder 完成修改
→ 父 Agent收到结果
→ tester 验证并发现问题
→ 测试结果返回父 Agent
→ 父 Agent创建新的 coder
→ 新 coder继续修复
→ 再次交给 tester验证
```

如果原 coder 是前台执行，它修改的是父工作区，新 coder可以直接看到这些代码；如果原 coder 是后台执行，修改位于独立 Worktree，新 coder不会自动进入原 Worktree，需要父 Agent根据返回的路径和 diff 决定如何继续处理。

# 既然子 Agent有 JSONL，为什么不能恢复？

子 Agent的 JSONL **在技术上能够用于恢复 Session**。项目底层已经支持根据 JSONL 重建 `SessionView` 和 `SessionRuntimeState`，然后重新创建工具注册表、权限管理器和事件写入器等运行时对象。

但当前限制出现在委托层：每次调用 `delegate` 都会生成新的 `session_id`，其参数中没有 `child_session_id` 或 `resume_session_id`，因此父 Agent无法要求系统恢复某个旧的子 Session。

所以两者并不矛盾：

> FirstCoder 底层具备恢复 Session 的能力，但当前 `delegate` 没有接入恢复旧子 Agent的入口。

另外，JSONL 恢复的是持久化数据，不能恢复已经结束的线程、协程或后台任务。真正恢复子 Agent时，还需要重新创建 AgentLoop、工具和权限环境；如果是后台 coder，还要重新绑定并验证原来的 Git Worktree。






# 四种子agent，可使用的工具上限？
“每种子 Agent 最多能看到多少种工具”，当前白名单上限如下：

|子 Agent|工具种类上限|最大工具轮次|
|---|---|---|
|researcher|12 种|16 轮|
|reviewer|8 种|10 轮|
|tester|14 种|30 轮|
|coder|18 种|40 轮|

这里的“工具种类上限”是角色白名单的最大值，实际数量可能更少，因为子 Agent只能从父 Agent当前已经注册的工具中进行筛选。

“最大工具轮次”也不等于最大工具调用次数。模型一次回答可以产生多个工具调用，这些调用整体算一轮，因此项目没有严格规定子 Agent最多只能调用多少次工具，而是通过工具轮数、模型请求次数和总运行时间共同限制：

|子 Agent|最大模型请求|最大运行时间|
|---|---|---|
|researcher|32 次|480 秒|
|reviewer|20 次|300 秒|
|tester|60 次|900 秒|
|coder|80 次|1200 秒|

所以准确地说，researcher 最多有 12 种工具权限，reviewer 8 种，tester 14 种，coder 18 种；执行量限制的是工具轮次，而不是单个工具调用的绝对次数。
# 子 Agent的最终结果如何返回父 Agent；
子 Agent执行结束后，不会把自己的完整 Session 和全部工具调用历史复制给父 Agent，而是只把最终回答逐层包装成 `delegate` 的工具结果返回。

具体流程是：

```
子 AgentLoop 完成执行
    ↓
得到子 Agent 的最终模型回答
    ↓
提取回答正文
    ↓
包装成 SubagentResult
    ↓
再包装成 delegate 的 ToolResult
    ↓
写入父 Session
    ↓
父 Agent 下一次调用模型时看到该结果
```

子 AgentLoop 最终会产生一个 `AgentTurnResult`，其中包含子模型的最终回答。子 Agent执行适配器从中提取回答正文，形成 `ChildExecutionResult`。随后 `SubagentRunner` 将它包装成 `SubagentResult`，其中主要包含：

```
是否成功
子 Agent 角色
子 Session ID
最终总结
错误信息
修改文件
Worktree 路径和分支
diff 摘要
```

普通 researcher、reviewer 或 tester 主要返回子 Agent的文本总结和子 Session ID。隔离执行的后台 coder 还会额外返回 Worktree 路径、独立分支、修改文件列表和 diff 摘要，并且不会自动把修改合并到父工作区。

如果是前台委托，`SubagentResult` 会立即被包装成一次正常的 `delegate` 工具结果，父 Agent等待这个结果，然后继续调用模型：

```
assistant：调用 delegate
tool：Subagent xxx completed + 子 Agent总结
assistant：父 Agent分析和整合结果
```

如果子 Agent执行失败，也不会直接让父 AgentLoop崩溃，而是返回一个失败的 `delegate` 工具结果，其中包含失败原因和子 Session ID，父模型可以决定重试、改用其他角色或者自己处理。

如果是后台委托，第一次返回给父 Agent的是“后台任务已经启动”的占位工具结果，其中只有后台任务 ID。子 Agent完成后，真实的 `delegate` 工具结果会保存在后台任务中，并在后续请求前转换成 `<task_notification>`：

```
<task_notification>
  <job_id>bg_0001</job_id>
  <tool_name>delegate</tool_name>
  <status>completed</status>
  <summary>子 Agent 的最终结果</summary>
</task_notification>
```

它作为一条独立的后台通知进入父 Session，而不会作为原 `delegate` 调用的第二个工具结果。

所以可以概括为：前台子 Agent通过 `delegate` 的正常 `ToolResult` 返回最终总结，后台子 Agent先返回任务 ID，完成后通过任务通知返回结果；无论哪种方式，父 Agent只接收最终报告，不会自动继承子 Agent的完整上下文。
# 为什么禁止子 Agent继续委托；

禁止子 Agent继续委托，主要是为了把多 Agent 的结构限制成一层清晰的父子关系，由父 Agent统一负责拆分任务、控制资源和整合结果。

如果允许子 Agent继续创建孙 Agent，就可能形成不断扩张的委托树：

```
父 Agent
├── 子 Agent A
│   ├── 孙 Agent A1
│   └── 孙 Agent A2
└── 子 Agent B
    └── 孙 Agent B1
```

这样会带来几个问题。首先是资源失控，每个 Agent 都可能继续调用模型和工具，Agent 数量、Token、线程和执行时间可能快速增长。其次是任务责任不清，孙 Agent的结果要先返回子 Agent，再返回父 Agent，中间任何一层失败、超时或者丢失信息，父 Agent都很难判断真实状态。再次是权限和副作用更难管理，例如后台 coder 已经运行在独立 Worktree 中，如果它再创建一个 coder，就要继续决定是否创建嵌套 Worktree、修改落在哪个分支、结果由谁审查和合并。取消任务也会变复杂，取消父任务时还必须递归取消整棵子任务树。

因此 FirstCoder 创建子 AgentLoop 时，会同时采取两层限制：不给子 Agent提供 `delegate` 工具，并设置 `enable_delegate_tool=False`。子 Agent只能完成父 Agent交给自己的具体任务，不能继续拆分出新的 Agent。需要更多并行任务时，子 Agent把结果返回父 Agent，由父 Agent决定是否再创建其他一级子 Agent。

所以这个设计牺牲了一部分递归协作能力，换来了可控的调用成本、清晰的任务所有权、简单的取消链路和可审查的执行结果。可以概括为：父 Agent是唯一的调度中心，子 Agent只负责执行，不再承担组织其他 Agent的职责。


# 如何选择前台委托还是后台委托。

选择前台委托还是后台委托，核心看子 Agent的结果是否处在父 Agent当前执行链路的关键路径上。如果父 Agent下一步必须依赖子 Agent的结论，例如需要 researcher 先定位实现位置，或者需要 reviewer 审查完当前修改才能决定是否继续，那么应该使用前台委托，父 Agent等待子 Agent结束，拿到真实结果后再继续推理。如果子任务耗时较长、相对独立，而且父 Agent等待期间还有其他工作可以做，例如并行搜索多个模块、运行完整测试或者让多个 reviewer 分别审查不同方向，就适合使用后台委托；父 Agent会先拿到任务 ID并继续执行，子 Agent完成后再通过任务通知返回结果。还要考虑副作用：researcher、reviewer 和 tester 主要负责只读分析或验证，通常更适合后台执行；coder 会修改文件，如果需要直接修改父工作区并让父 Agent马上继续处理，应该使用前台 coder，如果要让 coder 在后台运行，则必须放进独立 Git Worktree，完成后由父 Agent审查 diff，并且不会自动合并。因此可以概括为：强依赖、需要立即使用结果的任务走前台；独立、耗时、可以与主任务并行推进的任务走后台；涉及代码修改的后台任务还必须增加工作区隔离。

可能的追问包括：
前台委托为什么会阻塞父 Agent；
后台子 Agent的结果如何返回；
多个后台子 Agent如何并发执行；
后台 coder 为什么不能直接修改父工作区；
后台任务失败后父 Agent如何处理；
什么情况下不适合使用子 Agent；
如何避免委托成本超过并行带来的收益。

# 后台 coder 为什么必须使用 Git Worktree；

后台 coder 必须使用 Git Worktree，是因为它具备写文件、编辑和删除代码的能力，而后台执行时父 Agent不会等待它结束，还可能继续修改同一个项目，甚至同时启动其他 coder。如果它们直接共享父工作区，就可能同时修改同一文件、覆盖用户未提交的改动，或者让父 Agent在代码只修改了一半时读取并测试，普通文件锁也无法解决这种代码语义上的冲突。Git Worktree 可以基于当前仓库创建独立目录和独立分支，后台 coder 的文件工具、Shell 工作目录、沙箱和权限范围都会重新绑定到这个目录，因此它的修改不会直接影响父工作区。执行结束后，FirstCoder 只把 Worktree 路径、分支名称、修改文件和 diff 摘要返回给父 Agent，不会自动合并，父 Agent可以先审查，再决定是否应用这些修改。如果当前项目不是 Git 仓库，系统就会拒绝启动后台 coder。相比之下，前台 coder 执行期间父 Agent会等待，因此可以在正常权限控制下直接操作父工作区。这个设计的核心是：后台并发负责提高效率，Worktree 负责隔离副作用，显式审查和合并负责保证最终代码安全。

可能的追问包括：Git Worktree 和复制项目目录有什么区别；Worktree 是否拥有独立的 Git 仓库；后台 coder 完成后如何合并修改；两个 Worktree 修改同一文件怎么办；为什么普通文件锁不能解决代码冲突；Worktree 中未提交的修改如何处理；前台 coder 为什么不强制使用 Worktree。



# 四个子agent有明确的前后台划分吗？比如coder agent、test agent一定是后天，而research agent 一定是前台？  还是说具体情况具体分析，由模型决定的？
四个子 Agent 没有固定的前后台划分。不是 coder、tester 一定后台，也不是 researcher 一定前台，而是父模型在调用 `delegate` 时根据任务情况决定是否添加 `run_in_background=true`，运行时再检查这个选择是否合法。

当前四种角色都允许前台执行，也都具备后台执行能力：

```
researcher：前台或后台
reviewer：前台或后台
tester：前台或后台
coder：前台或后台，但后台必须有 Git Worktree
```

父模型主要根据依赖关系选择。如果下一步必须马上使用子 Agent的结果，就采用前台委托，例如先让 researcher 找到关键代码，再根据结果决定怎么修改；如果任务比较耗时、相对独立，而且父 Agent还能继续做其他事情，就采用后台委托，例如后台运行完整测试，同时父 Agent继续检查代码。

coder 的限制更严格：前台 coder 可以在权限控制下直接修改父工作区；后台 coder 因为会与父 Agent并发运行，必须进入独立 Git Worktree。如果当前项目不是 Git 仓库或者无法创建 Worktree，后台 coder 会被拒绝，但仍然可以改成前台执行。

所以准确地说：

> 前台还是后台主要由父模型结合任务依赖和执行成本决定，但最终受到运行时能力、后台工具白名单和 coder Worktree 隔离规则的约束，并不是模型想怎么执行都可以。



# 大多数情况下，四个子agent分别会在前台还是后台？

从代码默认行为看，四种子 Agent 都是前台执行，只有父模型显式传入 `run_in_background=true` 才会转为后台。项目本身没有统计数据证明哪种角色实际更常以前台或后台运行，但按典型使用方式来说，researcher 比较灵活：如果父 Agent下一步必须依赖搜索结论，通常前台执行；如果是在多个模块中并行收集资料，更适合后台。reviewer 通常更偏向后台，因为代码审查相对独立，父 Agent可以同时做其他工作，但最终提交前必须依赖审查结论时也可以前台等待。tester 取决于测试耗时，少量定向测试通常前台执行，完整测试套件、集成测试等耗时验证通常后台执行。coder 则更偏向前台，因为前台 coder 可以直接修改父工作区，父 Agent拿到结果后能立即继续；后台 coder 需要创建独立 Git Worktree，完成后还要审查和整合 diff，更适合边界清晰、能够独立实现的子任务。

可以简单记成：researcher 前后台都常见，reviewer 偏后台，tester 小测试前台、大测试后台，coder 通常前台、独立实现任务才后台。最终判断标准不是角色名称，而是父 Agent下一步是否依赖它的结果，以及任务能否安全地独立运行。
# 怎么解决这些子agent上下文污染的问题
FirstCoder 解决子 Agent 上下文污染的核心思路，不是在一份共享上下文里做过滤，而是直接让每个子 Agent 使用全新的 Session 和独立的 AgentLoop 实例。父 Agent调用 `delegate` 后，系统不会把父会话的全部用户消息、模型回答、工具调用和压缩历史复制给子 Agent，而是只传递明确的委托信息，包括任务描述、父 Agent主动整理的摘要、路径提示、角色说明和项目根目录。子 Agent拥有自己的 JSONL 会话日志、SessionView、上下文压缩状态和工具调用历史，因此 researcher 的搜索过程不会进入 tester 的上下文，多个子 Agent 之间也不会互相继承消息。

子 Agent 的上下文大致是这样构建的：

```
子 Agent 自己的系统提示
+ 项目的 AGENTS.md
+ 当前角色及职责
+ 父 Agent 提供的摘要
+ 路径提示
+ 明确的委托任务
+ 子 Agent 自己后续产生的消息和工具结果
```

而不是：

```
父 Agent 的完整历史
+ 其他子 Agent 的完整历史
+ 当前委托任务
```

角色限制也在降低污染。researcher 只获得代码搜索和读取工具，reviewer 只关注审查，tester 才能运行验证命令，coder 才能修改文件。子 Agent还拿不到 `delegate` 工具，不能继续创建孙 Agent。这样可以让每个子 Agent围绕一个明确目标工作，避免无关工具、无关任务和递归委托不断扩大上下文。

子 Agent完成后，它的完整执行历史仍然保留在自己的子 Session 中，不会自动合并回父 Session。父 Agent只会收到子 Agent最终输出的总结，它被包装成一次 `delegate` 工具结果。也就是说，父 Agent看到的是结论、证据、修改文件和风险，而不是子 Agent每一轮推理和所有工具输出。这相当于在父子 Agent之间建立了一个受控的上下文接口：

```
父 Agent → 精简任务说明 → 子 Agent
子 Agent → 最终结果摘要 → 父 Agent
```

还需要区分“模型上下文污染”和“工作区状态相互影响”。独立 Session 解决的是消息、记忆和工具历史污染；如果子 Agent直接读取同一个项目目录，它仍然能看到父 Agent已经修改的文件，这是共享环境，不属于模型上下文共享。对于能够修改代码的后台 coder，FirstCoder 进一步创建独立 Git Worktree，让它连文件环境也和父 Agent隔离，完成后只返回分支、Worktree 路径和 diff 摘要，不自动合并修改。

不过当前实现只是降低污染，并不能完全消除污染。因为子 Agent仍然继承项目的 AGENTS.md，而且父 Agent传入的 `parent_summary` 如果包含错误、无关信息或者误导性判断，子 Agent仍可能受到影响；子 Agent最终报告主要依靠提示词要求保持简洁，并没有非常严格的结构化结果校验。因此更准确地说，FirstCoder 通过“独立 Session、最小化上下文传递、角色工具白名单、禁止嵌套委托、只返回最终摘要和可写 Agent 的 Worktree 隔离”来控制上下文污染，而不是让所有 Agent共享同一份会话后再做清理。


# 子agent和普通的工具执行过程是一样的是吗？
对，从父 Agent 的视角看，`delegate` 和普通工具的执行过程基本一样：模型生成工具调用，工具执行层进行参数校验和权限检查，然后调用工具执行器，最后把 `ToolResult` 写入 Session，再请求模型继续处理。区别只是普通工具的执行器通常直接读文件、运行命令或者修改代码，而 `delegate` 的执行器内部会创建一个新的子 Session 和子 AgentLoop，让子 Agent完成一整轮“模型调用—工具执行”循环，最后把子 Agent的总结包装成 `delegate` 的工具结果返回父 Agent。

可以理解成两层嵌套：

```
父 AgentLoop
    ↓ 调用普通工具 delegate
delegate 工具执行器
    ↓ 启动
子 AgentLoop
    ↓ 多轮调用模型和工具
返回子 Agent最终总结
    ↓
包装成 delegate 的 ToolResult
    ↓
父 AgentLoop 继续
```

如果是前台调用，父 Agent会像等待普通工具一样等待 `delegate` 返回；如果设置了 `run_in_background=true`，它也和其他后台工具一样，由通用后台任务机制提交线程池，先返回任务 ID，子 Agent完成后再发送后台通知。所以父层的工具协议和执行框架是一样的，特殊之处只在于 `delegate` 工具内部执行的不是一个简单函数，而是另一个完整的 AgentLoop。





# 进程和线程的区别


进程是操作系统进行资源分配和隔离的基本单位，每个进程通常拥有独立的虚拟地址空间、文件描述符和运行环境；线程则是进程内部的执行单元，同一个进程中的线程共享内存、代码和大部分资源，但每个线程拥有自己的调用栈、寄存器和执行位置。因为线程共享数据，所以创建和切换成本通常比进程低，线程之间传递数据也更方便，但同时需要使用锁来避免数据竞争，一个线程发生严重错误也可能影响整个进程。进程之间隔离性更强，一个进程崩溃通常不会直接破坏其他进程，但进程创建、上下文切换和进程间通信的成本更高。在 Python 的 CPython 实现中，还需要考虑 GIL：多个线程适合网络请求、文件读写、Shell 等 I/O 密集型任务，因为线程等待 I/O 时可以让其他线程运行；对于大量 Python 计算的 CPU 密集型任务，多线程通常不能充分利用多核，更适合使用多进程。FirstCoder 的后台工具主要是文件、网络、命令和子 Agent调用，因此选择线程池能够以较低成本共享后台任务管理器和执行环境；如果未来要执行高强度计算、需要强制终止任务或者希望获得更强的故障隔离，就更适合改用独立进程或外部 Worker。

可能的追问包括：
什么是 GIL；
线程为什么需要加锁；
进程间如何通信；
协程和线程有什么区别；
线程池与进程池如何选择；
为什么 Python 线程仍然适合 I/O 密集型任务；
一个线程崩溃是否一定会导致整个进程退出。

# 进程，线程，协程梳理


进程、线程和协程处在不同层级。进程是操作系统分配资源和进行隔离的基本单位，例如在两个终端分别启动 FirstCoder，就会得到两个独立进程，它们各自拥有独立的内存，不能直接共享普通变量。线程是进程内部真正执行代码的单元，一个进程可以拥有多个线程，这些线程共享进程的内存和文件资源，但各自拥有独立的调用栈；因此线程之间传递数据比较方便，但同时修改共享数据时需要加锁。协程则是运行在线程上的轻量级任务，它不是操作系统线程，而是由事件循环调度；协程执行到 `await` 时，可以保存当前位置并主动暂停，把线程让给其他协程，等待的操作完成后再从原位置恢复。同一个线程在某一时刻只能执行一个协程，但可以通过快速、主动地切换管理很多协程。与线程切换相比，协程切换不需要操作系统进行完整的线程调度，所以开销更小，适合大量网络请求、用户输入和界面事件等 I/O 等待任务。在 FirstCoder 中，启动程序会创建一个进程，主线程运行 AnyIO 事件循环，Agent 可以作为其中的协程运行；当流式模式需要执行同步工具时，Agent 协程在 `await` 处暂停，工具被交给 AnyIO 工作线程，主线程则继续处理界面刷新和取消操作；如果是后台工具，任务还会进入专门的后台线程池。可以概括为：进程负责资源隔离，线程负责实际执行代码，协程负责在线程上高效组织大量可暂停任务。

```
FirstCoder 进程
├── 主线程
│   └── 事件循环
│       ├── Agent 协程
│       ├── 界面协程
│       └── 输入和取消协程
├── AnyIO 工具工作线程
└── 后台任务线程池
```

可能的追问包括：线程和协程的切换有什么区别；协程为什么不能直接执行阻塞代码；什么是事件循环；`await` 时线程在做什么；线程之间为什么需要加锁；进程之间如何通信；CPU 密集型任务应该使用线程还是进程。

# 工具调用流程
FirstCoder 的工具执行需要从三个相互独立的维度理解：流式和非流式决定工具执行服务运行在哪个线程；串行和并行决定同一轮多个工具如何调度；前台和后台决定 Agent 是否等待真实结果。这三个维度可以组合，不能混为一类。

完整流程可以记成：

```
模型返回 tool_calls
    ↓
保存模型的工具调用消息
    ↓
进入工具执行服务
    ↓
剥离后台控制参数
    ↓
参数校验和权限检查
    ↓
选择执行方式
    ├── 后台执行
    ├── 前台并行执行
    └── 前台串行执行
    ↓
记录工具结果
    ↓
Agent 再次调用模型
```

流式和非流式主要影响线程位置。非流式模式下，系统等待模型一次性返回完整结果，工具执行服务直接运行在当前调用线程中。流式模式下，主线程还要维护事件循环和终端界面的响应，因此系统通过 `anyio.to_thread.run_sync`，把整个同步工具执行服务交给 AnyIO 管理的工作线程。此时 Agent 协程会暂停等待前台工具结果，但主线程没有被阻塞，仍然可以刷新界面、接收用户输入和处理取消操作。工具完成后，事件循环再恢复 Agent 协程。需要注意，流式并不等于并行或后台，它只是改变了同步工具代码在哪个线程运行。

串行和并行处理的是模型一次返回多个工具调用的情况。默认情况下，工具按照模型给出的顺序逐个执行；如果连续出现的工具符合并行规则，系统就把它们组成一个批次，并创建临时 `ThreadPoolExecutor`，让多个工具在不同线程中同时执行。正常权限模式下，主要是文件查看、搜索和 Git 查询等只读工具能够并行；`task_update`、权限交互工具和后台工具不会进入这个并行批次。即使多个工具并行运行，Agent 仍然要等待整批工具全部完成，拿到真实结果后才能继续调用模型，因此这种并行仍然属于前台执行。

前台和后台决定 Agent 是否等待。前台串行工具是执行一个、等待一个；前台并行工具是同时执行一批，但仍然等待整批完成。后台工具则由 `BackgroundJobManager` 提交到长期存在的后台线程池，当前工具调用立即返回一个包含任务 ID 的占位结果，Agent 不等待真实结果就可以继续调用模型。后台任务完成后，结果先进入完成队列，在后续模型请求开始前，以 `<task_notification>` 的形式写入会话并交给模型。

三种线程机制可以这样区分：

|线程机制|解决的问题|Agent 是否等待|
|---|---|---|
|AnyIO 工作线程池|流式模式下避免同步工具阻塞主事件循环|等待前台结果|
|临时并行线程池|同一轮多个符合条件的工具同时执行|等待整批结果|
|后台任务线程池|耗时工具脱离当前工具轮次继续执行|不等待真实结果|

各种组合的执行效果是：

|组合|实际执行方式|
|---|---|
|非流式＋前台串行|在当前调用线程中逐个执行并等待|
|流式＋前台串行|在 AnyIO 工作线程中逐个执行，Agent 协程等待，主事件循环不阻塞|
|前台并行|在临时线程池中同时执行，Agent 等待整批完成|
|非流式＋后台|当前线程负责提交，后台线程池真正执行，立即返回任务 ID|
|流式＋后台|AnyIO 工作线程负责提交，后台线程池真正执行，立即返回任务 ID|

因此，最简单的记忆方式是：

> 流式和非流式决定“工具执行服务在哪个线程运行”；串行和并行决定“这一批工具是一个个做，还是同时做”；前台和后台决定“Agent 要不要等待真实结果”。

还有一个容易混淆的地方：前台并行和后台并发都可能使用多个线程，但语义完全不同。前台并行是“同时做完这一批，再继续调用模型”；后台执行是“先登记任务并继续调用模型，真实结果以后再通知”。

可能的追问包括：
为什么流式模式不直接在主线程执行同步工具；
前台并行为什么仍然属于前台；
哪些工具可以进入并行批次；
后台工具为什么先返回占位结果；
三个线程池之间有什么区别；
`task_update` 为什么不能并行和后台执行；
后台任务完成后如何重新进入模型上下文。

# 哪些工具可以进入并行批次；
FirstCoder 是否把工具放进并行批次，不只看模型是否一次返回了多个工具调用，还要同时满足工具在并行白名单中、调用之间连续、已经通过权限检查、不会触发用户确认，并且没有设置后台执行。在正常权限模式下，只有 `ls`、`view`、`grep`、`glob`、`tree`、`read_multi`、`git_status`、`git_diff` 和 `git_log` 这些只读探查工具可以并行，因为它们通常不会修改工作区，相互之间的影响比较小。在完全放开权限的 Bypass 模式下，白名单还会增加 `write`、`edit`、`delete`、`apply_patch`、`shell`、`python_exec`、`fetch` 和 `web_search`，但这意味着调用者已经明确接受了更高的并发风险。`task_update` 等任务计划工具、`delegate`、后台控制工具以及需要权限确认的调用都不会进入并行批次。符合条件的连续调用会被放进临时线程池同时执行，Agent等待整批完成后，再按照原始工具调用顺序记录结果并继续请求模型。所以这套机制的原则是：默认只并行无副作用的独立读取操作，只有在明确的 Bypass 模式下才扩大到可能产生副作用的工具。

可能的追问包括：
为什么只有连续的工具调用才能组成一个批次；
为什么后台工具不能进入并行批次；
并行结果如何保持原始顺序；
多个写工具并行可能产生什么风险；
`task_update` 为什么不能并行；
某个并行工具失败后会不会取消其他工具；
如何判断两个工具之间是否真的不存在依赖。


# 三个线程池之间有什么区别；

这三个线程池虽然都使用线程，但解决的是三个不同问题：AnyIO 工作线程池解决“不要卡住主事件循环”，并行工具线程池解决“同一轮多个工具同时执行”，后台任务线程池解决“Agent 不等待耗时任务”。

|线程池|作用|生命周期|Agent 是否等待|
|---|---|---|---|
|AnyIO 工作线程池|把同步工具执行从流式事件循环中移出去|由 AnyIO 统一管理和复用|等待工具结果|
|并行工具线程池|同时执行一批符合条件的工具|每个并行批次临时创建，用完销毁|等待整批结果|
|后台任务线程池|让耗时工具脱离当前工具轮次运行|随 FirstCoder 应用长期存在|不等待真实结果|

AnyIO 工作线程池只在流式工具执行中发挥作用。主线程运行事件循环和 Agent 协程，如果直接执行同步工具，界面刷新和取消操作都会被卡住。因此系统把整个工具执行服务交给 AnyIO 工作线程，Agent 协程在 `await` 处暂停，主线程继续处理其他异步任务。它改变的是“工具执行服务在哪个线程运行”，不会自动让工具并行，也不会自动把工具变成后台任务。

并行工具线程池是在工具执行服务内部创建的临时 `ThreadPoolExecutor`。当模型一次返回多个符合并行条件的工具，例如同时读取多个文件，系统会创建一个线程数量与当前批次工具数量相同的线程池，让这些工具同时执行。等全部完成后，这个线程池就被销毁，Agent拿到整批真实结果后继续调用模型。因此它虽然并行，但仍然属于前台执行。

后台任务线程池由 `BackgroundJobManager` 管理，默认最多有 4 个工作线程，并限制最多接收 8 个未结束任务。显式带有 `run_in_background=true` 的工具会被提交到这里，当前工具调用立即返回任务 ID，不等待真实结果。这个线程池还负责维护任务状态、取消令牌和完成队列，任务结束后再通过任务通知把结果交给模型。

三个线程池还可能嵌套出现。例如流式模式下模型返回三个文件读取工具时，AnyIO 先用一个工作线程运行工具执行服务，工具执行服务内部再创建临时并行线程池，让三个读取工具同时执行：

```
主线程
└── Agent 协程等待
    ↓
AnyIO 工作线程
└── 运行工具执行服务
    ↓
临时并行线程池
├── 读取文件 A
├── 读取文件 B
└── 读取文件 C
```

如果流式模式下提交后台工具，则是 AnyIO 工作线程负责完成校验和提交，真正的耗时任务进入后台任务线程池：

```
主线程
    ↓
AnyIO 工作线程：校验并提交任务
    ↓
后台任务线程池：长期执行真实工具
```

最简单的记忆方式是：AnyIO 线程池负责“不阻塞界面”，并行线程池负责“一批工具做得更快”，后台线程池负责“当前 Agent不用等”。它们都运行在同一个 FirstCoder 进程中，共享进程内存，并不提供进程级隔离。


# 多agent场景下 你是怎么做好子agent的拆分的 硬约束？

# 工具调用的类别划分顺序是怎么的？先辨别出前后台，再辨别出串行和并行？

整体上可以理解为先区分前台和后台，再对前台工具区分串行和并行。不过在真正分流之前，还会先做参数校验和权限检查。

完整顺序是：

```
确定当前是流式还是非流式
    ↓
接收模型返回的一批 tool_calls
    ↓
统一剥离并记录 run_in_background 等控制参数
    ↓
按照模型给出的顺序逐个处理
    ↓
参数与工具合法性校验
    ↓
权限检查
    ↓
是否要求后台执行？
    ├── 是：提交后台任务线程池，记录占位结果
    └── 否：属于前台工具
              ↓
          是否符合并行条件？
              ├── 是：收集连续的可并行工具，组成并行批次
              └── 否：按串行方式执行单个工具
```

所以严格来说，决策顺序是：

```
流式/非流式
→ 校验和权限
→ 后台/前台
→ 前台并行/前台串行
```

流式和非流式在最外层决定工具执行服务运行在哪个线程。流式模式把工具执行服务交给 AnyIO 工作线程，非流式模式直接在当前调用线程执行，但两者进入工具执行服务后的分流规则相同。

后台判断优先于并行判断。只要工具带有 `run_in_background=true`，通过权限检查后就直接提交后台线程池，不会再加入当前轮次的并行批次。后台调用虽然是由工具执行服务逐个提交的，但提交后的多个后台任务可以在后台线程池中并发运行。

没有后台标记的调用都属于前台调用。前台调用再判断是否位于并行白名单、权限是否已经通过，以及相邻调用是否同样符合条件；符合时组成临时并行批次，否则走单个串行执行。

例如模型一次返回：

```
view A
view B
shell(run_in_background=true)
task_update
view C
view D
```

实际会被划分为：

```
view A + view B       → 前台并行批次
shell                 → 后台执行
task_update            → 前台串行
view C + view D       → 新的前台并行批次
```

因此最简单的结论就是：后台工具先从当前批次中分流出去，剩余前台工具再按照并行白名单和连续性划分为并行批次或串行调用。

# 主agent能观测子agent的状态吗？还是说子agent执行过程中，主agent没有工具查看子agent的运行情况与步骤？
主 Agent只能观测子 Agent的粗粒度状态，不能在执行过程中查看子 Agent每一步的模型调用和工具执行过程。

如果是前台委托，父 Agent会阻塞等待 `delegate` 返回。在子 Agent执行期间，父 Agent本身不能继续调用工具，因此也没有机会查询子 Agent进度；子 Agent结束后，父 Agent才会一次性收到最终总结和子 Session ID。

如果是后台委托，父 Agent会立即获得一个后台任务 ID，例如 `bg_0001`，然后可以调用 `background_status` 查询：

```
running
completed
failed
cancelled
```

如果任务已经完成，还能看到最终结果摘要；也可以通过 `background_cancel` 请求取消任务。但是在任务仍处于 `running` 时，`background_status` 只能告诉父 Agent“这个 delegate 任务还在运行”，不会返回子 Agent当前正在阅读哪个文件、调用了什么工具、已经进行了几轮模型调用等内部步骤。

```
父 Agent
    ↓ background_status(bg_0001)
后台任务管理器
    ↓
返回：delegate 正在运行
```

子 Agent确实拥有独立的 Session，并且执行消息和工具结果会写入自己的 JSONL，但当前 FirstCoder 没有向父模型提供读取或持续追踪这个子 Session 的专用工具。父 Agent通常要等子 Agent结束后，才能通过返回结果获得 `child_session_id` 和最终总结；后台任务运行期间，后台任务 ID与子 Session的运行细节也没有作为可查询信息暴露出来。

因此，当前实现可以概括为：父 Agent能够查询后台委托的生命周期状态，也能取消任务，但不能实时观察子 Agent的详细执行轨迹。若要支持这种能力，需要增加子 Agent状态查询工具，或者把子 Agent的模型轮次、当前工具、阶段和阶段性结果通过事件总线持续上报给父 Agent。


# 子agent有自己的session，主agent要查看的话，只能用读文件的方式看一下。是吗？
从底层实现上说是的：子 Agent 的执行记录保存在自己的 Session JSONL 中，如果知道子 Session ID和数据目录，可以直接读取对应文件查看它已经产生的消息和工具结果。

但从 FirstCoder 当前提供给父 Agent的正式能力来看，父 Agent没有 `read_subagent_session` 或 `subagent_progress` 这样的工具，因此“读取子 Session 文件”并不是正常的观测链路。普通文件工具主要面向项目文件，Session 数据目录还可能受到沙箱和权限限制；而且后台子 Agent运行期间，父 Agent通常只知道后台任务 ID，`child_session_id` 要等 `delegate` 执行完成后才会随结果返回，所以父 Agent往往连正在运行的子 Session文件名都不知道。

因此更准确地说：

> 子 Agent的完整轨迹确实落在独立 JSONL 中，用户或程序底层可以读取；但父 Agent当前只能通过 `background_status` 查看粗粒度状态，不能通过正式工具实时读取子 Session。强行用文件工具查 JSONL 只是底层排查方式，不是项目设计好的多 Agent观测能力。

如果要正式支持，就应该新增一个只读的子 Agent观测工具，通过父子 Session关系查询子 Agent当前阶段、最近工具调用和执行摘要，而不是让父 Agent直接解析内部 JSONL 文件。




# 子 Agent 调用工具需要审批时怎么办？

当前 FirstCoder 没有实现父子 Session 之间的审批转发和恢复机制。因此，子 Agent调用敏感工具、触发人工审批时，不会把审批请求交给父 Agent或用户，而是终止本次委托，并将其判定为执行失败。需要注意，失败的是这次子 Agent委托，需要审批的敏感工具不会被执行，父 AgentLoop本身也不会崩溃。

完整流程如下：

```
子 Agent调用敏感工具
→ 权限系统要求人工审批
→ 子 Agent进入 waiting_for_user_input
→ 子 Agent执行适配器停止本次委托
→ delegate 生成 ok=false 的工具结果
→ 失败结果写入父 Session
→ 父 Agent再次调用模型
→ 父模型决定如何处理
```

父模型看到失败结果后，可以改由父 Agent执行该操作，让父 Agent走正常的用户审批流程；也可以缩小任务权限、换一个子 Agent角色、重新委托，或者向用户说明真实阻塞。系统不会自动重试，也不会在用户审批后恢复原来的子 Agent；父模型再次调用 `delegate` 时，会创建一个新的子 Session。

前台子 Agent同样适用这套规则。即使父 Agent正在同步等待子 Agent，当前实现也无法把子 Session中的权限请求桥接到父 Session，因此仍然会结束本次委托。

如果子 Agent失败前已经执行了其他操作，这些结果不会自动回滚。前台 coder此前对父工作区产生的修改会继续保留；后台 coder运行在独立 Git Worktree 中，已经产生的修改会保留在该 Worktree，系统会把路径、分支和 diff 摘要返回给父 Agent处理。

后台子 Agent失败时，父 Agent之前已经收到“后台任务已启动”的占位结果。审批导致子 Agent失败后，后台任务会变为 `failed`，并在后续模型请求中通过 `<task_notification>` 通知父 Agent；与其关联的 TaskPlan 任务不会被自动标记为 `completed`。

后台 coder对此进行了部分优化：它在独立 Worktree 中使用专属权限管理器，Worktree 范围内的常规修改和部分安全验证操作可以自动放行。但如果涉及敏感路径或危险命令，仍然会触发审批并导致本次委托失败。

一句话总结：

> 子 Agent只能执行已经授权或能够自动放行的操作；一旦需要人工审批，当前 FirstCoder会终止本次委托并将失败结果交给父 Agent，而不会转发审批并原地恢复子 Agent。
