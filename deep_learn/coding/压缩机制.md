

下面只总结四种压缩触发方式、各自目标、执行层级以及可能出现的情况。

## 一、先记住四层分别做什么

- L1：裁剪旧任务普通对话，模型只看到 `[Earlier dialogue trimmed]`。
- L2：按内容类型压缩已消费的派生工具结果，例如搜索结果、Diff、测试日志和JSON。
- L3：将失效、重复或过大的工具结果归档，替换成可取回的 `archive_id`。
- L4：调用模型生成七段式开发Checkpoint。

“执行某一层”只代表进入这一层检查，不代表一定找到内容并发生变化。

---

# 二、四种触发方式总表

|触发方式|什么时候触发|压缩目标|L1～L3|L4|
|---|---|---|---|---|
|`AUTO`|输入达到高水位|低水位|从L1顺序执行，可提前停止|L1～L3后仍未低于目标才执行|
|`TASK_HASH_CHANGED`|任务切换经过确认|低水位的2/3|强制L1，必须检查L2和L3|L1～L3后仍未低于目标才执行|
|`MANUAL`|用户执行 `/compact`|通常为当前输入的60%，同时低于低水位且高于固定开销|从L1顺序执行，可提前停止|程序化压缩后仍未低于手动目标才执行|
|`PROMPT_TOO_LONG`|Provider拒绝主请求，认为输入过长|低水位|从L1顺序执行，可提前结束程序化阶段|无论L1～L3是否达到目标，当前代码都会继续尝试L4|

---

# 三、AUTO：达到高水位自动压缩

## 触发条件

每次准备请求主模型前，系统估算：

```
input_tokens >= high_watermark
```

满足时启动AUTO。

低于高水位时，不启动AUTO压缩。

## 压缩目标

```
target = low_watermark
```

## 执行顺序

```
达到高水位
    ↓
L1
    ↓
达到低水位且无必须候选？
├─ 是：停止
└─ 否：L2
          ↓
       达到低水位且无必须候选？
       ├─ 是：停止
       └─ 否：L3
                ↓
             低于目标？
             ├─ 是：停止
             └─ 否：L4
```

## 可能情况

### 情况1：L1已经足够

```
压缩前：95,000
目标：  72,000
L1后：  68,000
```

结果：

```
只执行L1
不执行L2、L3、L4
```

### 情况2：L1不够，L2足够

```
L1后：80,000
L2后：70,000
```

结果：

```
执行L1、L2
不执行L3、L4
```

### 情况3：L3才达到目标

```
L1后：88,000
L2后：78,000
L3后：69,000
```

结果：

```
执行L1、L2、L3
不执行L4
```

### 情况4：前三层都不够

```
L3后：75,000
目标：72,000
```

结果：

```
进入L4生成Checkpoint
```

L4候选只有低于72,000才会提交，否则压缩失败。

### 情况5：某层没有候选

例如L1没有旧任务内容：

```
L1执行
changed_parts = 0
```

系统继续检查L2，而不是认为整个压缩已经结束。

### 情况6：AUTO被跳过

以下情况可能跳过AUTO：

- 没达到高水位；
- 自动压缩熔断器已打开；
- 相同上下文上一次压缩完全无效，指纹没有变化。

---

# 四、TASK_HASH_CHANGED：确认任务切换

## 触发条件

不是分类模型第一次返回 `new` 就立即触发。

默认流程是：

```
第一次new
→ 建立候选任务

下一次same
→ 状态机确认候选任务
→ active_task_hash发生变化
→ 触发TASK_HASH_CHANGED
```

## 压缩目标

```
target = low_watermark × 2/3
```

## 特殊配置

```
force_old_task_compaction = true
required_levels = ("l2", "l3")
```

它的执行方式与普通AUTO不同。

## 执行顺序

```
确认任务切换
    ↓
L1：强制裁剪旧任务普通对话
    ↓
L2：必须进入检查
    ↓
L3：必须进入检查
    ↓
低于任务切换目标（低水位的2/3）？
├─ 是：停止，不执行L4
└─ 否：执行L4
```

## 为什么L1是强制的

普通AUTO中，旧任务对话通常需要距离当前至少8轮。

任务切换触发时会绕过8轮冷却：

```
只要确认属于旧任务
→ 可以立即裁剪
```

## 为什么L2、L3必须检查

任务切换不仅清理旧对话，还要求检查：

- 可以确定性压缩的派生工具结果；
- 已失效的读取结果；
- 被新结果覆盖的旧结果；
- 重复工具结果；
- 可归档的大型结果。

但“必须检查”不代表一定产生变化。

例如：

```
L2进入检查
但没有derived工具结果
→ changed_parts = 0

L3进入检查
但没有stale、superseded或duplicate
→ changed_parts = 0
```

## 可能情况

### 情况1：原本低于低水位

即使当前只有30,000 Token，低水位是72,000：

```
仍然执行L1
仍然检查L2
仍然检查L3
L4不执行
```

任务切换压缩不完全是为了Token，也是为了减少旧任务干扰。

### 情况2：L1后已经低于目标

与AUTO不同，任务切换仍然会继续检查L2和L3，因为它们被标记为required。

```
L1达到目标
→ 继续L2
→ 继续L3
→ 不执行L4
```

### 情况3：L1～L3后仍然过大

```
执行L4
→ 生成Checkpoint
→ 低于任务切换目标（低水位的2/3）才提交
```

### 情况4：分类只返回第一次new

此时只是建立候选任务，没有确认切换：

```
不会触发TASK_HASH_CHANGED
不会立即强制执行L1～L3
```

# 五、MANUAL：用户手动执行压缩

## 触发方式

用户在TUI输入：

```
/compact
```

## 压缩目标

如果当前输入不超过2000 Token：

```
不设置更激进的手动目标
通常直接无操作
```

如果超过2000 Token，先计算：

```
proposed =
    min(
        low_watermark - 1,
        current_input_tokens × 60%
    )
```

再加固定上下文保护：

```
target =
    max(
        proposed,
        fixed_tokens + 1
    )
```

只有：

```
target < current_input_tokens
```

才采用该目标。

所以简化理解是：

> 手动压缩通常尝试压到当前输入的60%，并保证目标低于低水位，但不能低于系统提示词和工具定义等固定开销。

## 执行顺序

```
用户执行/compact
    ↓
计算手动目标
    ↓
L1
    ↓
达到手动目标且无必须候选？
├─ 是：停止
└─ 否：L2
          ↓
        L3
          ↓
       仍未达到手动目标？
       ├─ 否：停止
       └─ 是：L4
```

## 可能情况

### 情况1：什么历史都没有

只有系统提示词和工具定义：

```
input_tokens = fixed_tokens
```

没有可压缩历史，手动目标也不会设置到固定开销以下。

结果通常是：

```
Manual compact skipped
```

不会无限压缩，也不会不断调用L4。

### 情况2：输入不足2000 Token

通常不设置60%目标，使用默认预算判断。因为已经远低于低水位，一般无操作。

### 情况3：低于低水位但超过2000 Token

例如：

```
当前输入：20,000
低水位：72,000
固定开销：5,000
```

手动目标大约是：

```
20,000 × 60% = 12,000
```

虽然当前已经低于低水位，手动压缩仍可能执行，因为用户明确要求进一步压缩。

### 情况4：位于高低水位之间

这是最典型的使用场景：

```
AUTO不会触发
用户希望主动缩短上下文
→ 执行/compact
```

### 情况5：高于高水位

程序仍允许手动压缩。

正常情况下，下一次主模型请求前AUTO会自动处理，因此通常用不到手动操作。但恢复大会话、AUTO熔断或用户主动先压缩时，仍可能出现。

### 情况6：前三层无法达到手动目标

会执行L4。

如果L4仍然达不到手动目标：

```
候选Checkpoint作废
手动压缩返回失败
```

不会循环压缩到成功。

# 六、PROMPT_TOO_LONG：Provider拒绝后的兜底恢复

## 触发条件

本地估算认为请求可以发送，但Provider使用真实规则计算后拒绝，例如返回：

```
maximum context length exceeded
context length exceeded
prompt too long
```

本地归类为：

```
ProviderErrorKind.PROMPT_TOO_LONG
```

这里是输入太长，不是模型输出太长，也不是模型主动判断“内容太多”。

## 为什么本地可能没提前发现

项目采用近似估算：

```
Token ≈ 字符数 ÷ 4
```

没有使用模型对应的真实Tokenizer，因此可能低估。

还可能存在：

- 模型真实上下文窗口配置不准确；
- 工具Schema估算存在偏差；
- 图片或特殊字符Token估算不准确；
- Provider实际限制与本地配置不一致。

## 压缩目标

```
target = low_watermark
```

它和AUTO使用相同的低水位目标；这条恢复路径的额外激进之处，是程序化压缩后无论是否达到目标都继续尝试L4。

## 执行顺序

```
主模型请求被Provider拒绝
    ↓
触发PROMPT_TOO_LONG
    ↓
L1
    ↓
达到目标且无必须候选？
├─ 是：结束程序化阶段
└─ 否：L2
          ↓
        必要时L3
          ↓
程序化阶段结束
    ↓
无论程序化阶段是否达到目标
都继续执行一次普通L4
    ↓
成功后重新请求主模型一次
```

## 关键特点

`PROMPT_TOO_LONG`与其他触发最大的区别是：

> 即使L1～L3已经达到低水位目标，当前代码仍然继续尝试L4。

## 可能情况

### 情况1：L1已经达到目标

```
PROMPT_TOO_LONG
→ L1达到目标
→ L2、L3没有必须候选，因此停止程序化阶段
→ 直接执行L4
```

所以可能出现：

```
L1 → L4
```

### 情况2：L2达到目标

```
L1 → L2 → L4
```

### 情况3：L3达到目标

```
L1 → L2 → L3 → L4
```

### 情况4：前三层仍然没有达到目标

```
L1 → L2 → L3 → L4
```

L4必须把结果压到低水位以下才允许提交。

### 情况5：第一次L4正常成功

```
提交Checkpoint
→ 重建更短上下文
→ 重试主模型请求一次
```

### 情况6：L4摘要请求本身也Prompt Too Long

这与主请求Prompt Too Long是第二层错误：

```
主请求过长
→ 启动恢复
→ L4摘要请求也过长
→ 尝试更强程序化压缩
→ 必要时用stronger摘要Prompt再试一次
```

### 情况7：L4生成摘要，但仍然超过目标

结果是：

```
still_over_budget
→ 候选作废
→ 当前Fallback直接失败
```

不会自动反复使用stronger Prompt。

### 情况8：恢复成功，但重试主请求仍然过长

主模型只重试一次。

第二次仍然Prompt Too Long时：

```
错误继续向上抛出
```

不会无限执行恢复。

# 七、四种触发的决策流程

可以把整个机制记成下面这张图：

```
压缩请求来自哪里？
│
├─ AUTO
│   ├─ 没达到高水位 → 不压缩
│   └─ 达到高水位
│       → 目标=低水位
│       → L1→L2→L3按需执行
│       → 仍超目标才L4
│
├─ TASK_HASH_CHANGED
│   → 目标=低水位×2/3
│   → 强制L1
│   → 必须检查L2、L3
│   → 仍超目标才L4
│
├─ MANUAL
│   → 用户输入/compact
│   → 目标通常约为当前输入60%
│   → 不能低于固定上下文
│   → L1→L2→L3按需执行
│   → 仍超手动目标才L4
│
└─ PROMPT_TOO_LONG
    → 目标=低水位
    → L1→L2→L3按需执行
    → 程序化阶段可以提前停止
    → 但仍然执行L4
    → 成功后重试主请求一次
```

# 八、最容易混淆的五点

1. 单条工具结果过大不是独立触发器，只会影响已经启动的L2/L3是否继续。
    
2. 任务切换会检查L1～L3，但不一定执行L4。
    
3. 手动压缩的目标不是普通低水位，通常更激进，约为当前输入的60%。
    
4. `PROMPT_TOO_LONG`是Provider拒绝输入，不是模型语义判断，也不是回答生成过长。
    
5. “进入某层”和“该层实际压缩了内容”是两件事。一层可能被执行，但因为没有候选而产生0项变更。

# Coding Agent 上下文管理与四层压缩机制笔记

下面这份笔记完全按照当前源码整理，同时包含我们前面讨论中出现过的误解、纠正和设计风险。

---

## 一、先建立整体概念：Agent的上下文是什么

每次请求主模型时，系统需要发送三类内容：

### 1. 固定上下文

包括：

- 系统提示词；
- Agent行为规则；
- 项目规则；
- 工具名称、描述和参数Schema；
- 临时运行指令。

这部分通常不能通过L1～L4随意压缩。

### 2. 动态会话历史

包括：

- 用户消息；
- 助手回复；
- 助手发出的工具调用；
- 工具执行结果；
- 最近一次Checkpoint；
- Checkpoint之后的原始消息尾部。

这部分会随着任务运行不断增长，是上下文压缩的主要处理对象。

### 3. 输出预留

系统还需要为模型即将生成的回答预留Token，不能把整个上下文窗口都拿来放输入。

---

## 二、Token预算是怎么计算的

项目目前没有使用模型对应的真实Tokenizer，而是采用Provider无关的近似估算。

### 文本Token估算

```
Token ≈ 字符数 ÷ 4，向上取整
```

### 图片Token估算

每张图片固定估算为：

```
1024 Token
```

### 默认窗口配置

如果模型没有明确配置上下文窗口，当前代码默认：

```
context_window = 200,000
output_reserve = 4,096
```

首先只使用上下文窗口的95%：

```
usable_window = context_window × 95%
```

再扣除输出预留：

```
input_capacity = usable_window - output_reserve
```

然后计算两个水位：

```
高水位 = input_capacity × 90%
低水位 = input_capacity × 72%
```

因此，低水位和高水位不是整个模型窗口的72%和90%，而是扣除了5%安全余量和输出预留后的输入容量比例。

### 固定开销与历史开销

预算会进一步拆成：

```
fixed_tokens =
    系统提示词
  + 工具定义

history_tokens =
    用户消息
  + 助手消息
  + 工具调用
  + 工具结果
  + Checkpoint等历史内容

input_tokens = fixed_tokens + history_tokens
```

如果固定上下文本身已经达到低水位，即使删除全部历史也无法完成压缩，管理器会直接返回：

```
fixed_context_over_budget
```

因为L1～L4主要处理会话历史，不能随意删除系统提示词和工具定义。

---

# 三、任务边界分类机制

上下文压缩中的L1需要区分“当前任务”和“旧任务”，因此系统先维护任务边界。

## 1. 任务分类是一次单独的模型请求

除会话第一条用户消息外，每收到一条新的真实用户消息，系统会先执行一次隐藏分类。

流程是：

```
用户发送消息
→ 隐藏任务边界分类
→ 更新任务状态
→ 必要时触发任务切换压缩
→ 正式请求主模型
```

分类请求和主请求是两次独立的模型调用。

### 分类请求发送什么

分类请求包含：

```
任务分类专用系统提示词
+
当前有效会话历史
+
最新用户消息
```

当前有效历史可能包括：

- 用户消息；
- 助手回复；
- 工具调用；
- 工具结果；
- Checkpoint摘要。

所以，工具消息不是分类目标，但会作为判断依据提供给分类模型。

### 分类请求不包含什么

它不提供工具：

```
tools = []
tool_choice = "none"
```

最大输出为：

```
512 Token
```

模型只能返回严格JSON：

```
{
  "decision": "same|new|uncertain",
  "basis_message_id": "当前用户消息ID"
}
```

无效时最多尝试3次；最终仍然失败，则按 `uncertain` 处理。

## 2. 分类和主请求使用什么模型

当前代码复用主Agent的同一个Provider和模型，但属于两次独立请求。

所以准确说法是：

- 独立请求：是；
- 独立模型：当前不是；
- 对用户可见：不是；
- 每次主模型调用前都分类：不是；
- 每条新用户消息通常分类一次：是；
- 工具循环中的后续模型请求再次分类：不会。

一个用户需求可能产生：

```
一次边界分类请求
+
多次主模型工具循环请求
```

## 3. 为什么不能简单并行

当前流程依赖分类结果完成：

- `active_task_hash`更新；
- 用户消息任务标记；
- 任务切换压缩；
- 主请求上下文构造。

如果分类请求和主请求同时发送，主请求发出时还不知道是否应该清理旧任务，因此分类结果无法影响当前主请求。

并行可能降低部分延迟，但不会减少Token，因为两个请求仍然都要发送。

后续更合理的优化是：

- 给分类器单独使用轻量模型，降低费用；
- 只提供当前任务摘要和最近几轮，减少分类输入Token；
- 规则优先，语义模糊时才调用模型。

---

# 四、same、new、uncertain到底怎么处理

## 1. same

没有候选任务时：

```
decision = same
→ active_task_hash保持不变
→ 继续当前任务
```

源码会顺便把候选字段设置成 `None`、稳定计数设置成0。候选本来就是空时，这只是幂等重置，不产生实际变化。

存在候选任务时：

```
decision = same
→ 被程序解释为继续候选任务
→ 候选任务稳定计数增加
→ 达到默认2次观察后切换
```

## 2. new

程序根据当前用户消息ID生成候选任务哈希：

```
candidate_hash =
    stable_hash(
        session_id
      + basis_message_id
      + 策略版本
    )
```

如果还没有活动任务，例如会话第一条消息，则直接把它初始化成活动任务。

如果已经存在活动任务，则默认先保存为候选，不立即切换：

```
active = task_A
candidate = task_B
stable_count = 1
```

## 3. uncertain

```
active_task_hash保持不变
candidate_task_hash清空
stable_count归零
不触发任务切换
```

它采用的是保守策略。

---

# 五、task_hash到底是什么

`task_hash`不是用户消息正文的语义哈希，也不是通过比较两条消息内容计算出来的。

它只是任务身份ID。

计算输入是：

```
session_id
+ 任务起点消息ID
+ 策略版本
```

因此：

```
两个哈希相等
```

只表示程序认为它们属于同一个任务身份，不表示两条消息语义相似。

真正判断任务是否相同的是：

```
模型输出same/new/uncertain
+
程序状态机
```

随后程序把判断结果转换成任务哈希，并写入消息元数据。

L1最终只是机械比较：

```
消息task_hash == active_task_hash
→ 当前任务

消息task_hash != active_task_hash
→ 旧任务候选
```

所以正确因果关系是：

```
模型做语义判断
→ 状态机维护任务身份
→ 程序生成/切换task_hash
→ task_hash用于后续确定性压缩
```

不是：

```
程序比较消息内容哈希
→ 自动判断是否为同一任务
```

---

# 六、当前任务候选确认机制的问题

当前源码采用：

```
第一次new
→ 建立候选任务B

下一次same
→ 确认候选任务B
```

例如：

```
活动任务A：修改登录模块

用户：现在分析订单模块
分类：new
结果：建立候选任务B，但active仍然是A

用户：先看看订单创建流程
分类：same
结果：程序认为用户继续候选B
     将active切换为B
```

## 为什么不是连续两次new

因为候选哈希包含当前用户消息ID。

连续两条消息都返回 `new` 时：

```
第一条消息ID不同 → candidate_B
第二条消息ID不同 → candidate_C
```

第二个候选与第一个候选不同，稳定计数会重新开始，不能确认B。

## 这里存在语义问题

分类提示词要求模型判断最新消息是否延续“活动任务”，但程序在存在候选任务时，把 `same` 解释成延续“候选任务”。

模型并没有被显式告诉：

```
已确认活动任务是A
待确认候选任务是B
请判断最新消息延续A还是B
```

它只能通过最近对话自行推断。

因此，`same`在程序中有两种隐含含义：

```
没有候选时：
same = 继续active任务

存在候选时：
same = 继续candidate任务
```

这是当前设计中比较脆弱的地方。

## 旧任务历史会不会影响分类

会有这种风险。

候选任务尚未确认时，任务切换压缩还没有执行，因此分类请求里可能同时存在：

- 大量旧任务历史；
- 候选新任务第一条消息；
- 新任务第一轮产生的助手和工具消息；
- 最新用户消息。

最近消息通常会让模型倾向于判断用户正在继续候选任务，但代码没有显式保证模型一定以候选任务作为比较对象。

## 更合理的改进方式

可以把分类输出改成：

```
same_active
same_candidate
new
uncertain
```

或者显式提供：

```
当前活动任务：
修改登录模块

待确认候选任务：
分析订单模块

最新用户消息：
先看看订单创建流程
```

还可以直接在第一次高置信度 `new` 时切换任务，但必须同时提高L1的可恢复性，避免误判造成信息丢失。

## 另一个潜在问题

第一次 `new` 尚未确认时，Agent仍然使用旧的 `active_task_hash` 运行这一轮。

因此，这一轮新任务产生的部分助手消息和工具过程可能暂时带着旧任务哈希。下一轮确认后，源码会重新标记候选起点用户消息和当前用户消息，但不一定完整重标中间产生的所有助手与工具内容。

这可能导致新任务第一轮的部分内容后续仍被当作旧任务内容，是任务边界实现中需要进一步完善的地方。

---

# 七、压缩不会直接删除所有原始数据

系统采用append-only JSONL事件日志。

保存的内容包括：

- 用户消息；
- 助手消息；
- 工具调用；
- 工具结果；
- 任务边界观察；
- 压缩替换；
- 归档信息；
- Checkpoint。

压缩主要改变的是模型下一次看到的有效上下文投影。

可以理解为：

```
原始JSONL事实
        ↓
事件重放生成SessionView
        ↓
应用压缩替换和Checkpoint
        ↓
ContextBuilder生成模型消息
```

因此要区分三种“记忆”：

### 原始审计记录

底层JSONL中的原始事实，一般不删除。

### 重建后的有效会话状态

会应用压缩替换、归档占位符和Checkpoint。

### 模型当前看到的工作记忆

只包含有效Checkpoint、未压缩尾部和压缩后的工具结果。

压缩虽然不一定删除原始事件，但确实会改变模型可见的工作记忆。

---

# 八、启动压缩的四种管理器级触发

当前源码有四种触发方式：

```
AUTO
TASK_HASH_CHANGED
MANUAL
PROMPT_TOO_LONG
```

必须区分：

- 管理器级触发：决定是否启动一次压缩；
- 层级内部条件：决定启动后哪些层需要继续处理。

## 1. AUTO

每次准备主模型请求前，系统计算Token。

只有：

```
input_tokens >= high_watermark
```

才自动启动压缩。

目标是：

```
low_watermark
```

如果低于高水位，普通AUTO直接跳过。

## 2. TASK_HASH_CHANGED

任务切换经过稳定确认后启动。

目标是：

```
low_watermark × 2/3
```

特殊参数是：

```
force_old_task_compaction = true
required_levels = ("l2", "l3")
```

因此它会：

```
强制执行L1旧任务裁剪
→ 必须进入L2检查
→ 必须进入L3检查
→ 仍然超过目标才执行L4
```

“必须进入”不等于一定发生内容变化。没有合格候选时，对应层的变更数量可以是0。

## 3. MANUAL

用户输入：

```
/compact
```

触发手动压缩。

它不受AUTO高水位限制，可以在任何预算位置调用。

## 4. PROMPT_TOO_LONG

主模型请求已经发送给Provider，但Provider认为输入超过真实上下文窗口，直接拒绝请求。

Provider错误信息可能包含：

```
context length
prompt too long
maximum context
```

本地统一归类为：

```
ProviderErrorKind.PROMPT_TOO_LONG
```

它表示输入过长，不是模型输出过长，也不是模型生成一句“我觉得输入太长”。

目标是：

```
low_watermark
```

它与AUTO的目标相同；但这条恢复路径会强制继续尝试L4，因此整体恢复行为仍比普通AUTO更激进。

---

# 九、单条工具结果过大不是独立触发器

这是我们前面讨论中需要明确纠正的地方。

之前说：

> 单条工具结果超过1200 Token，即使整体上下文没有达到高水位，也会自动启动压缩。

这不符合当前源码。

普通AUTO触发只看：

```
整体input_tokens是否达到高水位
```

不会因为：

- 单条工具结果过长；
- 消息数量过多；
- 某轮工具结果总量过大；

自动绕过高水位启动管理器。

当前配置中：

```
l2_result_target_tokens = 800
large_tool_result_tokens = 1200
```

800是当前正常传入的单结果目标；1200主要是缺少有效单结果目标时的回退配置。

单结果压力的真正作用是：

```
压缩管理器已经因为某个原因启动
        ↓
程序化流水线发现某条derived结果仍超过800 Token
        ↓
即使整体已经达到目标，也允许继续检查L2/L3
```

它是流水线内部的继续条件，不是独立启动条件。

---

# 十、四层是不是每次都会全部执行

不会。

普通顺序是：

```
L1
→ 重新估算
→ 达到目标则停止

L2
→ 重新估算
→ 达到目标则停止

L3
→ 重新估算
→ 达到目标则停止

L4
```

但如果还存在必须处理的后续候选，即使达到目标，也可能继续检查下一层。

例如：

- 任务切换要求L2、L3必须检查；
- L3存在明确失效、重复候选；
- 某个派生工具结果仍超过单结果目标。

所以不是简单地：

```
达到目标后永远停止
```

而是：

```
达到目标
+ 没有required level
+ 没有mandatory candidate
+ 没有单结果压力
→ 停止
```

# 十一、L1：旧任务普通对话裁剪

## 1. L1处理什么

L1只处理旧任务中的普通文本消息。

主要条件包括：

```
消息task_hash与active_task_hash不同
+ part.kind == text
+ 尚未被压缩
+ 不是最新用户消息
+ 不破坏工具调用事务
```

正常AUTO压缩下，还要求：

```
current_turn - created_turn >= 8
```

也就是旧任务内容至少冷却8轮。

任务切换触发时：

```
force_old_task_compaction = true
```

会绕过8轮冷却，立即裁剪已确认的旧任务普通文本。

## 2. L1不会处理什么

不会直接处理：

- 当前任务普通对话；
- 最新用户消息；
- 没有task_hash的消息；
- 工具结果；
- 包含工具调用的助手消息；
- 已经被压缩的内容；
- Checkpoint覆盖范围之外不应重复处理的历史。

## 3. L1压缩成什么

L1不是摘要，而是刻意遗忘。

源码直接把文本变成：

```
content = ""
compaction_state = "trimmed"
```

ContextBuilder发现存在裁剪内容后，向模型上下文加入一次：

```
[Earlier dialogue trimmed]
```

无论裁掉多少条普通对话，通常只加入一个统一标记。

它不会生成：

```
登录任务已经完成
任务名称：登录模块
完成内容：……
```

也不会调用LLM总结旧任务。

## 4. 原始内容是否删除

底层JSONL原始事件仍然存在，但模型有效上下文看不到正文。

而且L1没有像L3一样提供 `archive_id` 和恢复工具。

因此：

```
底层审计数据：仍存在
模型有效工作记忆：已遗忘
普通Agent工具：不能直接恢复L1文本
```

## 5. L1是否过于粗糙

这是合理的担心。

风险包括：

- 分类模型可能误判任务切换；
- 任务切换会绕过8轮冷却；
- L1不生成语义摘要；
- L1不提供归档取回接口；
- 错误裁剪可能让模型失去仍然需要的事实。

默认稳定窗口能降低误判风险，但不能彻底解决。

更稳妥的方案包括：

- L1前生成旧任务简短摘要；
- 对L1文本也建立可恢复归档；
- 提取Pinned Facts后再裁剪；
- 显式区分active和candidate任务；
- 只有高置信度任务切换才强制裁剪；
- 任务切换后延迟若干轮再执行L1。

# 十二、L2：内容感知的工具结果压缩

## 1. L2不是普通消息截断

L2不会处理所有非系统消息，也不会处理普通用户和助手文本。

它遍历当前有效消息尾部，但只处理符合条件的工具结果：

```
part.kind == tool_result
+ 已经成功发送给模型至少一次
+ 生命周期为derived
+ 尚未被压缩
+ 没有处于归档取回保护期
```

新产生但模型尚未看过的工具结果受保护，不能提前有损压缩。

## 2. 为什么只处理derived

`derived`表示可以重新生成或者属于派生输出，例如：

- 搜索结果；
- 测试日志；
- 编译输出；
- Git Diff；
- Shell输出；
- 部分结构化查询结果。

当前刚读取的源码通常属于 `fresh`，不会因为路由器支持源码类型就自动进入L2。是否进入L2首先由生命周期决定。

## 3. 内容类型如何判断

判断规则写在代码中，主要采用：

- 工具名称提示；
- 正则表达式；
- JSON解析；
- 内容结构特征。

支持的类型包括：

```
SEARCH_RESULTS
GIT_DIFF
BUILD_OUTPUT
JSON_ARRAY
JSON_OBJECT
SOURCE_CODE
HTML
PLAIN_TEXT
```

例子：

```
工具名为rg或grep
→ 搜索结果

包含diff --git、--- a/、+++ b/、@@
→ Git Diff

包含FAILED、ERROR、Traceback、pytest
→ 构建或测试输出

能被json.loads解析
→ JSON

包含def、class、import、function等结构
→ 源码

包含html/body标签
→ HTML

前面都不匹配
→ 普通文本
```

## 4. 不同内容如何压缩

压缩器也是确定性代码，不调用LLM。

例如：

- 搜索结果保留文件路径、行号和代表性命中；
- Git Diff保留文件头、Hunk和统计信息；
- 构建输出保留错误、失败和关键日志；
- JSON保留结构、字段和代表性值；
- HTML保留主要结构；
- 普通文本保留头尾预览。

普通文本Fallback比较接近截断，但整个L2不能简单称为截断。

## 5. L2处理一条还是全部

当L2执行时，它扫描当前有效尾部中的所有合格 `derived tool_result`，不是只处理超过800 Token的那一条。

不过必须满足：

- 原始结果至少约40 Token；
- 路由器能产生压缩版本；
- 压缩版本确实比原文更小。

已经执行过L2的内容会被标记为：

```
l2_route_compacted
```

后续L2不会重复处理。

## 6. L2会不会改变Agent记忆

会改变模型可见的工作记忆。

过程是：

```
保存原始工具结果
→ 将原始结果写入归档
→ 生成内容感知压缩版本
→ 记录压缩替换事件
→ 后续模型看到压缩版本
```

因此：

- 原始JSONL事实仍然存在；
- 原始工具结果归档仍然存在；
- SessionView应用压缩替换；
- 模型看到的是压缩后的内容。

它不是只修改临时请求而完全不改变会话状态；压缩替换会持久化。

---

# 十三、L3：归档替换与渐进式披露

## 1. L3处理什么

L3比L2更激进，会把完整工具结果或L2压缩结果替换成归档占位符。

主要生命周期包括：

### stale

旧读取结果已经失效。

例如：

```
读取user.py
→ 后来修改user.py
→ 第一次读取结果变成stale
```

### superseded

旧读取结果被后来的读取结果替代。

```
第一次读取user.py
→ 第二次重新读取user.py
→ 第一次结果被superseded
```

### duplicate

重复出现的派生工具结果。

### derived

搜索、日志、Diff等可以重新生成的结果。

## 2. 哪些是必须处理候选

以下生命周期属于L3 mandatory候选：

```
duplicate
superseded
stale
```

它们即使在整体预算已经达到目标时，也可能继续被归档。

单条仍超过目标的 `derived` 结果也可能继续进入L3。

## 3. L3处理顺序

候选优先级大致是：

```
duplicate
→ superseded
→ stale
→ 超过单结果目标的derived
→ 其他derived
```

然后根据体积、轮次和在尾部的位置排序。

## 4. L3占位符

完整结果会变成类似：

```
[Tool result archived]
archive_id=ar_xxx
tool=shell
status=success
lifecycle=superseded
original_tokens=3500
summary=shell result is superseded
Use retrieve_archive(...) to inspect the original.
```

占位符最大约480字符。

## 5. 原始结果如何保存

归档采用内容寻址：

```
archive_id = SHA-256内容摘要的一部分
```

保存：

- 原始文本；
- 内容哈希；
- 字符数；
- Token估算；
- 创建时间；
- Schema版本。

读取时会重新校验SHA-256。如果内容或元数据不一致，则拒绝读取。

归档失败时，L3不会替换原始工具结果。

## 6. 如何渐进式取回

模型可以调用：

```
retrieve_archive
```

支持参数：

- `archive_id`：归档ID；
- `query`：只取关键词附近的行；
- `max_chars`：限制返回字符数；
- `full=true`：请求更完整内容。

默认最大返回：

```
6000字符
```

硬上限：

```
12000字符
```

因此可以渐进披露：

```
先看占位符摘要
→ 按关键词查局部
→ 必要时再取更完整内容
```

取回结果会成为一条新的工具结果，不是永久恢复原历史位置。新取回结果在当前轮受到再次压缩保护。

## 7. L3会不会破坏工具调用序列

不会删除工具消息，只替换工具结果内容。

仍然保留：

```
assistant tool_call
→ tool tool_result
```

因此Provider要求的工具调用配对仍然合法。

# 十四、L4：模型语义压缩与Checkpoint

## 1. L4什么时候执行

通常在：

```
L1～L3后仍然没有达到目标
```

才执行。

但 `PROMPT_TOO_LONG` 是特殊情况：即使程序化压缩已经达到目标，管理器仍然会继续尝试L4。

## 2. L4处理什么

L4只总结会话历史，不总结：

- 系统提示词；
- 工具Schema；
- Provider能力；
- 稳定系统前缀。

如果没有旧Checkpoint：

```
L4输入 = 当前有效会话历史
```

如果已经有Checkpoint：

```
L4输入 =
    上一个Checkpoint摘要
  + Checkpoint之后的有效消息尾部
```

不会每次都重新总结最早的全部原始历史。

另外，构造L4摘要Prompt时，每条消息正文最多保留约4000字符，超过部分会先标记为截断。

## 3. L4输出结构

L4固定生成七个部分：

1. 当前目标；
2. 已知事实与硬约束；
3. 已确认的决定及理由；
4. 相关文件与当前实现状态；
5. 已运行命令及有效结果；
6. 当前错误与未解决事项；
7. 下一步（可立即执行）。

输出最大约：

```
1200 Token
```

如果某一项没有历史证据，要求填写“无”，不能编造。

## 4. 模型是否决定Checkpoint边界

当前默认实现中，模型只生成摘要正文，不负责决定Checkpoint边界。

这是之前容易说错的地方。

边界由本地程序选择：

```
covered_until_message_id
tail_start_message_id
```

程序尽量选择一个较靠后的合法尾部起点，同时保证剩余尾部的工具调用序列合法。

模型系统提示词中甚至明确写着：

```
不要选择checkpoint边界
```

随后L4服务再次验证边界：

- 边界必须位于当前有效尾部；
- 被覆盖消息必须位于保留尾部之前；
- 不能切断工具调用和工具结果；
- 不能隐藏尚未成功发送给模型的工具结果；
- 源上下文指纹必须一致。

## 5. L4结果怎么提交

L4先在内存中生成候选Checkpoint，然后用候选重新构建模型上下文并估算Token。

只有：

```
candidate_input_tokens < target_tokens
```

才提交Checkpoint事件。

如果：

```
candidate_input_tokens >= target_tokens
```

结果被标记为：

```
still_over_budget
```

候选作废，不写入会话。

所以：

- 成功提交的L4一定低于目标；
- L4本身不保证一定能够成功；
- 不会提交一个仍然超限的Checkpoint。

## 6. 压缩后模型看到什么

```
新的Checkpoint摘要
+
Checkpoint之后保留的原始消息尾部
```

不是只剩一条摘要，也不是所有原始消息都消失。

## 7. L4是不是无限重试

不是。

失败原因不同，策略不同：

- `prompt_too_long`：允许有限处理；
- `timeout`：允许有限重试；
- `no_summary`：允许有限重试；
- `invalid_tool_sequence`：失败；
- `unconsumed_boundary`：失败；
- `still_over_budget`：当前Fallback直接失败；
- 重复源指纹：跳过；
- 自动压缩熔断打开：跳过。

L4不会把一个失败摘要先提交，再继续总结失败摘要。只有合法且低于目标的候选才会提交。

自动L4连续失败还会记录失败次数，并可能暂时打开熔断器，避免不断消耗模型调用。

# 十五、普通L4与stronger L4

第一次L4通常使用：

```
summary_mode = default
```

Prompt表示：

```
常规压缩
```

只有发生特定失败并进入Fallback时，才可能使用：

```
summary_mode = stronger
```

额外提示：

```
更强压缩，优先保留可恢复事实。
```

因此：

```
进入L4
```

不等于：

```
直接使用最激进摘要Prompt
```

而且 `still_over_budget` 当前不会自动改成stronger再试，而是直接失败。

# 十六、PROMPT_TOO_LONG的两个不同含义

这是最容易混淆的部分。

## 场景A：主Agent请求太长

```
Agent向主模型发正常请求
→ Provider发现输入超过真实限制
→ 返回Prompt Too Long
→ Agent启动上下文恢复压缩
```

这是管理器级触发：

```
ContextWindowTrigger.PROMPT_TOO_LONG
```

流程是：

```
目标设为低水位
→ 执行L1～L3程序化压缩
→ 程序化层达到目标可以提前停止
→ 仍然执行一次普通L4
→ 成功后重试主模型请求一次
```

## 场景B：L4摘要请求本身太长

L4也需要把历史提交给模型生成摘要：

```
L4摘要请求
→ Provider又返回Prompt Too Long
```

这时进入L4内部兜底：

```
尝试更强程序化压缩
→ 如果达到目标，直接成功
→ 如果仍不够，使用stronger模式再尝试一次L4
```

所以：

```
主模型Prompt Too Long
```

和：

```
L4摘要模型Prompt Too Long
```

是两个不同阶段的错误。

# 十七、任务切换与PROMPT_TOO_LONG为什么采用不同的激进策略

先给出源码事实：

```
AUTO目标 = 低水位
TASK_HASH_CHANGED目标 = 低水位 × 2/3
PROMPT_TOO_LONG目标 = 低水位
```

`TASK_HASH_CHANGED`还会强制L1，并要求L2、L3都进入检查；`PROMPT_TOO_LONG`则允许L1～L3在达到低水位后提前结束程序化阶段，但无论是否已经达到目标，管理器都会继续尝试L4。

下面是根据源码行为作出的设计意图推断。源码和测试明确规定了上述行为，但没有完整写出作者为何这样设计。

## 1. 为什么任务切换使用低水位的2/3

任务切换是一种语义触发，它发生时，上下文占用可能本来就不高。如果仍把目标设为普通低水位，当前输入很可能一开始便已经满足预算；即使强制L1并检查L2、L3，也缺少继续大幅释放空间的预算压力。

因此，任务切换采用更低的2/3目标，可以理解为：

- 旧任务价值已经明显下降，允许更积极地清理；
- 给刚开始的新任务留出更长的运行空间；
- 减少旧任务内容对新任务推理的干扰；
- 如果L1～L3清理后仍高于2/3目标，就允许继续进入L4。

我们前面讨论的理解是合理的：任务切换时，总占用可能并不多，很容易满足普通低水位，但需要清理的旧任务内容却可能很多，所以代码用更低目标促使这次“上下文换代”更彻底。这里的2/3主要不是为了修正Tokenizer估算误差，而是为了新任务腾空间和降低旧任务干扰。

## 2. 为什么PROMPT_TOO_LONG不是低水位的2/3

`PROMPT_TOO_LONG`是容量失败后的恢复触发：主请求已经被Provider以输入过长拒绝。它的目标仍然是普通低水位，而不是2/3。

本地Token估算是字符数除以4，不是真实Tokenizer，因此可能低估。例如：

```
本地估算：95,000
Provider真实计算：102,000
模型上限：100,000
```

本地认为可以发送，但Provider拒绝。

它没有通过“把目标降到2/3”留余量，而是采用另一种额外安全措施：即使L1～L3已经压到低水位以下，仍强制尝试L4，把较长历史折叠为Checkpoint。从行为上看，这是因为Provider已经证明本地预算估算不可靠，所以仅满足本地低水位还不够稳妥。

可以把两种策略记成：

```
任务切换的额外策略
= 更低的2/3目标 + 强制L1 + 必须检查L2、L3

PROMPT_TOO_LONG的额外策略
= 普通低水位目标 + 强制尝试L4
```

两者都更激进，但激进的位置不同：任务切换在“目标值和程序化清理范围”上更激进；`PROMPT_TOO_LONG`在“必须做语义Checkpoint”上更激进。

主模型请求在压缩成功后只重试一次。如果第二次仍然Prompt Too Long，就把错误继续抛出，不会无限恢复。

# 十八、手动压缩的目标

用户输入：

```
/compact
```

触发MANUAL。

## 1. 输入不超过2000 Token

不设置更激进的自定义目标，通常因为已经满足默认预算而不产生变化。

## 2. 输入超过2000 Token

先计算：

```
proposed =
    min(
        低水位 - 1,
        当前输入 × 60%
    )
```

再保护固定上下文：

```
target =
    max(
        proposed,
        fixed_tokens + 1
    )
```

只有：

```
target < 当前输入
```

才采用这个自定义目标。

所以手动压缩通常比AUTO更激进，但不允许目标低于无法压缩的固定上下文。

## 3. 什么都没输入时

假设只有系统提示词和工具定义：

```
input_tokens = fixed_tokens
```

如果不超过2000，直接不设置自定义目标。

如果超过2000：

```
target至少为fixed_tokens + 1
```

这个目标反而不小于当前输入，因此也不会设置自定义目标。

最终通常返回：

```
Manual compact skipped
```

不会因为目标不可能达到而无限压缩。

## 4. 高于高水位还能不能手动

程序允许。

正常Agent流程中，AUTO会在下一次主请求前自动处理，因此高水位以上通常不需要用户手动。

但以下情况仍可能手动：

- 恢复一个很大的旧会话，还没发起主请求；
- AUTO熔断；
- 用户希望压得比AUTO更低；
- 用户在主请求前先执行 `/compact`。

# 十九、四种触发方式是否都走L1～L4

不会。

|触发方式|程序化L1～L3|L4|
|---|---|---|
|AUTO低于高水位|不启动|不执行|
|AUTO达到高水位|从L1顺序执行，可提前停止|程序化后仍超目标才执行|
|任务切换|强制L1，必须检查L2和L3|仍超目标才执行|
|MANUAL|按手动目标启动，可能无操作或提前停止|仍超手动目标才执行|
|PROMPT_TOO_LONG|从L1开始，达到目标可提前结束程序化阶段|当前代码仍继续执行一次L4|

因此正确理解是：

```
触发方式
→ 决定是否启动压缩、目标是多少、有没有强制层级

层级内部规则
→ 决定具体处理哪些消息或工具结果

每层处理后的Token
→ 决定是否继续下一层
```

# 二十、一次完整AUTO压缩示例

假设：

```
高水位：90,000
低水位：72,000
当前输入：95,000
```

执行：

```
L1裁剪旧任务对话
95,000 → 88,000
仍高于72,000
```

继续：

```
L2压缩派生工具结果
88,000 → 76,000
仍高于72,000
```

继续：

```
L3归档失效、重复工具结果
76,000 → 68,000
已经低于72,000
```

停止，不执行L4。

如果L3后仍然是：

```
74,000
```

才执行L4。

# 二十一、一次任务切换压缩示例

当前活动任务：

```
task_A：修改登录模块
```

确认切换到：

```
task_B：分析订单模块
```

执行：

```
L1：
立即裁剪task_A的合格普通对话
不要求冷却8轮

L2：
必须进入，检查所有合格derived工具结果

L3：
必须进入，检查stale、superseded、duplicate和大derived结果

检查总Token：
低于任务切换目标（低水位的2/3）→ 停止
仍然超限   → L4
```

即使整体原本低于普通低水位，也会检查L1～L3；它的实际目标是低水位的2/3，因为任务切换除了节省Token，还试图清除旧任务干扰并为新任务腾出空间。

# 二十二、一次PROMPT_TOO_LONG恢复示例

```
本地估算没有达到高水位
→ 向Provider发送主请求
→ Provider使用真实规则判断输入过长
→ 返回maximum context length exceeded
```

Agent执行：

```
触发PROMPT_TOO_LONG
→ 目标设为低水位
→ L1
→ 达到目标且无强制候选，程序化阶段停止
→ 直接执行普通L4
→ Checkpoint合法且低于目标
→ 提交Checkpoint
→ 重试主请求一次
```

因此可能出现：

```
L1 → L4
```

不一定每次都是：

```
L1 → L2 → L3 → L4
```

# 二十三、整个设计的核心原则

可以总结成六点。

## 1. 先规则，后语义

```
L1～L3：确定性程序规则
L4：模型语义压缩
```

先使用更可控的规则，最后才让模型总结。

## 2. 从低风险到高风险

```
旧任务普通对话
→ 派生工具结果压缩
→ 工具结果归档
→ 整体工作状态总结
```

## 3. 不直接删除底层事实

原始JSONL事件通常保留，压缩主要改变模型有效视图。

但“原始数据存在”不代表“模型还能直接看到”，尤其是L1。

## 4. 保护未消费工具结果

工具结果至少成功发送给模型一次后，才能进入有损L2/L3处理。

## 5. 保持工具调用完整性

任何压缩和Checkpoint都不能切断：

```
assistant tool_call
→ tool result
```

## 6. 压缩结果必须有实际收益

- L2结果必须比原文小；
- L3归档必须成功；
- L4必须低于目标；
- 不满足则不提交替换。

# 二十四、源码中值得在面试里主动承认的问题

## 1. 分类请求增加成本和延迟

每条新用户消息通常多一次隐藏模型请求，而且输入包含当前有效历史。

优化方向：

- 小模型；
- 本地分类模型；
- 规则优先；
- 只提供任务摘要和最近消息。

## 2. active与candidate语义不清晰

模型只返回 `same`，程序却在不同状态下解释为：

- 继续active；
- 继续candidate。

分类Prompt没有明确描述候选任务，存在契约不一致。

## 3. L1比较激进

L1不总结、不归档，只从模型有效上下文隐藏旧任务普通文本。误分类可能造成较大影响。

## 4. Token估算不精确

字符数除以4不能完全匹配不同模型Tokenizer，因此需要高低水位和Prompt Too Long兜底。

## 5. L4仍然可能丢失语义

即使采用七段结构，模型摘要仍可能遗漏细节。原始日志存在，但模型恢复时主要依赖Checkpoint和消息尾部。

## 6. L4边界选择较激进

本地程序会尽量保留较少但合法的原始尾部，其余内容交给Checkpoint覆盖。如果摘要质量不足，可能损失近期细节。

## 7. PROMPT_TOO_LONG路径成本较高

真实Provider拒绝后，目标仍是普通低水位，但当前代码即使程序化阶段达到目标，仍继续尝试L4。这有利于进一步留出余量，但会增加一次模型摘要调用。

# 二十五、面试时可以这样总结

> 我把上下文管理分成任务边界、Token预算、程序化压缩和语义Checkpoint四部分。系统在每次主模型请求前估算固定上下文和历史上下文的Token占用，达到高水位后，以低水位为目标依次执行L1到L4。L1裁剪旧任务普通对话，L2按搜索结果、Diff、构建日志和JSON等内容类型压缩派生工具结果，L3将失效、重复或过大的工具结果归档为可按需取回的索引，前三层仍无法达到预算时，L4才通过模型生成七段式开发Checkpoint。
> 
> 除高水位AUTO外，系统还支持任务切换、手动压缩和Provider实际返回Prompt Too Long三种触发。底层会话采用append-only JSONL保存，压缩主要改变提供给模型的有效上下文视图，同时保护未消费工具结果和工具调用配对。当前不足主要是任务边界分类需要额外模型请求、active与candidate的语义契约不够明确、L1裁剪较激进，以及字符近似Token与真实Tokenizer存在误差。
