## 5、压缩机制怎么做的？


如果面试官问我“你这个项目的四层上下文压缩是怎么设计的”，我会这样回答：

我们不是等模型报 `Prompt Too Long` 才压缩，而是通过 Token Budget 提前治理上下文。系统会分别统计系统提示词、工具定义和历史消息的 Token 占用；当输入达到上下文容量的高水位时触发压缩，目标是降到低水位。

当前默认配置中，高水位是输入容量的 90%，低水位是 72%。压缩按照 L1 到 L4 逐层执行，但并不是每次都会走完四层：每完成一层都会重新估算 Token，如果已经降到目标范围，就立即停止。

### 第一层：旧任务对话裁剪

L1 处理的是已经结束或不再活跃的旧任务对话，主要包括普通的用户消息和助手回复。

它有两种触发场景：

第一种是正常的 Token 压力。当上下文达到高水位后，系统会优先寻找距离当前至少 8 轮、并且不属于当前任务的冷对话，把它们替换成简短的裁剪标记。

第二种是检测到[[任务切换]]。比如用户从“分析登录模块”切换到“修改订单接口”，即使当前 Token 还没有超出预算，也可以强制清理旧任务对话，避免旧目标继续干扰模型。

这一层有几个保护条件：

- 不删除当前任务的消息；
- 不删除最新一条用户请求；
- 不单独裁剪包含工具调用的助手消息；
- 不破坏 `tool_call` 和 `tool_result` 的配对关系。

L1 本质上是在清理价值最低的闲聊和旧任务过程。如果压缩后已经降到低水位，就不会再执行后面的层级。

### 第二层：工具结果的内容感知压缩

如果裁掉旧对话后仍然超出预算，就进入 L2。L2 主要处理体积较大的工具结果，但不是简单按字符截断，而是先判断内容类型，再使用对应的压缩策略。

系统目前会区分搜索结果、编译与测试输出、Git Diff、源代码、JSON、HTML和普通文本等内容。例如：

- 搜索结果保留文件路径、行号和命中片段；
- 编译日志优先保留错误和失败信息；
- Git Diff 保留文件头、变更块和统计信息；
- JSON和HTML保留主要结构；
- 普通长文本保留摘要和关键信息。

L2 在两种情况下会执行：

- 整体上下文超过预算；
- 某一条工具结果自身过大。当前默认单条结果超过约 1200 Token，就会形成单结果压缩压力，即使整体上下文还没有到高水位，也可以对它进行处理。

工具结果在被压缩前必须至少成功发送给模型一次。也就是说，刚产生但模型还没有看过的结果不会立即被压缩。

另外，在做有损替换之前，系统会先把原始结果完整归档，并记录摘要、哈希和归档编号。如果归档失败，或者压缩后的内容没有变小，就继续保留原文。

所以L2的特点是：原始数据仍然存在，只是提供给模型的上下文变成了更紧凑的结构化版本。

### 第三层：工具结果归档替换

如果L2完成后仍然超出预算，就进入L3。L3比L2更激进：L2是压缩内容，L3则会把旧工具结果替换成一个很小的归档占位符。

L3重点处理以下几类结果：

- `stale`：读取文件后，该文件又被修改，旧内容已经失效；
- `superseded`：同一个文件后来被重新读取，前一次结果已被覆盖；
- `duplicate`：重复出现的搜索结果或命令输出；
- `derived`：可以重新生成的日志、搜索结果、Diff等派生内容；
- 体积特别大的旧工具结果。

替换后，上下文里会保留归档编号、生命周期状态、简短摘要和关键错误。例如模型仍然知道“之前执行过测试并出现两个失败”，但不再携带几千 Token 的完整日志。如果后面确实需要原文，可以通过归档读取工具按编号取回。

这一层同样会保护：

- 当前轮刚读取的源码；
- 还没有被模型消费过的工具结果；
- 无法确定是否已经失效的结果；
- 归档失败的结果；
- 当前任务仍然依赖的关键内容。

L3不会删除工具消息本身，只替换工具结果的内容，因此工具调用事务仍然是完整的。某些明确失效、重复或单条过大的结果属于必须处理的候选，即使整体 Token 已经暂时低于目标，也可能继续完成归档。

### 第四层：模型生成结构化检查点

如果前三层确定性压缩完成后，上下文仍然超过目标，才进入L4。它是最后一层，也是唯一需要调用模型进行语义压缩的一层。

L4不会简单总结聊天内容，而是生成一份可以继续开发的结构化工作交接，固定包含七个部分：

1. 当前目标
2. 已知事实与硬约束
3. 已确认的决定及理由
4. 相关文件与当前实现状态
5. 已运行命令及有效结果
6. 当前错误与未解决事项
7. 下一步（可立即执行）

它的触发场景主要有：

- L1到L3处理后仍然高于目标水位；
- 用户主动要求压缩或创建检查点；
- 模型已经返回上下文过长，需要立即恢复；
- 某些恢复流程明确要求生成新的检查点。

模型除了生成摘要，还要提出一个压缩边界，说明历史覆盖到哪条消息、从哪条消息开始保留原始尾部。但这个边界不能由模型直接决定，系统还会在本地验证：

- 边界是否位于当前有效消息范围内；
- 是否把未消费的工具结果隐藏了；
- 剩余消息中的工具调用配对是否合法；
- 生成摘要期间原始上下文是否发生变化；
- 新上下文是否真的降到了目标水位。

只有全部验证通过后，才会追加一条 checkpoint 事件。恢复会话时，系统加载的是“结构化检查点 + 检查点之后的原始消息”。

如果验证失败，不会覆盖原始历史，而是进行有限次数重试；自动压缩连续失败后还会触发熔断，防止模型反复生成无效摘要。

### 总结

我把四层压缩设计成了一个由低风险到高风险的渐进式过程：

- L1清理已经结束的旧任务对话；
- L2对大体积工具结果做内容感知压缩；
- L3把失效、重复和可恢复的工具结果替换为归档引用；
- L4将整个工作状态压缩成可恢复的结构化检查点。

前三层是确定性压缩，规则明确、结果可验证；第四层才使用模型做语义压缩。同时，整个过程只改变提供给模型的上下文视图，不直接删除底层的 append-only 事件和归档数据，所以既能控制 Token，又能支持审计和任务恢复。

# 面试问题
## 1、为什么要自己做一个新的coding agent？
有以下几个原因吧。
	1、coding agent 相较于别的智能体，学习资料比较多。   比如learn-claude-code。opencode，claude code 的源码等。方便我进行学习
	2、我觉得agent的技术是通用的。比如上下文管理，记忆管理，权限管理，HIT，测评等等等，我做好一个这个agent，可以让我在做其他agent时都能用上。现在的llm是输入文字，输出文字，不管什么agent，他都要做上下文管理，长短期记忆，权限管理，审批等。在企业办公agent，不同的人能使用不同的东西，这是一种权限管理。对于主管需要审批，这是HIT。所以我想亲自动手做一个coding agent ，来了解这些技术。毕竟对于现在的大模型来说，不管模型怎么更新，他的本质还是一个输入文字，输出文字的机器。上下文，记忆这些东西都少不了。
	3、coding agent 是我日常接触过程中，使用的最多的agent。不管是写代码， 还是让他帮我工作，coding agent 是能作为成熟的产品的（这也是我唯一会花钱使用的agent，能够让用户有付费意愿），当然企业内部也有很多使用的agent，但是我接触的不多，所以我选择做一个coding agent。
	4、coding agent 有一种自由的感觉（对llm来说，但是也是一种挑战），我之前做过一个简单的pr review的workflow的agent 。它没有记忆，没有权限管理。一开始我给他分成几个阶段，提示词中告诉agent，你就按这几个阶段走，先判断这个pr是否适合自动审批，然后搜集信息，然后根据我定义的规则（什么风险等级，小bug，什么可优化等等），进行pr审批。然后根据审批结果，采取行动。给了它一堆工具，获取pr信息的工具（什么diff，pr的描述），以及根据审批结果采取行动的工具。后来我发现，没必要，因为pr信息的采集，这个东西是确定的，到了这个阶段，我直接将这个pr的所有信息发给agent，让agent进行判断，这个不更好了嘛。不仅节省了上下文，能让agent集中注意力根据规则对pr进行 review。以及最后阶段，几条支路是确定的。也可以脱离模型的决策。   包括我的第一个项目，我用langgraph搭建的。呢个执行阶段，它也不太需要模型的参与，直接根据计划（使用什么工具，什么参数），进行执行就好了。而coding agent 不一样，所有的东西没有确定性。也就是langgraph没有条件边。就显得非常的需要控制，我学会了控制一个coding agent，那么我做一些有流程流转的agent时，就能更好的判断，那些需要确定性，那些需要模型来做决策，也能让我掌握如何更好的做一个agent。
